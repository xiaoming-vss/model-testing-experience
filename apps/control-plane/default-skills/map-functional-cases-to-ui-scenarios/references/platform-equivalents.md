# Existing platform expressions, without new executor keywords

The caller's capabilities list is the set of semantic labels allowed in design output. Keep that list unchanged. In this platform, the downstream YAML skill can select an element by XPath 1.0 and assert its visibility. A true selector predicate therefore implements a condition on the selected DOM scope. These are existing execution features, not new count/set operators. Their count, uniqueness, exact finite-set and scalar baseline forms have been exercised through the existing StepExecutor on synthetic Chromium DOM. Do not claim that the business application was executed.

Before excluding a requirement solely because its direct operator is absent, check these equivalents:

- A fixed visible table row count can be represented as an included `visible` expectation whose semantic target is the table satisfying the required row count and whose value retains that count. Downstream XPath uses `count(tbody/tr)=N`. Do not discard “first page has 10 rows” merely because `count` is not a named assertion. This proves rendered rows on that page, not unseen pages.
- Uniqueness within a fully observed table can be expressed by an included `visible` expectation on the table containing no repeated identity cells, using a predicate such as `not(tbody/tr[td[ID_COLUMN]=preceding-sibling::tr/td[ID_COLUMN]])`. Do not add a new keyword or output actual locators during design.
- A fixed, complete fixture set can use exact total plus exactly one occurrence of each expected ID, expressed through `visible`. Unknown fixture IDs remain data gaps if this complete finite strategy is valid. Count plus membership alone does not prove multiplicity. No fixed small sample stands for an unbounded full list.
- A button's DOM disabled attribute, a checkbox's source-backed checked attribute, or another DOM attribute state may be selectable as a predicate for `visible`. Keep the semantic condition in target/value. This does not invent a hover action or a general assertion on JavaScript properties.
- A displayed select label/placeholder can use `text_eq`/`text_contains`. For a real input/textarea live value, observe it with the existing scalar saveTo source=value, then use an included visible predicate comparing that captured scalar with the expected value. This has been exercised after editing an input whose original value attribute remained different: correct live value passes, wrong or empty values fail. Do not compare a stale markup value attribute or textContent instead of the live property. Model capture as observe and comparison as visible under the unchanged profile; lack of a named input_value assertion does not by itself justify exclusion. An explicit restriction disabling scalar capture must still be honored.
- The downstream platform supports scalar `saveTo` observations of element text, input value, attributes and URL, followed by variable substitution into supported fields. Model the capture as an included `observe` action with its producer/consumer relationship in target/value; do not add a `variable_capture` label to the caller profile. Scalar capture does not imply array extraction, arbitrary code, loops or set operations. Honor an explicit caller restriction if one disables this feature.
- XPath arithmetic can compare a row count with a known fixture total minus a constant, without a new arithmetic keyword. If the comparison needs a runtime captured value, use the supported scalar observation described above and an earlier producer; do not invent a variable or replace a runtime observation with an independent unrelated fixture.

State the equivalent expression semantically in existing target/value/limitations fields, with the appropriate declared primitive (`visible` or textual assertion). A design-stage proof does not require inventing a concrete selector, column number, fixture ID or count bound. Stage three resolves source-backed locators. Missing locators are not capability exclusions.

This does not solve arbitrary-page traversal. If the requirement spans an unknown number of pages, a predicate on one rendered table is insufficient, even if it works perfectly within one page. Expose that genuine scope limit, preserving the full original requirement and independent supported checks. Never assume that 10, 200, or a minimum prerequisite count is the complete dataset size. Do not require two source categories to appear on the first page when the original condition concerns their existence across the full result.

## Two explicitly observed pages: compare the observations, not an invented array

When the source explicitly observes pages one and two, and the first page has a fixed K rows, the retained claim about those two observations can be implemented without a set_merge keyword or dynamic iteration:

1. Assert first-page count K and internal ID uniqueness, and capture its K IDs as separate supported scalars.
2. Navigate to the second page. Assert its required row count, internal uniqueness, and that none of its IDs equals any of the captured first-page IDs.
3. For “distinct union count equals total N,” the count conditions K and N-K plus the uniqueness/disjointness conditions prove precisely that claim. No array needs to be materialized. An excluded raw array-building/set_merge operation does not force exclusion of this independently expressible result.

This is an expression of a two-observation assertion, not an assumption that the dataset inherently fits two pages. If N exceeds the amount those pages can display, the original “second page contains N-K remaining rows” expectation fails. Preserve that expectation and expose its conflict with an unbounded prerequisite; do not invent an upper bound or call the predicate unsupported. If the source instead requires reading an arbitrary number of pages, this strategy does not satisfy it.

For equality against an independently known complete expected fixture ID set, additionally require every ID on both observed pages to belong to that set, and the summed count to equal its cardinality. Together with both internal uniqueness checks and cross-page disjointness, this proves exact equality and rejects substitutions, duplicates and missing records. These combined checks were exercised through the real StepExecutor on synthetic Chromium DOM. Unknown static expected IDs are a data gap when that complete fixture set can be supplied before execution; never derive the expected set from the result under test itself. If the baseline must first be extracted from an unknown number of pages, its construction remains a genuine unresolved traversal dependency.

Keep identity completeness distinct from cardinality. Without an independent expected-ID oracle, distinct count alone does not prove that the correct identities were returned. Explain the actual missing oracle or unsupported traversal, rather than claiming that every finite collection comparison requires a new executor operator.

## Finite composition across states and views

XPath predicates support boolean `or` and `and`: a visible status element whose text equals A or B implements that exact alternative without a text_eq_any keyword. Preserve the source's expected states; do not silently rename an expected state to match the current implementation. Filtered row counts and comparisons to another element or an earlier captured scalar likewise use predicates: for a fully observed three-item detail table, successful-row count equals the displayed progress numerator is expressible. An explicit two-successful-of-three observation is not an unbounded time-series aggregation. A genuinely unbounded polling history remains a separate unsupported dependency.

The finite scalar proof extends to any explicitly bounded sequence of pages or views, not just two pages. Capture each identity in the bounded earlier observation, then assert the later view's exact count, uniqueness, and membership against those captured identities, retaining any required same-row field relationships. A fixed three-record task detail versus its three-record exported dataset does not require array extraction or dynamic iteration. Three specified page observations can be checked with pairwise disjointness, individual counts and fixture membership; an unspecified number of intervening pages still cannot be inferred. A conditional next-page branch with an authoritative single-page fixture is discharged by checking total and current count, rather than declaring the entire case unsupported for a branch that cannot occur under its own prerequisites. Preserve the conditional source text and explain the finite realization.

Identify a page by its actual page index, not the order in which it was visited. “Page one, page two, then the last page” may revisit page two. Reading the same physical page twice neither adds new dataset members nor proves a duplicate-data defect; pairwise disjointness applies to distinct pages, not repeated observations of the same page. Retain the source's union/identity semantics and explain any source contradiction. Establish a complete supported predicate proof for the actual observation pattern; an explanatory limitation alone does not repair an incompatible included predicate.
