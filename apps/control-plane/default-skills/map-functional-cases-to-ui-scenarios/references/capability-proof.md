# Check capability claims before finalizing design

This is a design reasoning pass, not an additional output schema. Use the caller's declared capability profile; preserve original case identities, prerequisites, source clauses and core goals. Do not change fixture sizes or remove original requirements to make a case easier to automate.

For each included target, identify its required observation, transformation and comparison. Check the complete relationship, including its page/time scope and runtime dependencies. Unknown fixture values or missing locators are ordinary completion gaps when the strategy remains valid after those values are supplied. Missing loops, aggregation, or a necessary unsupported operator are capability dependencies; a missingFields locator cannot supply them later.

For a target depending on an excluded operation:

- Retain it when a supported equivalent implements the whole relationship without the excluded operation. Explain the relationship in existing target/value/limitations text; no executable locator is needed at this stage.
- Otherwise classify the dependent semantic check with the precise unsupported operator and an honest limitation. Do not retain it as a plain text_eq check whose expected input must be calculated manually or by an unavailable tool during execution.
- Preserve independently supported clauses and all original source accounting. A partial case must explicitly say when its core goal is not covered. Exclusion is a disclosed limitation, never evidence of success.

Examples:

1. A known single expected ID plus authoritative total one can establish the complete singleton result using supported comparisons. Do not reject it just because the requirement says “all records.”
2. For two explicitly observed pages, use the complete scalar-and-predicate strategy in platform-equivalents.md before excluding a distinct-count or finite fixture-set result. Both page counts, both internal uniqueness checks and cross-page disjointness are necessary. The assertion may fail when an unbounded prerequisite permits more records than two pages can display; that is a preserved requirement conflict, not proof that the two-observation assertion is unexpressible. Never silently add an upper bound.
3. “Read every page and compare the complete collection” with unknown page count requires a genuine complete traversal strategy. If the profile has neither runtime iteration nor an established finite scope that can be expanded, do not relabel the traversal as a single observe or aggregate comparison as text_eq. Preserve exact source clauses under precise unsupported operators such as iterate_pages or collection_eq, with the missing capability explained. Do not invent a maximum of 10 or 200, and do not treat a page-size change as proof of complete coverage.
4. A source branch hides a required column. This may be a product defect: an expressible expectation on that intended column remains included. Do not exclude it as an executor limitation solely because it will fail on the current implementation.
5. An existing fixture ID or expected label is unknown. Keep the target included when supplying that value completes the supported strategy. An environment prerequisite supplied externally before execution differs from a calculation that the test must perform on newly observed values.

Finish by checking that included targets do not rely on excluded runtime transformations without a complete alternative, and that limitations distinguish unsupported scope from ordinary unknown data. Respect the caller's exact profile rather than claiming an operator is supported because a similarly named primitive exists.

## Recheck every clause after format repair

A syntactically valid response can still lose requirements. Re-read each original expected result clause by clause. A combined expectation is valid only when its target/value and supported expression establish every clause under that status; otherwise split the original contiguous excerpts and classify them separately. Do not label a whole source sentence by its first clause.

- “The total is shown, equals the prepared count, and page size defaults to 10” needs visibility plus both equality checks; a single visible-total target does not cover it.
- “Page two shows the remainder, whose count is total minus ten” cannot become a plain visible-row assertion while retaining the full quote.
- “Recording is complete and the recorded count equals the displayed total” contains both bookkeeping and a business comparison. Only the recording instruction may be bookkeeping.
- “Source shows A, project remains empty, query executes” cannot become only a source=A comparison.
- A globally required witness need not be on page one. Do not silently replace across-result existence with first-page existence.

Format-only repair must not merge these distinctions, demote business assertions to bookkeeping, or replace precise limitations with “see excluded items.” Preserve core unsupported claims explicitly in limitations, without presenting surviving setup checks as proof of the original goal.

## Complete lists also have scope when pagination is implicit

“Task count and task-ID list equal the baseline” compares two objects. A count equality target alone cannot cover the list equality clause, even when both appear in one grammatical sentence. Split their source excerpts as needed, retaining their full semantic comparison in target/value. A list [A,B] changed to [A,C] is a concrete equal-count counterexample.

For “no omitted or extra records even when counts match,” test a replacement counterexample: expected [A,B] versus observed [A,C]. Both IDs can be nonempty, both can have the correct data type, and counts and uniqueness can all match. Those properties do not establish identity completeness. Keep the original identity claim: use an independently supplied complete expected-ID oracle plus finite exact membership when the observation scope supports it. If only the expected count was supplied, name the independent identity oracle as a concrete input gap; never fabricate its values or derive it from the result under test. If constructing that oracle requires unavailable runtime traversal, disclose that dependency instead. Do not write “0 omissions” from count+uniqueness or “0 extra records” from nonempty IDs, even inside limitations. Similarly, unchanged count alone does not prove no newly created identity and cannot discharge a conditional identity inspection on that basis.

A complete list remains complete scope even when the source does not explicitly say “every page.” For a paginated list of unknown total size, declaring `visible` with target “ID list equals baseline” is not an implementation proof. Use an established complete observation strategy or explicitly classify the unresolved traversal/collection dependency. A prepared baseline list supplies an oracle; it does not make all current-result rows visible. Conversely, a fixed selected set, an explicitly bounded observed result, or checking one newly captured ID against a static fixture list can have a finite supported proof and must not be excluded merely because it mentions a list.

Keep a source clause's scope attached to its status. An included claim that “every result has status X” must cover every result; a target restricted to the current rendered page plus a limitation about unseen pages does not implement that claim. If the original whole-scope clause cannot be split into independently stated source subclauses, preserve it as excluded with the precise scope dependency, rather than inventing a narrower included excerpt. Likewise, do not defer missing traversal to stage three. A singleton query is different: authoritative result total one, one rendered row and its exact expected identity prove the complete result without traversing other pages. Prefer that finite proof where its expected cardinality is actually part of the requirement.

For negative actions, distinguish the retained whole-list equality from its weaker count or disabled-control checks. Do not claim full coverage merely because the button is disabled or total count stays unchanged when the source also requires checking the complete ID/name list. Keep supported count and control-state checks, and disclose any genuinely unimplemented identity scope. Do not invent concurrent activity to reject a valid fixture assumption; the counterexample establishes an untested identity change, not a claim that such activity occurred.

## Apply coverage to producers and active UI context

Classify every clause of actions as well as assertions. Bind an action summary to its original sourceAction/sourceQuote: observing a panel or feedback does not additionally establish whether a new business record exists. Keep an expected outcome in its own accounted expectation; if the original action also explicitly requests that outcome, classify that clause using the same capability proof. Excluding a full-collection result does not leave its unknown-page enumeration or collection comparison automatically implementable as observe, even when appended to an otherwise supported panel observation. Check included action/target/value text against the excluded claims and limitations; split mixed clauses so the supported UI observation remains and the unsupported claim stays explicitly excluded. Likewise, observe(condition) does not implement conditional control flow. Retain a conditional action only with a complete supported strategy; otherwise classify the conditional part and dependent claims precisely, while retaining independent controls and scalar observations.

Attach each observed value to its identity, filter, tenant/session, page scope and observation time. An ID-filtered result total cannot be compared to a baseline from the whole list. Preserve the source's total relation by capturing the same-scope total before filtering, or by explicit supported clear/query actions restoring that scope. After navigating to a different result or an empty result, a previous row must be revisited or its needed fields must already have been captured. Changing tenant/account requires the supported logout/login/input/click/identity-confirmation sequence; navigate alone does not create a new session. Unknown credentials remain input gaps.

For each runtime consumer, identify the earlier concrete producer and capture target. A capture may be attached to a supported interaction when the platform allows it; the operation label alone is not evidence that capture is absent. Specify the observation in action/target/value so it can actually be bound. Distinguish independently chosen input from observed display value: comparing a captured display only to itself cannot test that input was applied correctly. Full-record correspondence includes the original same-row field relationships, not only one retained ID column.

Wait for an explicit required final state or declared terminal-state set. “Not running” also matches queued/not-yet-started states and is not a terminal condition. Status change needs ordered observations or an explicit final-state relationship, not merely a nonempty label. Final equality of a failed state does not establish that a retry never executed; preserve any required attempt identity/history proof or its missing capability. Business statements about counts or state updating according to actual results remain assertions even when the source also asks to record them.
