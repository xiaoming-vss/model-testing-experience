# UI case design contract

Return `{schemaVersion: "ui_test_scenarios/2.0", capabilities, cases}` directly as the final JSON response. The supplied cases define this invocation’s entire scope: under module batching, output exactly the IDs in `batch.caseIds`, without adding cases from other modules or omitting any current-module case. Keep the original case order. The Worker schedules one batch per module, validates and repairs each independently, and checks the merged result against the full selection.
Capabilities contains `operations` and `assertions` arrays with supported semantic capability names. Use the supplied capability profile; if absent, use this platform baseline:
operations: navigate, click, dblclick, input, clear, press, wait, observe, reload, screenshot, sleep.
assertions: visible, text_eq, text_contains, url_eq, url_contains.
`select` is implementable by clicking a select and its option. Model it as click operations, without requiring either locator. A textual total can be text_eq. The profile has no direct collection equality, input_value, attribute, absent, disabled, count, variable_capture, hover or time_bound operator; absence of a direct operator does not rule out an equivalent expression through declared primitives. This platform supports source-backed XPath predicates for visible checks: consult platform-equivalents.md before classifying a fixed count, state or finite-collection check. The downstream platform supports source-backed scalar text/value/attribute/url observations with saveTo and later variable substitution; express these as observe under the unchanged caller profile. This does not imply array extraction, iteration or set comparison. The supported XPath composition boundaries are described in platform-equivalents.md. Express dependencies in the existing semantic fields. Initial inputs are environment prerequisites, runtime outputs need an earlier producer. Evaluate the acceptance question, not keywords in its wording.

Each case has:
- `caseId`: original caseId (one design per selected case).
- `name`: meaningful UI case name; `sourceTitle`: unchanged original title.
- `preconditions`: unchanged original list. These are required conditions, not statements that the environment is prepared.
- `goal`: original acceptance question; `coreExpectationIds`: IDs of defining expected excerpts, including excluded ones.
- `steps`: one entry per original source step, preserving order. Each has `sourceStepNo`, `sourceAction` (verbatim), `actions` and `expectations`.
- Each action: `actionId` unique within the case, `sourceQuote` (verbatim contiguous excerpt of the original action), `action` (UI instruction), `operation` (semantic capability), `target` (semantic object), `value` (known value or null), `status: included|excluded`, `reason` when excluded. Split compound actions so an unsupported operation does not remove supported navigation/input/clicks. Action excerpts account for the complete sourceAction exactly once, as expectation excerpts do for expected text.
- Each expectation: `expectationId` unique within the case, `sourceQuote` verbatim contiguous excerpt of that step's expected result, `assertion` (semantic capability), `target`, `value` (literal, business relationship or null), `status: included|excluded|bookkeeping`, `reason` when not included.
- `coverage: full|partial|excluded`: full when all actions and non-bookkeeping expectations are included; partial when some are included and some excluded; excluded when none are included. This is design scope, never a test pass or runnable status.
- `limitations`: explanations of excluded core claims and any dependency of a retained assertion on an excluded action. An external setup prerequisite may remain required, but a missing automation strategy is not an ordinary data/locator gap. Before retaining an assertion that depends on an excluded action, identify a complete equivalent supported strategy. If no such strategy exists, classify the dependent check under its actual unsupported semantic operator and preserve its source clause and core limitation; do not label it text_eq merely because a hypothetical external tool could return text.

Included operations/assertions must belong to capabilities. A supported assertion such as `text_eq` cannot be marked excluded; for an actually unsupported business check, name the precise unsupported operator and explain its limitation. Excluded ones must be outside capabilities, with an explanation such as an external storage check or unsupported set comparison. Bookkeeping applies only to recording instructions, never business conditions. Unknown locator/fixture/value does not justify exclusion. Retain known semantic values even when locating is unresolved. Source conflicts remain intended tests that may fail.

Every original expected clause is accounted for exactly once across expectations, including punctuation/connecting words in adjacent excerpts. Never drop a qualifier to make an assertion supported. Whole unsupported clauses may be excluded while independent supported clauses remain included.

No actionBindings, observationBindings, locatorType, locatorValue, dataPlan or ready/missing_page statuses are required or emitted. Stage three receives this design plus original cases, stage-one surface, sourceRoot and execution context.
