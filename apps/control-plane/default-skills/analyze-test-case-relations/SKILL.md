# 测试用例关联分析

每条原始用例就是一个图节点，节点名称由调用方读取原始 case_title。直接用 case_id 连接用例，输出主骨及有向关联边；不另外建立业务流程节点，不输出用例正文或图坐标。关联表示业务场景衔接或派生，不表示用例必须依赖彼此执行。

## 输入

读取正文、附件或分次提供材料的实际内容，无需额外输入包装：

1. 原始需求：文本或 Markdown 功能理解记录。
2. 最新版需求分析：含 functionalOverview、scenarioFactors、businessRules、scenarioBreakdown、openQuestions 的 JSON。
3. 原始完整用例：顶层 cases 数组；每项包含唯一非空字符串 case_id，以及 case_module、case_title、case_type、priority、precondition、test_steps、expected_results。后三项为字符串数组。
4. 已有关系 JSON（可选）：2.0 结果可用于保留仍适用的 path_id、edge_id；旧版业务流程映射仅作分析线索，不能直接转换成用例间连线。

正常流程结合前三项；独立处理历史用例时可仅提供完整用例，但只建立内容明确且无冲突的关系。测试点 JSON 不是必要输入，不读取无关任务补需求。

## case_id 硬性约束

- 先从本次输入的原始 `cases` 建立允许引用的 `case_id` 集合。`main_paths[].case_ids[]`、`edges[].from_case_id`、`edges[].to_case_id` 必须逐字存在于该集合中。
- 禁止凭空生成 ID、临时编号、截断、补齐、修改大小写，或用标题推测 ID。示例中的 C001 等仅用于解释格式，不能复制到实际结果中，除非本次输入确实包含该 ID。
- 历史关系或其他材料中出现的 ID 也不能替代本次输入：只有属于本次输入集合的 ID 才允许引用。缺少对应原始用例时，不创建占位节点；需要恢复该关系时先澄清缺失输入。
- 输出前逐项检查所有引用的集合是否为输入 ID 集合的子集。未知 ID 是错误，不得交付；不能通过向原始 cases 添加虚构用例来让校验通过。仅 `path_id` 和 `edge_id` 可以为新关系生成。

## 关联判断

- 原始需求和用户明确补充决定业务规则；最新版分析辅助定位场景与缺口。遵循用户指定来源优先级和最新明确确认；示例或推导不能自动成为产品事实。
- 阅读标题、前置条件、步骤和预期，内部记录候选关系的依据。不能仅因名称相似、同属模块、共用账号、覆盖同一业务路径或输入相邻就连线。
- `next`：目标用例验证源场景的后续业务阶段。必须能指出源场景建立的状态或业务结果如何衔接目标场景，并结合目标的前置、动作和断言确认；只有术语的阶段顺序或共用前置条件不足以成立。若目标只是改变配置取值、失败位置、角色、切换方向或断言角度，应优先判断为派生/并列场景，不据此生成 next。无需前一条测试实际执行，也不能宣称结果展示用例覆盖了此前处理步骤。
- `branch`：目标是源场景的替代、异常、边界、权限、性能等有明确对象的派生或补充场景。仅有宽泛主题相同不足以建立关系。它不意味着两个场景一定互斥或同时执行。
- 父场景选择检查业务对象、验证范围和条件变化：目标须能明确解释为源场景的替代或补充；互斥取值可以形成替代分支，但不能把一个并列情形误当作另一个情形的基础。例如“保留任意历史值”不能仅凭同属配置，挂在“初始值必须为某值”的检查下。多个候选中选实际覆盖该变化的最直接场景，不按词语相似度或模块归属选父节点。分支可继续 next 或再次 branch，层数不限。
- 多个场景有共同后续时允许指向同一 case_id，不复制用例。多个关联有独立依据时可以多入边，不强制每条用例只有一个父节点。
- 同一个原用例可能覆盖多个阶段，但仍只是一条用例；不得拆分、改名、新增节点或分配新 case_id。没有明确关系的用例保持独立，不为凑鱼骨或关联率强行连线。
- 并列分支、汇合仅表达图结构，不表达并发、等待全部成功等调度规则。不得恢复旧版并行业务节点来代替用例。重试一般关联到已有重试用例，不能仅因“重试”一词生成回边或自环。

## 工作流程

1. **核对输入。** 核对完整用例与 ID，读取 [输出协议](references/output-contract.md)、[输出模板](assets/output-template.json) 和 [关联示例](references/association-examples.md)。ID 缺失、重复或目标用例集不明确时集中澄清，不临时编号或以空结果掩盖输入错误。
2. **先识别完整业务链。** 从需求和完整用例识别业务目标、对象、配置/状态的生效与消费、处理及结果等实际存在的阶段。阶段仅用于内部分析，不输出或新增业务节点。跨模块检查有依据的衔接，不先按模块、标题主题或局部 next 分组；没有的阶段不强行补齐。
3. **先定直接关系，再选主骨。** 为候选用例对判断后续、派生/补充或无明确关系，并记录内部依据。检查某用例所验证的配置/结果是否被其他场景实际使用，避免遗漏有依据的跨阶段连接。对多个并列条件场景寻找共同基础用例，不能按正常业务的阶段顺序串联不同失败场景。重叠覆盖也不自动表示 next；应有可解释的业务阶段衔接。
4. **从已确认关系选主骨。** 同一业务目标下可衔接的阶段组织为同一骨架；优先选择需求明确的默认或代表性正常路径，其他取值及其后续作为分支展开。需求未指定时，依据实际覆盖选择一致的代表路径，不虚构产品默认值。不因局部存在一段 next 就新建主骨，也不把所有正常替代路径各列为主骨。只有独立业务目标、无法合理纳入已有骨架的业务入口/链路等有明确理由时，才建立其他主骨；不强求单主骨或最长路径。没有明确主骨时 main_paths=[]，仍保留确定的边。
5. **递归组织分支。** 将派生场景挂到最直接的用例，逐条检查分支的后续、次级分叉和共同后续；分支内的 next 不要求另建 main_paths。相邻主骨用例必须有 next，不能反过来为了凑主骨制造 next。按同源出边设 order；每条输入用例都检查过，未关联时独立保留。
6. **语义复核后输出。** 按下述检查修正关系，再执行结构校验；局部证据不足时省略该边并完成其他关系。用户要求必须确定但缺关键规则时集中澄清。完全无关系或空用例集均输出 {"schema_version":"2.0","main_paths":[],"edges":[]}。

## 输出前的语义复核

- **主线是否拆碎：** 对每条短主骨、每个断开的组件检查是否遗漏了同一业务链中配置生效、业务处理、结果展示等已被用例支持的连接；若有，补边并重新选主骨。不存在连接依据时保持独立，不能为了减少主骨数量强行合并。
- **是否把并列场景串联：** 对每条 next 检查目标是否需要假设一个新的失败、反向切换或独立初始条件才能衔接。若是，不能仅凭阶段名称相邻建立后续；回到共同基础场景判断分支。特别检查异常重试、双向切换和同场景不同断言，不能视为天然顺序。
- **父节点是否选错：** 目标的条件变化能否从父场景解释？父节点是否只是关键词相近的兄弟情形？该检查应覆盖升级、默认值、权限、范围及非功能分支，不限于示例业务。
- **分支是否被重复声明为主骨：** 已能沿分支表达的替代路径及后续，不因存在 next 再建主骨；不同主骨各自的业务理由应明确。不要用重复节点或新增用例来修复图形。

## 正式输出与校验

- 只输出一个标准 JSON 对象，不含 Markdown 围栏、前言、注释或校验报告。澄清输入问题时允许自然语言。
- 顶层严格为 schema_version、main_paths、edges，顺序沿用模板。禁止输出顶层 case_ids、label、flows、links、业务节点、用例正文或坐标；main_paths 内保留 case_ids。
- 所有字段与枚举按输出协议，不用 null 代替空数组。ID 完整沿用输入，不按格式改写；新增关系 ID 不与已提供历史 ID 冲突，保留仍适用的已有 ID。
- 环境支持 Python 时运行 `python3 <本skill目录>/scripts/validate_relations.py <关系JSON路径> --cases <原始用例JSON路径>`，修正后交付。没有原始用例时校验器仅能检查结构，不能核实引用或找出独立用例；实际生成仍需原始用例。
- 校验器不判断业务关联是否成立；不得把结构校验通过当作语义正确，也不声称仅凭旧版映射就能还原用例关联图。
