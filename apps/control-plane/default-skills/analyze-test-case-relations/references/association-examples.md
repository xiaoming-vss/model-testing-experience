# 用例直接关联示例

以下是虚构例子，只说明结构，不是当前产品规则。完整 JSON 见 [example-relations.json](example-relations.json)。

假设输入有 C001—C008 八条完整用例：C001 提交任务；C002 正常处理；C003 查看正常结果；C004 处理失败后重试；C005 重试成功后查看结果；C006 重试仍失败后查看结果；C007 对已完成的正常或重试结果导出；C008 与该任务无明确业务关系的独立检查。

已确认业务支持这些场景时：

- 主骨 C001 → C002 → C003 → C007，相邻边都是 next。
- C002 → C004 是 branch；C004 → C005 是 next，表示重试成功后的后续验证。
- C004 → C006 是 branch，表示分支用例还可再次分叉。
- C005 → C007 是 next，与主线汇合到同一个导出用例。C007 不复制，也不解释为必须等待两个前序测试都成功。
- C008 不出现在关系 JSON 中；消费者仍从原始 cases 显示它。

## 判断边界

| 情形 | 处理 |
| --- | --- |
| 两条用例覆盖同一条业务流程路径 | 不足以确定关系；检查各自验证目标及实际内容 |
| B 以处理完成为前提查看结果，A 验证相应正常处理 | 业务确有先处理后展示时可 A next B；不说明 B 覆盖了处理过程或必须先执行 A |
| A 正常处理，B 检查该处理的失败重试 | 可 A branch B，不额外新增一个“处理失败”节点 |
| 标题说重试，步骤预期只查看失败记录 | 不能据标题建立重试后续关系，按实际内容保守判断 |
| 两个异常用例只是并列情形 | 从共同基础场景分叉，不把异常 A next 异常 B |
| 某性能用例测量特定功能，在需求中有对应指标 | 可作为该功能用例的补充分支；泛化长稳检查无明确对象则独立 |
| 用例内有并行操作 | 仍只保留该用例节点；本协议不描述业务并发调度 |
| 两个用例共用账号或同属模块 | 不因此连线 |
| 有边但没有明确主线 | main_paths=[]，保留有依据的 edges |
| 用户只给旧业务节点/路径映射 | 请求原始完整用例，不能唯一转换为用例图 |

生成时依据完整内容选择关系，不照搬例子的业务、数量或形状；所有边都需要内部依据，但不把依据写成 label 或新增字段。

## 完整业务链与替代路径：避免拆成短主骨

另一个独立的假设需求：管理员设置报告生成策略并保存；新策略立即被新提交的报告任务采用。需求明确默认自动发布，也可选择人工审核后发布。用户可查看相应发布结果。此例中的用例均为已存在的完整用例，不允许生成时补造。

| 示例用例 | 完整内容中的关键依据 |
| --- | --- |
| A01 保存生成策略 | 管理员修改策略并保存，断言所选配置持久化 |
| A02 新任务按新策略处理 | 保存后立即提交新任务，分别核对自动发布、人工审核两种配置生效 |
| A03 自动发布 | 前置为自动策略已生效；提交报告并核对自动发布行为 |
| A04 自动发布结果展示 | 前置为自动发布完成，核对结果内容 |
| A05 人工审核后发布 | 前置为审核策略已生效；提交报告并完成审核发布 |
| A06 审核发布结果展示 | 前置为审核发布完成，核对结果内容 |
| A07 未修改时的默认策略 | 核对未修改配置时为自动发布 |
| A08 升级保留历史策略 | 分别准备自动/审核历史值，升级后确认保留原值 |
| A09 非管理员修改策略受限 | 在非管理员角色下尝试修改策略并核对权限限制 |

正确组织：

- 主骨 A01 next A02 next A03 next A04。
- A02 branch A05，A05 next A06；A05—A06 是替代分支的后续，不另建主骨。
- A01 分别 branch A07、A08、A09。
- A02 内容与 A03/A05 存在覆盖交叠，但明确串起“配置生效—配置被业务消费”；关联不声称 A03/A05 必须在 A02 测试执行后运行。

错误组织与原因：

- 分别建立 A01—A02、A03—A04、A05—A06 三条独立主骨：漏掉配置被任务实际采用的连接。
- A07 branch A08：仅默认策略的条件无法概括保留任意历史值，选到了相似主题的兄弟场景。
- 仅因都属于报告模块就把任意其他用例接入：同模块不能替代业务依据。

若输入只有 A03/A04 与完全无业务联系的账号注销用例，应保持两部分独立；不能套用本例强求一个骨架。

## 并列条件不是后续阶段：负例复核

| 错误候选关系 | 应检查的内容与处理 |
| --- | --- |
| 解析失败重试 next 转换失败重试 next 写入失败重试 | 解析、转换、写入有正常阶段顺序，不代表三个独立失败场景先后发生。每条都以不同失败状态开始，应从有依据的处理用例分别分支；无基础用例时不补造节点 |
| 自动切到审核时在途任务不受影响 next 审核切到自动时在途任务不受影响 | 两个不同初始配置与切换方向，不是一次在途场景的后续；分别挂到对应处理场景，不串成主骨 |
| 重试采用当前配置 next 重试保持原失败位置 | 可能是同一重试行为的两个验证维度，不是天然后续。按完整内容判断补充分支或分别关联共同基础场景；不能只按标题决定层级 |
| 重试完成后结果展示 next 另一任务的失败重试 | 目标引入了独立任务与新的失败条件，无明确衔接依据时不连 |

评估生成结果时，应同时检查：有依据的跨阶段边是否缺失、并列用例是否误串、替代分支是否另列主骨、父场景是否能解释子场景。结构校验通过不能代替这些语义检查。
