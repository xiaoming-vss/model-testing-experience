# 解决方案测试用例生成

将已确认测试点展开成测试人员可执行、可判定结果的用例。关注完整业务使用与结果，不新增测试范围，不实际操作业务系统。默认交付业务级测试设计，不以“已取得环境权限、接口地址与全部测试数据，能够立即自动执行”为生成门槛。

## 上游需求理解 JSON

结构化需求仅接受 artifactType="requirement_understanding"、schemaVersion="2.0"。读取 functionalOverview、businessFlows、modules、businessRules、questions、sources 和 evidence；普通文本需求按本技能的输入说明处理，旧版结构化对象不当作普通文本解析。

先建立规则与证据索引：operation.ruleIds、流程 conditionRuleIds 指向 businessRules；事实 evidenceIds 指向 evidence，再通过 sourceId 追溯 sources。多个条件规则表示同时满足。同一规则被多个模块或流程引用仍是一条规则，引用关系本身不新增测试目标。

读取事实 value，省略 confirmationStatus 仅在事实有有效证据时表示 confirmed；example 不作为产品事实，unconfirmed/conflicting 保留缺口，not_applicable 不扩大为禁止行为。概述字符串只说明职责或路径，不单独形成已确认验收规则；可选字段省略表示未记录，不推断默认值或不适用。options.completeness 保留选项完整性语义，open 问题的影响继续有效。

确认承接必须闭环：用户已经回答的问题，要把答复写入对应事实、规则、操作或交互，补齐确认状态与来源；随后从 `questions`/`openQuestions` 删除已解决问题，并清理所有 `relatedQuestionIds`。问题列表只保留答复未覆盖的独立业务缺口。已确认的行为不能再次拆成同义或更细粒度的问题；只有原始材料明确要求的、且答复确实没有覆盖的独立清单或判定，才继续保留为待确认问题。

modules.entryPoints 提供入口，operations.steps 提供操作，interaction 提供控件、选项、触发、联动及 results 观察依据。按 ID 读取规则与来源，无需把证据表和规则全文复制到各处。当前技能仍使用自己的输出协议，不把需求理解的 evidence/evidenceIds/conditionRuleIds 加入输出结构。

展开跨阶段步骤时分别核对当前阶段完成证据与下一阶段放行条件。仅满足进入当前阶段的条件，不足以写出后续阶段成功预期；状态聚合冲突按现有阻塞处理约定处理受影响用例。避免用虚构保存、回退、提示或完成信号补齐步骤。

当 open 问题与正文 confirmed 结论不一致时，对问题质疑的部分保留阻塞，其他明确内容照常展开。可选查看不写成业务推进必做步骤；重试的恢复目标须有依据，空后继不等于流程成功结束。

## 输入协议

接受以下三部分，允许以消息正文、文件或分次提供，不要求增加外层包装字段：

1. **需求**：完整 2.0 需求理解 JSON 或普通文本需求，包含目的、入口、使用分支、完整流程及待确认信息。
2. **需求分析**：JSON 对象，包含 `functionalOverview`、`scenarioFactors`、`businessRules`、`scenarioBreakdown`、`openQuestions`。
3. **测试点**：JSON 对象，路径为 `categories[]`，每项含 `model` 和 `data[]`；data 每项含 `test_model` 和 `test_points[]`；每个测试点含 `case_name`。

识别粘贴时产生的转义和排版差异，不将转义符作为业务名称的一部分。读取附件的实际内容后再使用，不仅依靠文件名。输入中的格式示例只规定结构，不自动成为业务依据。

## 业务依据与版本

- 原始需求与历次已确认业务补充共同构成依据，以最新明确确认及用户指定的来源优先级为准。采用用户提供的最新版分析，不因补充未回写原始需求或缺少完整历史对话就丢弃。
- 测试点决定要验证的目标，需求与分析决定如何执行及预期；测试点名称不单独证明其中未确认的行为。
- 不把格式优化、示例内容或上游推导当成业务确认；也不把明确补充退回为未知。
- 核对规则组合是否实际冲突，不因 openQuestions 为空或可生成标记为 true 就忽略冲突。
- 保持具体断言的对象范围，不把特定对象规则推广到其所属类型，不自行等同或分离业务术语。

## 展开单位与字段映射

- 按输入模块、维度、测试点的顺序展开。每个测试点对应一条用例，不擅自新增、删除、合并、拆分或重新命名已确认测试点。
- `case_module` 默认直接取所属 `model`，不另造子模块，也不拼入步骤或场景名称。
- `case_title` 默认原样取 `case_name`，不自行添加标签。用户明确要求标题前缀时才应用其格式，保留原验证目标。
- `case_type` 必须使用以下类型名称之一：功能测试、性能测试、配置相关、安装部署、安全测试、接口测试、单元测试、其他、异常测试、兼容性测试、升级测试、资料测试、可靠性测试、易用性/体验测试、规格一致性测试、长稳测试、可维/可服测试。
- 按当前测试点的实际验证目标选类型，每条只选一个。类型列表仅用于分类，不授权增加对应场景或改变解决方案测试范围。用户明确提供其他平台类型规范时按其规范执行。

| 输入测试维度 | 默认 case_type | 目标明确时的细分选择 |
| --- | --- | --- |
| 功能场景 | 功能测试 | 配置行为选配置相关；安装部署行为选安装部署 |
| 异常/容错场景 | 异常测试 | 可靠性保障目标可选可靠性测试 |
| 用户体验场景 | 易用性/体验测试 | 按当前目标填写 |
| 兼容性场景 | 兼容性测试 | 版本升级行为选升级测试 |
| 权限与渠道场景 | 安全测试 | 仅验证渠道业务支持、不涉及访问控制时选功能测试 |
| 数据与一致性场景 | 功能测试 | 明确验证规格符合性时选规格一致性测试 |
| 边界场景 | 功能测试 | 无效输入或异常处理目标选异常测试 |
| 时序与并发场景 | 功能测试 | 以容错、可靠性或性能为目标时分别选异常测试、可靠性测试或性能测试 |
| 性能场景 | 性能测试 | 指标验收与基线测量均按性能测试归类 |
| 长稳场景 | 长稳测试 | 持续负载、资源趋势及长期业务正确性 |

未列出的输入维度按实际目标从允许列表选择；确实不能归类时使用其他，不直接输出未经允许的类型名称。不得将类型值与优先级值颠倒。

- `priority` 必须是 `"1"`、`"2"`、`"3"`、`"4"` 之一，不能使用数字类型。根据失败的业务影响分配，不仅按测试类型、场景频率或步骤数量判断。用户已指定等级时沿用。

| priority | 判断标准 |
| --- | --- |
| "1" | 支撑核心业务流程，缺失或故障直接导致业务中断或系统无法使用，必须优先实现和验证 |
| "2" | 支撑非核心但重要的业务流程，不阻断核心业务，但严重影响体验或业务完整性 |
| "3" | 支撑非核心、非高频需求，故障仅影响局部体验，对整体业务和多数用户无显著影响 |
| "4" | 支撑个性化、极低频的特殊需求，影响有限，可延后验证 |

优先级是测试设计判断，不是新业务规则。低频但高影响的场景不能仅因低频降为 4；没有明确影响依据时默认 2，不编造风险结论。

- `precondition`、`test_steps`、`expected_results` 均为字符串数组，各自从 `1. ` 连续编号。无前置条件时为 []。
- 测试数据放入前置条件或相关步骤，不新增数据字段。必要的环境恢复动作可作为末尾步骤并配对结果，不新增后置处理字段。

以上为未另行指定时的填写默认值；用户的字段内容要求可覆盖默认值，但不改变固定 JSON key。

## 生成前可展开性检查

先按标题对应有效规则与关联问题，区分以下三类。readyForTestPointGeneration 和历史阻塞结论都只是线索，须重新判断缺口是否影响本条预期。

| 缺口类型 | 判断 | 处理 |
| --- | --- | --- |
| 业务预期不确定 | 不知道允许/拒绝、计算公式、边界含义、完成或放行条件，且当前目标必须依赖该未知结论 | 只澄清受影响目标，不能猜测业务答案 |
| 执行准备未落实 | 预期明确；尚无具体接口地址、账号、查询工具、日志位置、数据清单、故障模拟配置或测试环境 | 正常编写业务级用例；在 precondition 中明确执行前需准备的资源、观察字段与能力。未准备不等于需求缺失 |
| 普通测试设计 | 可以选用有效测试数据、既有状态、已提供页面或工具类别完成观察 | 直接展开，不索取无关底层证明 |

- 操作路径按业务对象和动作表达，如“向目标 data 提交语义核验请求”；不猜实际 URL、HTTP 方法、表名或按钮标签。可将实际接口与字段映射作为执行前绑定事项，写出本次对象、输入条件和应观察的响应/状态，不能仅写“按接口文档测试”。
- 后台或资源目标可要求测试环境提供观察能力，如按 data/管线/片段记录任务启动、执行次数或读取产物关联；在步骤中明确前后快照、对象集合和比较方法。不要求 PRD 提供日志查询命令，但不宣称某日志、字段或查询工具已经存在。
- 证据与标题相称。界面保存回读、选择联动和筛选可使用输入记录及既有页面；独立依据指不由本次待测结果倒推答案，不要求另一个系统或数据库。需要证明真实任务未启动时仍检查任务活动证据，不以页面没变化替代；观察渠道待绑定归执行准备。
- 预置数据、已知版本清单、正反账号、失败对象及可恢复/持续故障可作为测试资源。写明应具备的属性及使用时的核实方法，不必从上传、升级一路重新构造到本条起点。只有本条正在验证该构造过程时才从过程之前开始。
- 上游条件不明不自动传递为所有下游目标阻塞。例如“核验完成”的动作未知，确实影响核验准入规则；仅验证已经进入切片阶段后的展示或迁移，可从可核实的切片中对象开始。不能预设本条需要证明的终态。
- 精确业务判据不能伪装成环境参数：未知聚合公式不能写成“准备正确公式后按公式验证”；若仅检查显示范围、字段关联或不同对象不串用，则不要求无关计算公式。按实际目标局部处理。
- 执行准备未满足时，执行人员应记录未就绪而非测试通过；这不妨碍生成条件完整、观察和预期明确的用例。具体示例见 [references/evidence-and-readiness.md](references/evidence-and-readiness.md)。

## 性能与长稳用例展开

- 只展开已确认测试点，不因支持性能/长稳类型自行增补范围。先识别目标为指标验收还是基线测量，保留输入名称；测量型名称无需改成“验证”。
- 涉及上述目标时读取 [references/performance-and-endurance.md](references/performance-and-endurance.md)。通过现有前置条件、步骤和预期说明环境、负载、持续时间、采样方式、证据及结束与恢复安排，不增加字段。
- 指标验收缺少阈值或判断口径时按关键缺口处理；基线测量没有产品阈值不阻塞生成，但仍须有可执行的测量条件和证据来源。基线的 expected_results 描述应得到的数据、趋势或对比证据，不预填数值，不把完成测量写成性能达标。
- 可在已知测试资源与范围内选择合理测试数据，并标明是本次测试条件；负载、周期或监控方式尚未配置时列为执行前实验准备；只有业务验收目标本身不能确定时才集中澄清，不自动写死 24/72 小时、峰值并发或安全停止阈值。本 skill 只生成用例，不执行负载。

## 用例展开流程

按以下顺序展开，在内部核对后才写入最终 JSON。

### 1. 明确本条用例要证明什么

- 将测试点匹配到有效规则，确定目标是入口存在、操作受理、过程执行、执行完成还是结果变化，步骤和预期必须验证到该目标所在阶段。
- 保持已确认目标和范围，不把受理成功等同业务完成，不在入口查看后断言操作能力。
- 不擅自强化规则：执行起点不等于唯一执行范围，支持执行不等于保证成功；“仅”“全部”“必定”等限定必须有对应依据。

### 2. 选定前置状态和测试数据

- 需要登录时，前置条件明确已登录及角色，或者步骤中执行登录，不能只有账号准备却直接进入受限页面。登录本身为测试动作时不要预先要求登录成功。
- 指定本次采用的配置、对象状态及数据，不使用未选定的“某状态”“任一环节”或互斥选项代替执行方案。
- 一个测试点覆盖多个取值时，在同一用例明确数据组、每组初始状态、重复执行顺序及对应结果；不同组使用独立对象或恢复初始环境，不拆改输入测试点。等价数据组可共用参数化步骤：在前置条件列全取值与各组对照规则，步骤明确每轮依次设置、触发、读取、比较和切换，预期使用当前组取值。无需为每个枚举复制整套相同步骤，也不能仅写“同上”而省略每轮操作与判定。
- 已有满足条件的记录可作为执行起点，无需重复构造故障；准备中写明需具备的状态及核实方式，可要求执行前绑定已有页面、测试夹具或观察来源，不能只声明“已准备符合要求的数据”。这只免除构造步骤，不免除状态核实；但不能把本次验证结论预设为前置条件，也不能用“已按规范正确配置/产出”绕过验证。动态状态须在执行中即时确认。验证状态迁移本身时，从迁移前开始执行；验证迁移后已有能力时才可使用迁移后的记录。
- 用业务名称说明测试对象及关系，例如“当前记录的三个保留片段”“同一记录旧管线的片段”“另一条采集记录的片段”；执行时记录实际标识，确保操作、观察和结果对应同一对象。正式用例不携带生成批次、分组编号或审阅编号。
- 数据叙述优先使用用途、状态或来源明确的名称，例如“待修改检查项”“保存前的起止帧”“包内产物清单”。只有确实需要区分多个同类对象时才使用少量就地解释的简称；能用业务名称直接说清时不再另设字母代号。保留需求中的真实字段名、产品术语、输入值与有意义的步骤编号，不把“去代号”理解为删掉必要标识和数值。
- 改写后通读整句，说明谁属于谁、操作哪个对象、和什么比较；避免机械替换形成重复名词或用“该对象”“相关数据”抹平不同对象。对象已明确且指向唯一时，后文可自然写“该记录”“待修改项”或“当前管线”，无需每句重复全部限定。业务称谓要保留对象的实际层级和状态，区分输入范围、已生成产物与执行任务。保留必要的数量、正反对照、完整集合和观察时机，删除没有用于本条判定的内部备注。
- 反向用例排除无效凭据、环境故障等无关失败因素；只改变与目标相关的条件，对照沿用可用环境，不扩展新的测试范围。
- 每条用例只保留本条步骤或判定实际使用的准备条件，不能把通用后台观测、接口权限、故障工具清单套给普通页面编辑或显示用例；未被使用的资源应删除。本条用到的对象、清单与取值须在该条内说明来源和含义，正反分支复用后检查是否残留未定义对象。
- 每条用例自行具备执行条件，不默认前一条用例已完成准备。代表性数量、时长是本用例数据，不是产品限制，有限样本不能证明无限范围。

- 已有合法值或可辨识的测试素材可以作为本次数据：编辑能力可使用已确认有效的另一组值，不必先穷尽所有边界规则；筛选可记录筛选前已有页面的对象及字段作为对照，前提是该来源覆盖本次检查范围且不使用本次筛选结果自证。只有无法确定任何有效输入或标题专门验证精确边界时，才因对应规范缺失阻塞。准备资源不能替代缺失的业务判据：例如“审核完成”的形成条件未知时，不能仅声明已有已审核数据便当作已核实。
- 数据准备应明确本次使用的类别、状态、数量及判定所需字段；仅在数量影响目标时规定最小数量。需要识别具体记录时，要求执行人员记录实际标识，不编造真实 ID。
- 目标需要区分命中与排除对象时，准备正反向对照数据，并在后续核对中实际使用；不要求所有一致性或展示用例都准备反向数据。
- 验证结果集合时，先明确本次完整目标集合及其已知来源；涉及“全部完成”的准入或计数，读取该集合的全部相关记录/页并核对标识，不能仅抽取两条就断言全体完成。从独立预期清单逐项查找实际对象，再反向检查实际集合的多余项；仅遍历已生成结果不能发现整项未产出。核对记录标识与关键业务字段，检查遗漏、混入及要求的重复性约束，不能仅凭数量相等判定通过。用于比对的预期集合须来自已知测试数据或独立依据，不能直接把待测查询结果当作正确基准。

### 3. 编排可达步骤

- 按执行阶段展开步骤，让测试人员可以逐步操作、逐步判定。完整跨阶段流程也逐段写明触发、完成观察及后继准入，不以一条列举全部阶段的长句代替实际执行序列。页面进入与初始状态确认、条件设置与提交、结果读取与记录、结果比对应根据实际流程分别编排；不能把多个阶段压缩成“选择条件后查看并核对结果”。
- 每步一个主要操作或观察动作，必要导航、条件设置与提交可以合并；涉及多条记录的结果读取、记录与清单比对应充分展开，不把全部检查压入一个长步骤。后续同类检查可合并明确的读取与比对动作，但仍须写出字段、范围和比对依据，不能只写“同上”或“查看结果”。所有步骤都能从前一步的预期状态继续执行。
- 每个步骤必须包含明确的操作对象、操作动作和必要的输入值、选择值或观察范围。不能只写“查看结果”“选择条件”“确认正确”或“检查是否符合预期”。
- 记录动作应说明字段及后续用途；准备性记录可并入前置条件或相关操作，没有判定或留证用途的记录应省略。
- 验证没有启动、没有重复执行等否定结果时，明确观察到本次请求处理及相应调度评估完成的界点，再比较任务活动；不能仅立即读取一次就排除延迟启动。隔离旧事件影响时控制并核实新流程的自然推进，或按事件因果归属比较，不能要求正常推进中的状态绝对不变。
- 并发请求不等于同时执行；按实际配额与调度条件准备可达场景。容量为1时允许请求同时竞争而执行串行，不要求违背配额的执行重叠。
- 流程按预期拒绝或终止后，不再安排依赖该流程成功的动作。拦截后的观察可写入同一步；不能在预期中写“用例结束”却保留不可达操作。
- 输入未明确故障构造工具时，不虚构注入方式。若标题要求并发、重复回调、旧任务迟到或未加载资源，写清测试环境须提供的可控触发/观察能力、事件身份和先后关系，以及实际确认动作；具体工具与命令可在执行前绑定。不得只准备“存在并发回调”或用页面正常代替事件确已发生。
- 前置说明具备故障、调度或事件控制能力，不等于已实际启用控制；需要暂停、注入、释放或恢复时，在步骤中执行并核实。保存/修改目标准备旧值和不同的新值，实际修改与保存放在步骤中，不提前完成本次写入后再用同值重存证明持久化。
- 观察短暂状态时明确采用过程事件记录或受控观察窗口，不假定读取当前页面时仍停在目标状态；错过窗口不能反推通过。
- 时序用例采用“确认目标阶段→立即干预→观察同一对象”的顺序；目标阶段已结束时重新准备符合条件的对象，不把错过时机的执行判为通过。
- 结果涉及多条记录或多组数据时，写明检查范围、记录字段、比对清单及重复执行方式，不让执行人员自行补出操作过程。当前测试点覆盖多个条件取值时，明确各轮的设置、查询与检查；已完成的静态准备无需重复，动态状态需即时复核。

#### 查询、筛选、分页与排序场景

- 查询、筛选类用例生成前必须读取 [references/step-detail-example.md](references/step-detail-example.md)，以其中完整示例的展开粒度为参照，不照搬业务选项，不强制固定步骤数量。
- 查询与筛选用例须交代对照数据、明确的条件取值、查询触发动作、结果范围及核对依据。准备信息可放入前置条件；步骤按“初始状态 → 设置条件并查询 → 读取和记录结果 → 比对 → 切换条件并再次检查”的实际阶段展开，不以一条“选择条件、刷新、查看结果”代替查询后的具体检查过程。
- 说明其他条件的初始取值或确认其不影响本次判断；切换取值时写明覆盖原条件，只有实际需要时才清除或重置，不假设产品提供重置按钮。
- 核对命中与排除结果，并按前述集合规则检查完整性。若实际结果跨页且目标要求完整集合，则检查相关页；不为单页筛选强行增加分页测试。分页测试本身须写明覆盖页和数据范围。
- 排序测试须依据已知规则指定字段、方向及顺序核对方式，不自行增加排序选项或同值记录的次序要求。

### 4. 将预期放到实际观察步骤

- test_steps 与 expected_results 等长、同号对应。每个业务判断所在步骤必须含对应观察或检查动作，不能在提交时提前断言随后才观察到的结果。
- 预期写清具体观察对象和应满足的业务条件，不以“正常”“正确”“查询成功”等概括词替代判定。涉及筛选、排除或集合完整性时，再明确哪些记录应出现、哪些不得出现。操作受理、执行过程和最终结果按目标检查，不强行全部加入每条用例。
- 比对前核对字段语义、来源和显示精度，不能以创建时间代替上传时间，或用已取整的分项显示值精确相加来断言总值。可选不产生取整歧义的已知测试数据；仅在目标要求精确换算且依据缺失时澄清。前一状态的值不自动构成后一状态必须保留该值的规则。
- 只使用已知观察渠道能提供的信息。当前状态不等于完整历史，结果字段不等于执行日志，页面回显不等于业务生效。
- 需要证明顺序或跳过环节时安排过程观察；仅在结束后查看当前状态不能证明历史过程。不要声称观察渠道提供未明确的历史记录或瞬态事件。
- 分开过程不变量和稳定后的最终结果：并发处理期间核对不提前放行、不重复计数等约束；所有目标事件处理完成后再核对最终集合与数量，不能把最终数值套到每次中间采样。
- 同一条预期不包含本步未触发或未检查的能力。复用规则原意，不把后续处理范围自行限定或扩大。
- 目标为恢复后完成时，准备已解除已知故障且可正常执行的条件；目标仅为重新发起时，不追加最终成功要求。

### 5. 恢复环境并复核目标覆盖

- 改变共享配置或测试环境时，必要时记录原状态并安排末尾恢复动作和对应预期，恢复步骤不作为新增业务验收目标。不清理本次测试仍需保留的证据。
- 标题覆盖多个资源类型、渠道或流程阶段时，每项须有实际操作及观察，或明确的参数化轮次；仅在前置清单中出现不等于已经验证。
- 核对核心观察确实覆盖标题，前置条件没有预设结论，各数据组与用例之间没有隐含依赖。
- 对每个核心断言反问：如果目标能力失效，现有检查是否仍可能通过？若可能，应补足观察与判定；若缺的是观察工具，写明执行前所需能力；若缺的是业务判据才澄清。集合验证尤其要能发现“数量相同但记录错误”。具体反例见 [references/evidence-and-readiness.md](references/evidence-and-readiness.md)。

## 信息不足时的处理

- 仅当当前标题的业务预期或不可替代的判定规则无法确定，返回 `CLARIFICATION_REQUIRED:`，集中说明受影响原标题、问题及为什么现有规则不能决定答案。合并同源问题，不把多个受影响用例计成多个需求问题。
- 接口地址、物理字段映射、日志位置、账号权限、测试数据及故障控制工具未提供，通常属于执行准备；将所需能力和对象/字段/范围写入 precondition，具体核对动作写入步骤。不得因此要求需求方补全技术运行手册，也不得编造实现。
- 保持固定七字段正式协议；执行准备是前置条件，不是隐藏的未知业务答案。不将真实业务疑问或“待确认后再定预期”塞进正式用例。
- 不擅自改名、降级或删除已确认测试点。存在真正业务未知时，当前批次按澄清协议处理，不返回假装完整的部分 cases。用户明确选择了可展开测试点批次时，仅对该批次承担完整映射责任，其他目标的缺口不阻塞本批。
- 本地评估中的分类/准备清单是辅助产物，不加入正式 JSON。没有测试点输入时输出 {"cases":[]}。

## 固定输出协议

生成前必须读取 [assets/output-template.json](assets/output-template.json)。模板只展示结构，不是业务示例，不复制占位值。

- 正式生成阶段的最终响应仅包含一个标准 JSON 对象，不输出 Markdown 围栏、注释、前言、结语或其他文字。
- 顶层只有 `cases`，类型为数组。
- 每条用例恰好包含七个 key，按模板顺序输出：`case_module`、`case_title`、`case_type`、`priority`、`precondition`、`test_steps`、`expected_results`。
- 字段名、层级和集合固定，不增删或另加包装。前四个字段为字符串，后三个字段为字符串数组；priority 为字符串 "1"、"2"、"3" 或 "4"。内容使用中文，必要产品术语保留原文。
- 数据与必要恢复动作按前述规则放入既有字段，不另加测试数据、来源或后置处理字段；澄清问题不写入正式用例。

## 输出前验收

正式生成前逐条检查：能用现有依据修正的重写；业务预期或必需判据缺失的返回澄清阶段；仅执行资源未落实的补明前置准备，不用反复改写掩盖缺口。正式 JSON 不追加检查报告。

- 映射：数量、顺序、模块与标题对应输入，未扩展范围或强化业务规则。
- 准备：数据与状态明确，未预设结论，无跨用例隐含依赖；需要时具备有效对照。
- 可读性：执行人员无需记忆额外代号表即可理解对象、来源与比较关系；没有生成批次编号、无意义代号或机械替换造成的病句，必要业务术语、具体数据和判定力度仍保留。
- 执行：每步对象、动作及必要取值明确，路径可达，动态条件及时复核，必要恢复已安排。
- 判定：对应步骤实际观察了预期所述对象，字段、范围和比对依据明确，证据足以发现目标失效。
- 展开粒度：是否将设置条件、查询、读取结果和比对压在一个笼统步骤或长句里？若执行人员仍需自行拆解阶段，必须重写为可逐步执行的步骤。
- 操作完整性：是否仍需执行人员自行补出查看哪些页或记录、记录哪些字段、与哪份清单怎样比对？缺少的执行信息必须补齐。
- 断言落地：预期中的“无遗漏”“无混入”“一致”等判断，是否在对应步骤中有具体的检查过程？只有预期结论而没有检查动作时，必须展开步骤后再输出。
- 格式：JSON 可解析，字段集合与类型符合模板；步骤与预期非空、等长，各数组连续编号；类型和优先级合法，无额外文字。
