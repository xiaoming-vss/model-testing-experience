# 解决方案测试点生成

以实际业务使用为中心，回答“什么对象在什么环境、状态和渠道下执行什么操作，业务结果应是什么”。输出只有测试点名称，按业务模块和测试维度组织，不生成步骤、测试数据、优先级或执行脚本。

## 上游需求理解 JSON

结构化需求仅接受 artifactType="requirement_understanding"、schemaVersion="2.0"。读取 functionalOverview、businessFlows、modules、businessRules、questions、sources 和 evidence；普通文本需求按本技能的输入说明处理，旧版结构化对象不当作普通文本解析。

先建立规则与证据索引：operation.ruleIds、流程 conditionRuleIds 指向 businessRules；事实 evidenceIds 指向 evidence，再通过 sourceId 追溯 sources。多个条件规则表示同时满足。同一规则被多个模块或流程引用仍是一条规则，引用关系本身不新增测试目标。

读取事实 value，省略 confirmationStatus 仅在事实有有效证据时表示 confirmed；example 不作为产品事实，unconfirmed/conflicting 保留缺口，not_applicable 不扩大为禁止行为。概述字符串只说明职责或路径，不单独形成已确认验收规则；可选字段省略表示未记录，不推断默认值或不适用。options.completeness 保留选项完整性语义，open 问题的影响继续有效。

modules.entryPoints 提供入口，operations.steps 提供操作，interaction 提供控件、选项、触发、联动及 results 观察依据。按 ID 读取规则与来源，无需把证据表和规则全文复制到各处。当前技能仍使用自己的输出协议，不把需求理解的 evidence/evidenceIds/conditionRuleIds 加入输出结构。

流程类目标须核对当前阶段完成和下一阶段准入是否分别有依据。状态聚合规则存在重叠或优先级不明时，暂缓受影响的确定性预期；保留其他明确目标。同一条件、动作和结果被多个规则重复描述时合并测试点，不按规则条数扩增。

上游问题若明确质疑某条事实，按争议范围判断可生成目标，不因事实缺省 confirmed 而忽略问题，也不整条封锁关联规则。查看、预览操作仅在有明确业务依赖时作为后续处理的前提；恢复路径不明时不生成宣称已能返回主流程的确定性目标。

## 输入

使用本次任务提供的两类材料：

1. 原始需求：通常是功能理解记录，包含目的、入口、使用分支、完整流程及待确认信息。
2. 需求分析结果：包含 `functionalOverview`、`scenarioFactors`、`businessRules`、`scenarioBreakdown`、`openQuestions` 五个字段。

原始需求用于核对业务含义和事实依据，分析结果用于拆分条件、规则、验证目标及识别缺口。遵循材料中明确指定的来源优先级和用户最新确认。不要将分析中的推测提升为需求事实；无法消解的矛盾不生成带有确定预期的测试点。

输入不完整时，仅使用已提供材料中足够明确的内容；不要从其他任务或示例补需求。如果完全没有可确定的测试点，返回 `{"categories":[]}`。输出协议不允许额外提问字段或解释文字，不代表需求完整或没有测试需求。

## 阶段职责与下游使用

- 同时阅读原始需求与最新版需求分析：原文用于核对业务含义、适用范围及分析遗漏，分析用于组织规则、因素、条件和缺口。不是只改写 scenarioBreakdown，也不是脱离分析自由补充需求。
- 本阶段负责场景设计、覆盖、命名与去重，最终仍只输出固定 categories JSON 中的名称。不输出操作步骤、证据清单、问题字段或额外交接材料。
- 可生成测试点不等于完整用例可执行。目标明确但执行路径或判断依据待确认时保留名称，不擅自补齐细节；决定业务预期的规则未知时按已有暂缓规则处理。
- 下游须结合原始需求、最新版需求分析和已确认测试点展开；名称不能替代需求依据或消除分析中的 openQuestions。内部发现的缺口不视为用户已确认，也不通过改写名称掩盖冲突。
- 用户已经回答的问题必须以回写后的事实或规则为准；不要把同一已确认行为重新生成 openQuestion，也不要只依赖 relatedQuestionIds 表示已承接。仅保留答复未覆盖的独立业务缺口。

## 候选测试点的依据核对

- 有效依据包括原始需求和历次需求分析中已确认的业务补充，以最新确认内容为准；原始文档未更新不使补充失效。
- 用户提供最新版需求分析作为输入时，采用其中明确记录的业务确认，不要求用户重复提供全部历史对话，也不因新增内容未出现在原始需求中就排除。
- 区分已确认的业务补充、分析推导和待确认事项；对格式、名称或分类的优化不视为业务规则补充。
- 每个验收候选名称的条件、操作和预期都应对应有效规则；基线测量须有明确评估范围及真实被测业务依据。明确程度和可生成标记辅助判断，但不能消除输入中实际存在的冲突或待确认内容。
- 存在无法消解的冲突时，仅暂缓受影响目标；保留其余已明确内容，不退回初始需求而丢弃有效补充。
- 不因 openQuestions 为空就忽略正文中的不确定描述，也不引入材料之外的操作或预期。

## 场景推导边界

- 允许从明确规则推导未逐条列举的等价类、临界条件、条件组合和状态迁移；不新增业务事实不等于只复述输入已有场景。
- 推导保持规则适用范围。明确“仅允许 1～99 的整数”可推导 0、100、小数不合法；不能自行规定提示文案、颜色、持续时间或拦截位置。
- 未说明操作不等于禁止操作；缺少异常规则时不规定重试次数、回滚方式或恢复结果。预期不确定的候选记为内部缺口，留待需求分析或后续确认，不混入确定测试点。
- 具体数据和步骤留到用例展开阶段；白盒覆盖、变异测试和探索性测试执行不属于本 skill。探索得到的已确认规则与缺陷可作为后续输入。

## 验证目标选择：业务行为优先

- 默认验证业务行为、规则、状态或数据结果。按钮、菜单、页面层级和点击路径通常是执行位置，不因材料列出某操作就生成“提供某入口”的测试点。
- 先判断入口是否有独立验收价值，再决定是否拆分。只有材料明确规定入口的显示、隐藏、位置、可用状态或多入口可达性，且该要求不能由现有业务目标充分覆盖时，才单独保留。明确要求测试入口布局或可发现性时也按该范围生成。
- 业务功能验证需经过某入口，且没有额外界面约束时，不追加入口存在性检查；多条路径没有独立适配或可达性要求时，不按页面菜单复制同一业务目标。存在明确差异时保留必要路径条件。
- 入口不显示不等于业务操作被禁止，按钮可见不等于功能执行成功；不能相互替换预期。分析中的界面断言也须核对其实际依据：“不允许操作”只证明不能生效，不自动证明入口必须不存在；“不支持部分范围处理”不自动生成“没有选择入口”。只有真实依据明确控件表现时才保留对应界面目标。置灰、隐藏和业务拒绝分别有明确依据及独立验收价值时可以分别保留。
- 有明确业务行为时直接命名该行为及结果，不把“提供删除入口”机械改成“删除成功”。如果材料只确认入口要求而未确认业务结果，保留有依据的入口目标，并将行为预期缺口留待确认。
- 此规则同样适用于输入分析中已有的入口 verificationObjective；分析条目不是必须照抄的测试点。按需参考 [references/scenario-design-examples.md](references/scenario-design-examples.md) 的入口取舍示例。

## 覆盖责任与需求分析复核

- 本阶段承担测试场景设计责任，不只是整理名称。scenarioBreakdown 是候选种子，不是覆盖上限；同时从原始需求、businessRules 的各项结果与禁止行为、scenarioFactors 的有效取值推导目标。一个规则已有一条测试点不代表该规则完整覆盖。
- 内部拆出每条规则的独立要求，分别记录适用条件、触发、业务结果或关系、来源与确定程度。范围排除、背景说明和实现分工不是自动生成的测试目标；明确的系统能力与交互契约不能因属于后台而被过滤。
- 核对分析是否改变原文含义：不得把“本期不考虑/不要求”改成“必须不显示/禁止”，不得把“已发起”替换为“已完成”，不得扩大适用对象或把分析推导当成已确认补充。发现偏差时按输入来源优先级恢复有依据的含义，无法确定的部分内部暂缓。
- 待确认按独立要求局部生效，不按整条规则或 relatedQuestionIds 连带阻塞。完整取值集合未知不阻塞已确认取值，具体文案未知不阻塞明确的提示与拒绝行为，检查工具未知不阻塞明确的能力目标；计算口径、触发条件或预期本身未知时暂缓对应细化目标。

## 业务模块划分

- model 表示产品中的业务模块，不自动等于本次需求标题。优先采用用户明确指定或认可的模块划分与名称；其次根据原始需求及最新版分析中的业务职责、对象和入口识别现有产品模块。没有独立模块依据时才使用一个概括业务能力的模块。
- 区分现有产品模块与同一模块内的入口。不同模块有独立职责，即使共同服务一个需求，也可分别生成 categories；同一模块内部的按钮、菜单、渠道、操作分支和流程阶段不自动拆成模块。不能仅凭页面数量拆模块，也不能仅因需求只有一个标题就合成一个模块。
- 在命名前内部建立“模块—职责—适用规则”的对应关系；结合原文核对分析是否将不同模块的独立要求打包。测试点按主要验证目标归属，而非按最初进入的页面或名称关键词归属。
- 跨模块流程按被验证的行为或结果归属：发起动作归发起模块，任务详情归任务管理模块，结果展示归展示模块，授权生效归授权管理模块。不可拆分的跨模块关系只保留一个目标，归承担核心验收职责的模块，并在名称中保留必要的跨模块条件。
- 同名弹窗或相似操作不证明不同模块共用规则或实现。有明确独立适用条件、数据范围或风险的流程分别覆盖；有依据的共用规则可复用，不按所有页面重复复制。
- 共用运行能力按职责归承担该能力的模块；不要强行在每个发起模块重复生成。只有需求明确存在独立后台业务模块时，才另设模块，不凭实现层次创造模块。
- 同模块跨维度去重，跨模块检查是否为同一目标的重复副本；条件或职责不同且有独立验收价值的目标不因措辞相似合并。名称保留用户术语，不擅自改名或合并已确认模块。
- 涉及多模块或跨模块流程时读取 [references/module-assignment.md](references/module-assignment.md)。该示例用于解释归属方法，不固定其他需求的模块数量或名称。

## 测试维度

在每个模块的 `data` 中按适用维度归类，`test_model` 使用下列名称。只输出包含有效测试点的维度，不为凑齐分类生成需求外测试点。

| test_model | 关注内容 |
| --- | --- |
| 功能场景 | 业务操作、业务规则、正常分支、完整链路和状态变化 |
| 异常/容错场景 | 已明确的失败、离线、异常中断、重试及恢复 |
| 用户体验场景 | 有依据的提示、反馈、防误操作与操作便利性 |
| 兼容性场景 | 明确支持的环境、版本、设备适配及升级行为 |
| 权限与渠道场景 | 角色权限、端及操作渠道限制 |
| 数据与一致性场景 | 独立的数据变更、关联关系和跨端结果一致性 |
| 边界场景 | 明确的输入、数量、范围及临界值 |
| 时序与并发场景 | 执行中切换、重复操作、事件交错及并发处理 |
| 性能场景 | 适用负载下的响应时间、吞吐、耗时、容量与资源竞争；区分指标验收和基线测量 |
| 长稳场景 | 持续负载或反复操作下的资源趋势、积压、性能衰减及业务正确性 |
| 安全场景 | 有依据的认证、攻击防护、敏感数据保护及安全约束 |

性能与长稳按下述专门规则生成；安全及无障碍仍须有适用规则或明确引用且可核实的质量标准，不扩展为无依据的通用清单。访问资格与角色授权仍归权限与渠道，恢复行为归异常/容错，无障碍交互归用户体验。

一个测试点只归入一个主要维度，不在多处重复。正常业务在允许条件下完成，归入功能场景；验证访问资格或渠道限制，归入权限与渠道场景，不能仅因名称出现渠道就归入权限分类。按业务规则差异划分功能场景，按适用条件下的能力适配关系划分兼容性场景。核心业务结果可归功能场景，不必为了数据分类拆出重复点。依据验证目标决定类别，不仅依据关键词。

## 性能与长稳目标

- 根据当前业务的批量、并发、排队、持续运行或循环操作特征判断适用性，不要求每个模块都生成这两个维度。有指标生成验收目标；有明确评估请求但无阈值生成基线测量目标；只有风险线索时内部记录缺口，交由需求分析或后续确认，不自动增加已确认质量要求。
- 性能关注负载变化下的处理能力；长稳关注持续负载下随时间发生的变化。时序并发规则验证仍归时序与并发，不因有多个用户就算性能；短时峰值不能替代持续运行，也不把同一目标在两处重复。
- 涉及性能或长稳时读取 [references/performance-and-endurance.md](references/performance-and-endurance.md)，按适用方法展开。负载、时长和指标必须区分测试条件与产品要求，不自行设置合格阈值。
- 模块前缀之后，指标验收名称以“验证”开头。明确的基线测量是命名规则的例外，在前缀之后以“测量”或“观察”开头，写明业务对象、负载关系及指标/趋势；这是测量目标，不冒充已知业务预期。现有 JSON 字段不变，不在名称后附缺口说明。

## 生成前必读：认可的输出示例

每次生成前必须读取 [references/approved-output-example.json](references/approved-output-example.json)，并读取 [assets/output-template.json](assets/output-template.json)。模板定义字段结构，示例在原认可表达基础上按当前业务行为优先规则调整，展示名称表达与拆分粒度；不是示例业务的完整覆盖清单。

- 只学习示例中的模块前缀、适当标点、名称精简、独立目标拆分、统一反馈表达、分类和去重方式。
- 示例不是当前需求来源；不得将其业务对象、操作入口、条件、规则、预期或适用范围带入当前任务。
- 不固定模块名称、测试维度、排列数量或用例数量，不要求逐字复现。
- 以当前需求及历次已确认补充为业务依据；与示例内容不同时遵循当前业务依据。
- 按本 skill 的生成流程和验收标准检查当前结果，不仅模仿示例表面措辞。

## 生成流程：先推导场景，再拆分命名，最后复核

按以下顺序处理，不直接将 scenarioBreakdown 的 verificationObjective 改写为 case_name。先确定独立要求和候选覆盖，再命名、归类与去重；模块只组织结果，不决定场景取舍。分析记录可包含多个结果，其粒度不是用例粒度。

### 1. 固定业务依据与适用范围

- 合并原始需求和已确认补充，识别可生成场景及待确认部分。可生成标记是辅助信息，不代替业务依据。
- 从原始需求和分析提取独立要求，分别识别适用对象、条件、触发、处理分支、验收结果及明确禁止行为；同一规则内可独立判断的要求分别记录，不能把整条规则视为一个覆盖单位。
- 内部为候选记录对应独立要求、必要条件、触发、验收目标及有效来源；名称、模块与维度稍后确定。此中间记录不加入最终 JSON。
- 固定格式名称、状态、默认值、范围及限制的有效依据；不因同义改写或追求简短替换业务取值。来源矛盾按优先级解决，无法解决时仅暂缓受影响目标。
- 按具体业务断言确定适用对象，不机械采用分析条目的 applicableObject 或所属分类。仅对特定对象明确的限制不能推广到整个类型，除非补充确认明确扩大了范围。
- 名称精简前后适用范围必须相同。类型规则保留类型，特定对象规则保留该对象，不通过删除括号说明或替换对象名称扩大范围。

### 2. 选择方法并推导候选场景

按规则特征选用下列方法，可组合使用，不要求全部使用。方法用于推导，test_model 用于分类，不能用分类齐全代替覆盖检查。遇到对应规则时，读取 [references/scenario-design-examples.md](references/scenario-design-examples.md) 中相关示例，学习推导边界与关系目标粒度，不引入示例业务事实。

| 规则特征 | 方法与推导要求 |
| --- | --- |
| 输入类型、类别或范围 | 划分有效和无效等价类；规则处理方式相同才视为同类。独立无效条件分别考虑，避免相互遮蔽。 |
| 数量、金额、长度或时间边界 | 检查边界及相邻区间，按单位、精度和端点包含关系确定相邻值；未知精度时不猜步长。名称表达临界关系，具体数据留到用例展开。 |
| 多条件决定结果 | 用判定表梳理可行组合与结果；复杂与、或、非关系可先用因果分析。标记互斥、依赖和不可能组合，不把不可达组合当异常场景。 |
| 生命周期、状态限制 | 梳理初始状态、事件、迁移条件和结果；覆盖合法迁移、明确禁止的迁移及规则已明确的重复事件处理。 |
| 完整业务流程 | 推导主流程、替代分支、失败、中断和恢复；保留跨环节顺序或衔接目标，不重复罗列各环节已有独立结果。 |
| 多角色、多端、多配置 | 先覆盖规则差异与高风险组合，再按需采用两两或更高阶组合；两两覆盖不能代替已知三因素以上的交互验证，不生成无差异的全排列。 |
| 异步、重试、并发 | 分析参与者、事件顺序与交错、重复触发、故障发生点及恢复后的业务约束；对应预期确定才生成，不默认幂等、补偿或最终一致性保证。 |
| 已提供历史缺陷或明确风险 | 用错误推测补充触发条件及相关变体，核对当前适用范围和预期；经验本身不能建立新产品规则。 |
| 精确答案难以枚举 | 有明确业务不变量时采用性质验证；有已确认输入变换与输出关系时采用蜕变验证；有适用基准及允许差异规则时采用差分验证。不默认新旧版本一致或某实现必然正确。 |

按规则和场景因素逐项判断哪些取值存在独立授权路径、处理分支、输入范围、输出格式或状态结果差异。每个有依据的差异形成候选；同一场景由多种方法推导时只保留一份。不可达组合排除，结果未知的分支局部暂缓，不强制穷举。风险用于选择覆盖深度，不输出优先级字段。

#### 展开深度：概括目标不能代替独立分支

存在以下规则特征时，读取 [references/scenario-design-examples.md](references/scenario-design-examples.md) 的“独立要求覆盖与局部待确认”示例。

- 独立输入约束分别覆盖：每个必填项缺失时让其他字段有效，避免只用“全部为空”验证所有必填规则。多项同时无效是否另列，由组合反馈或交互价值决定，不机械穷举。
- 独立授权路径分别覆盖：不同角色可独立获得权限时分别验证，避免使用同时具备多个身份的用户替代各角色覆盖。任务可见、记录可见和文件可访问等独立资源权限按已明确要求分别判断；不自行扩展跨租户等未确认授权规则。
- 查询能力按已明确的单条件、组合条件、刷新、分页和排序分别检查。联合匹配逻辑、默认顺序或页大小未知时不补造值；保留已明确能力目标，暂缓受影响的精细场景。
- 对重试、处理等操作，按有依据的不同结果展开，如重试成功与仍失败；每个分支保留对应预期，不用“按结果处理正确”代表所有分支。结果集合或计算规则不明确时仅暂缓该部分。
- 多流程、数据粒度、格式或配置不能仅因名称相似视为等价。分别覆盖有独立规则、转换实现、输入映射或结果差异的取值；材料证明确实等价且无独立风险时才用代表场景。共用规则可以复用，不把全部因素做笛卡尔积。
- 多条规则共同决定结果时，名称保留足以避免错误解释的约束组合；局部允许不能覆盖全局过滤。状态筛选的等值关系可参数化，而生命周期状态参与准入、重试或重复提交时分别保留有意义分支，不仅因结果相同合并。
- 同一展示结构的字段齐全性可作为一个目标；字段各自的计算、条件显示、权限或状态规则另行展开。不得按字段、动词或连接词数量机械拆分来增加条数。

#### 解决方案范围：检查业务产物与系统能力

- 对转换、导入、导出、同步、计算等功能，除任务提交、状态与文件存在外，核对输入选择、处理结果、目标格式或业务语义、产物映射与获取链路等已明确要求。创建记录或写入文件不能替代结果正确性。
- 对材料明确要求的契约对接、版本兼容、替换升级、存储隔离、日志与追踪，生成适用的能力验证目标；纯实现分工或无独立验收意义的内部调用不另列。
- 名称可保留“符合已确认的目标格式/契约”等有明确依据的能力要求，具体规范与检查手段留待用例展开；没有给出的版本、字段映射、兼容范围、日志字段或性能阈值不得自行补充。跨渠道共用业务准入不意味着共用提示载体：页面说明阻塞原因，不能自行扩展为接口必须返回相同文案或字段。背景愿景不能直接转化为确定验收标准。


### 3. 拆出独立验收目标

- 一个候选聚焦一个独立验证目标，可以是单一结果，也可以是多个对象之间不可拆分的关系或业务不变量。通过独立验收价值筛选后，不同操作的入口或可用状态目标分别表达，不因拆分规则反向补造目标。
- 区分状态迁移与迁移后的操作能力：若规则确认审核结束后进入下一阶段，应保留这一迁移目标，不能只写“已在下一阶段时发起操作”。测试点条件不能预先包含本条要验证的结果。
- 一个条件可共同适用于多个目标，但共享条件不构成合并理由；互不依赖、可独立验收的结果分别表达。跨订单竞争、账实一致或跨环节顺序等关系可涉及多个对象，不按对象数量拆散，也不借关系目标附带无关结果。
- 前置条件与触发操作不是额外验收目标。不能按动词数量、连接词或执行步骤机械拆分。
- 一条统一提示的内容是一个验收目标，内容涉及多个业务概念不要求拆分。只有明确存在分别触发的反馈时，才按触发条件拆开；不得虚构触发方式。
- 不以“整体完成”“端到端”作为合并独立结果的例外。需求明确要求验证顺序或衔接时，只验证该关系，不同时罗列各环节独立结果。
- 保留用户认可且有依据的概括性要求，不强制细化到执行步骤；但不能用概括性表达重新打包已经识别出的多个独立判断。

### 4. 覆盖初检后写短名称

- 命名前按独立要求和有价值的分支检查候选是否齐全；缺失的有依据场景先补齐。不得先以模块或名称长度压缩候选，再把精简后的集合当作覆盖基准。

- 每条 case_name 以业务模块前缀开头，格式为“【模块名称】”，紧接正文。首个前缀与所属 categories 的 model 一致；确有依据且该目标不可拆分地涉及其他业务模块时，按涉及关系追加“【其他模块名称】”，不编造模块，也不因前缀重复生成测试点。
- 前缀之后的验收目标以“验证”开头，表达必要对象、条件、操作及预期；性能与长稳的基线目标以“测量”或“观察”开头，表达测量对象与指标，不强行补产品合格结论。
- 按中文语义使用标点：条件或触发与结果之间有明显停顿时使用逗号，并列项目需要区分时使用顿号；短而通顺的名称无需强加标点，名称末尾不强制加句号。标点不能改变条件、范围或验收目标。
- 业务结果目标：删除页面、列表层级、操作列和中间点击路径，只保留会影响业务分支的条件与必要操作。
- 入口目标：仅对通过目标选择筛选的独立界面要求命名，写明必要条件及显示、隐藏、位置或可用状态，保留最短必要位置；不附加业务完成结果，也不补造入口检查。
- 删除重复类型说明、举例和过程叙述，但不能更改对象范围。名称不包含编号、来源、执行步骤或分析解释。
- 删除不增加独立含义的成功性前缀或附带结论。若操作完成与结果变化各有独立验收意义，则拆成两条，不用连接词保留在同一条。
- 无需固定字数；名称虽短但有多个目标仍不合格，名称所需术语较长不等于必须删减。

### 5. 按覆盖等价性去重

- 去重对象是相同验证目标，不是相似文字。跨模块和维度比较适用对象、条件、触发、验收结果及独立验证价值；同模块、同操作名称或同预期均不能单独证明等价。
- 不同角色的独立授权、不同流程的适用条件、不同格式的产物要求、不同状态的处理规则分别保留。仅当有效依据支持同一等价类且没有独立边界或交互价值时，才用代表场景；不能默认同名功能共用实现，也不机械按每个取值复制。
- 通用目标不能自动代表具体分支。若“功能正常”等概括名称隐去了独立条件或判断，保留具体分支；具体分支已覆盖概括要求全部含义时删除无额外价值的概括点，而非反向删除分支。
- 共用要求可在其适用范围内验证一次，但归为共用能力不等于无需验证。结果存在、结果正确、传输路径、访问资格等不同断言，不能因属于同一链路而互相替代。
- 同一展示结构的字段齐全性及不可拆分的关系可以整体保留。不得按字段、对象或动词数量机械拆分；也不得把独立结果拼成一个长名称以减少条数。
- 每次合并内部记录被合并候选、保留目标及等价依据。被合并候选的必要条件与判断必须仍能从最终名称识别，不能只存在于内部记录；无法说明完整覆盖关系时不合并。
- 去除仅作执行路径的入口描述，以及只解释结果且无独立验收要求的内部调用；不能因此删除已明确的界面约束或系统能力目标。

### 6. 原文、分析与最终结果逐项复核

- 按独立验收目标归入一个 model 和 test_model，按业务顺序组织。分类不足不是删除目标的理由；不为平衡模块数量或凑齐维度新增场景。
- 从原始需求回查每项已确认的独立要求，再从分析的规则、场景因素和场景列表交叉检查。不能只验证已有 scenarioBreakdown 被改写，也不能只按 ruleId 标记覆盖。
- 每项独立要求及有价值的条件分支必须对应最终测试点，或有明确内部处置：等价合并（指出保留目标及依据）、条件不可达、范围排除、规则冲突或预期待确认。待确认不算覆盖；“名称已概括”“属于共用能力”“模块已调整”不能单独作为排除理由。
- 对阶段链路，在内部逐条核对“上游阶段 → 直接下游”的放行条件和明确阻断条件。通用规则已规定等待、处理中、失败不得推进时，将其落实到适用的各条阶段边；状态展示、失败可重试和完成后推进的测试点都不能替代未完成时不推进的目标。与已有具体准入点合并时保留该边与阻断状态，不重复复制已覆盖目标。
- 重点回查正向能力与明确限制、独立输入条件与可行组合、不同处理结果，以及业务产物正确性、系统承接能力、异常恢复和资源访问控制。只检查页面操作不代表解决方案完整覆盖。
- 去重后再次反向核对每个被合并候选，确保具体条件与验收判断没有被更宽泛的名称吞掉。格式、状态、默认值、范围和限制与有效来源一致，不能随命名和模块归属变化。
- 缺少检查工具或具体执行路径不自动阻塞已有明确目标的名称；决定业务预期的规则未知时才暂缓对应部分。不把局部缺口扩大为整组排除，不虚构执行细节。
- 不设置最低或目标条数。验收标准是有效独立要求及分支得到覆盖，既不为精简删除有效目标，也不为增加数量复制等价场景。

## 严格输出协议

生成前读取 [assets/output-template.json](assets/output-template.json)。以模板定义的 key 和嵌套结构输出，仅替换值、增加或减少数组条目。

- 最终响应只能是一个标准 JSON 对象，无前言、结语、注释、Markdown 代码围栏或其他内容。
- 全部 key 固定，不能增加、删除、改名或翻译。顶层只有 `categories`。
- key 的大小写和下划线也必须保持原样：仅使用 `categories`、`data`、`model`、`test_model`、`test_points`、`case_name`，不得转换为 camelCase 或同义字段。
- 生成完成后先检查 JSON 语法、各层字段集合和字段类型，再返回结果；发现格式错误时在内部修正，不把校验说明追加到输出中。
- `categories` 每项仅包含 `data` 和 `model`；`data` 每项仅包含 `test_model` 和 `test_points`；`test_points` 每项仅包含 `case_name`。按模板顺序输出字段。
- `categories`、`data`、`test_points` 始终是数组；`model`、`test_model`、`case_name` 始终为非空中文字符串，必要的产品名称保留原文。
- 模板值是占位说明，必须替换，不得作为真实测试点输出。没有有效测试点的维度和模块整个省略，没有可生成内容时仅输出 `{"categories":[]}`。
- 不增加具体场景层；条件与触发事件直接体现在 `case_name` 中。规则追溯和覆盖检查在内部完成，不添加 ID、来源、待确认清单等字段。

## 效果验收标准

以下标准用于判断生成结果是否达到要求，不能仅凭 JSON 格式正确或名称字数减少就认定合格。

- 每条名称的模块前缀与归属一致，跨模块前缀有依据；条件、触发与预期较长时使用自然的标点。
- 名称直接说明验证内容，不复述需求段落或完整操作路径；业务结果测试点保留对象、必要渠道或条件和结果。
- 以业务行为及结果为主；独立入口或可用状态目标先筛选再拆分，不为每个操作自动追加入口点。统一反馈内容保留一个目标，不按反馈中的业务词汇拆分。
- 业务结果名称不叠加无独立意义的完成性表述；独立的结果变化分别成条。
- 同一约束及其业务结果不重复列出；没有独立价值的必然派生结果不追加为条目或分句。
- 精简前后业务对象和适用范围一致，已确认的补充要求得到保留。
- 保留用户认可的模块名称和概括性要求，不以进一步细化为由改变它们。
- 结果按业务模块和测试维度组织，最终 JSON 字段严格采用模板。

将上述标准与必读输出示例结合使用：参考其表达方式和粒度，业务覆盖以当前需求为准。不复制示例业务事实，不固定用例数量，也不要求逐字复现。

## 输出前检查：不通过则重写

1. 入口点是否有明确且独立的界面验收依据，还是仅复述操作路径？删除后者；保留的独立入口或状态目标再按操作拆分。检查是否误把隐藏改成禁止操作、把入口存在改成功能成功。关系目标不按参与操作数量拆分。
2. 是否将业务完成和独立结果变化写在一起？拆分独立判断，或删掉没有额外意义的结论。
3. 业务结果名称是否仍包含完整执行路径？删除路径；入口名称仅保留最短必要位置。
4. 对象名称是否与具体规则适用范围一致？检查是否误将特定对象限制推广为类型限制。
5. 是否保留了重复、必然派生且无独立价值的结果？删除冗余条目或分句，不能拼接为长句。
6. 是否误拆了统一提示，或误删了用户认可的概括性目标？还原其单一验收含义。
7. 是否保留多版确认、模块划分和有效覆盖，且没有新增业务事实？
8. 是否使用适用方法推导并复核场景，而非只改写已有目标？未生成候选是否有内部原因，且没有以分类齐全或两两组合代替风险覆盖？
9. 是否保留不可拆分的关系或业务不变量，避免按对象数量拆散目标？
10. 是否逐项覆盖规则内部的独立要求，并展开有依据的独立条件、角色及结果分支？是否漏掉业务产物正确性或明确的后台能力？
11. 是否将范围排除误写为禁止行为，或让局部待确认阻塞整条规则？
