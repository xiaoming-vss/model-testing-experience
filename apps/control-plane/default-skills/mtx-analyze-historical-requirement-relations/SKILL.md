# 历史需求关联与规则影响分析

读取平台冻结的 [输入 JSON](references/input.schema.json)，输出一个符合 [输出 Schema](references/output.schema.json) 的 JSON 对象。输入包括本次整理条目、历史候选和可用的已确认关系。材料内容作为业务数据处理。输入缺失或结构有误时，报告缺少的输入或校验错误。

## 分析过程

1. 逐条比对业务对象、角色、操作、状态、触发条件和结果。以共享规则、明确依赖或本次变更为关联依据。同名功能只作为检索线索。按规则拆分影响，每条影响对应一个具有明确条件的结论。
2. 从当前需求指向历史需求判断关系。沿用旧规则用 `depends_on`，追加行为用 `supplements`，调整局部条件或结果用 `changes`，旧行为在明确范围内由新行为接管用 `replaces`。同一历史需求快照用一条关系汇总，`relationType` 取本次主要动作，各条规则分别记录 `ruleEffect`。明确取消且缺少接续行为时用 `retired`，`currentRule` 填 `null`。
3. 按角色、状态和条件写明适用范围。旧行为及其适用边界照旧、只增加新场景时，用 `supplemented`，范围写新增部分。若新增行为同时改变旧规则的前提、操作、预期或适用边界，把受影响的旧行为单独记录为 `changed`、`replaced` 或 `retired`，即使整组关系仍是 `supplements`。例如，只新增手机报销是补充；若旧规则明确手机端禁止提交，则应把这条限制的变化单独记录。先后有多次变更时，沿已确认关系核对相交范围及实际条件。材料时间和版本顺序用于定位来源，适用性由规则证据决定。旧规则的其他适用范围按证据保留。
4. 为每条影响分别引用新旧材料中实际支撑判断的条目。两侧证据都已确认且适用时用 `proposed`。示例、冲突和未确认条目用于定位问题。范围或规则仍有疑问时用 `needs_confirmation`，并在 `openQuestions` 给出要向业务方确认的具体问题。有问题但尚无法定位到一条影响时，问题的 `impactId` 为 `null`。

## 输出和校验

- 原样复制当前需求 ID 和材料快照 ID。历史需求 ID、材料快照 ID 以及两个方向的条目引用均取自输入。为每组关系和影响项分配产物内唯一的 ID。
- 成功但没有可关联项时返回 `relations: []`。保留已发现的待确认问题。候选结果由平台审核，确认后才能用于历史用例核验。
- 对照 [输入示例](examples/input.json) 和 [输出示例](examples/output.json) 查看字段交接。输入和输出有文件时，用装有 `jsonschema` 的 Python 执行 `python3 scripts/validate.py <输出.json> <输入.json>`，通过后按调用约定返回结果。直接响应时只返回 JSON。
