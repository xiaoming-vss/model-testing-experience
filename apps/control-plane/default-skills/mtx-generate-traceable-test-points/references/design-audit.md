# 设计审查

初稿按完整范围、修订后按[独立审查协议](independent-review.md#修订后的增量复核)确定的增量范围执行以下适用检查，先检查再修改；逐项对照完整材料和范围分析，不以名称数量或格式合格代替业务审核。测试点和缺口必须有材料支持其关联本次变更、业务规则或受影响行为；上游问题、风险及引用本身不能证明相关性。对无关或明确排除的事项不要求覆盖，也不记录缺口；有依据的上下游影响仍须覆盖。审查记录可在内部维护，最终只输出约定 JSON。

## 1. 覆盖审查

逐条回查材料中的独立业务规则、明确结果及有意义的条件分支；核对分析的对象、影响、风险和未解决问题。先按[需求相关性筛选](../prompts/test-point-design.md#需求相关性筛选)剔除无关候选，再对相关要求标为已有测试点、可证明等价合并、明确排除/不适用，或预期未确认而形成覆盖缺口。被合并的要求必须能从保留名称识别，不能只在内部记录。对属于本次需求的不同状态、角色或处理路径，若各自可独立触发、失败或遗漏，逐个形成测试点；不得因结果相同将它们合成一条笼统名称。可独立失败的相关授权路径、状态准入、处理结果和必要先后关系分别审查；入口若只是执行路径不机械加点。检查有效范围的边界；仅在完整规则足以确定边界预期时生成，否则记录缺口。

## 2. 依据与条件审查

对每条名称按对象、前置条件、触发、预期回查材料正文及引用的材料块。名称中保留决定本条目标和预期适用范围的全局限制、例外及必要前置状态；例外如果是另一独立验证目标，应按其规则单独覆盖，不把不用于判定本条目标的分支塞进名称。相邻测试点或引用不能代替本条必要条件。共同条件相互约束时检查组合：局部允许不能覆盖全局过滤。审查逐条比较一般规则与其例外：若小于阈值被丢弃，概括“所有有效对象均有产物”的名称必须明确保留阈值等适用条件；即使有括号解释例外，也要检查主句是否仍断言所有对象都产生结果；产物数量不得等同于过滤前的全部有效对象数量。若阈值以上仍有其他未知条件，仅能验证不因该阈值被过滤，不保证最终产物一定生成。流程中分别确认每个直接前置阶段及其准入；完成上一步不自动代表跳过上传、审核或其他已明确的中间阶段。

区分充分条件与必要条件，材料说“符合条件时产生结果”不能反推其余情况；未达到某过滤条件的规则也不能证明达到阈值就必然成功。两个功能可以独立交付，不能据此断定所有开关状态下互不影响。报告、任务启动、状态变化与产物完成分别核对，不能将“已启动”写成“已完成”。核查每个并列对象与后续谓语的适用范围：若仅确认报告可查询，不得写成报告和其他产物都可查询；保留、不删除、可查询是不同判断。只有材料或明确确认支持的结论才能作为确定性预期，推断的影响只作关注方向；仅阻塞受争议影响的部分。

## 3. 粒度与名称审查

对一条名称中的多个状态或结果逐一判断是否可独立失败：独立角色权限、阶段准入、不同失败分支、产物内容或数据关联通常需要分别覆盖；不可拆分的关系可以作为一个目标。对每个条件和结果，核对它验证的是本条哪条规则，并比较该规则正确与典型错误时能观察到的结果；若结果相同，检查是否有依据使用其他观察或条件。另一独立规则先与所有候选比较，已有覆盖则去除重复，没有覆盖且在范围内时单独设计；不能因一个条件不能验证当前目标就删除其独立业务价值。不要根据同一接口、相同操作或相同前提自动合并正反分支。统一提示及其必要文案可以保留一个目标；枚举只在规则、范围和判断真正等价时参数化，名称仍需让覆盖范围可识别。比较所有候选，删除重复而不吞掉必要条件或结果。

最后检查每条的功能项、场景、【功能项】前缀和中文名称；再按覆盖审查结果回查修订未引入遗漏。每个测试点必须有真实材料块引用，适用的测试对象、影响和风险也关联相应 ID；引用不能证明语义正确或与需求相关。通过相关性筛选的目标若预期缺失或未解决，写为覆盖缺口，而不是替用户作结论。审查无法消解时如实保留相关缺口。
