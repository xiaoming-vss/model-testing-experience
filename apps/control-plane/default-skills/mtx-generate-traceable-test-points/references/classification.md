# 功能项、场景与命名

`module` 是被测产品中有实际职责的业务功能项，优先使用用户明确的名称；根据业务职责、对象和入口划分，需求标题、页面或按钮不自动成为独立功能项。上游 functions[].name 如果只是涵盖多个环节的需求主题，不视为用户已指定的功能项：结合明确职责区分例如核验、切片、分析、存量处理等独立能力；名称使用简短职责名，不直接用长句。只有输入明确要求的模块划分才优先保留。跨功能的关系归承担主要验收职责的功能项，并在名称中保留必要的跨功能条件；不凭关键词重复分配。按 module 再按 dimension 将 testPoints 相邻排列，同一目标只归一个主要场景。

`dimension` 使用以下适用场景，不为凑齐分类增加测试点：

- 功能场景：业务规则、操作与流程结果。
- 异常/容错场景：有依据的失败、拒绝、恢复和重试。
- 用户体验场景：独立且有依据的界面、反馈和交互要求。
- 兼容性场景：已明确的设备、版本、升级及原有行为兼容。
- 权限与渠道场景：角色权限及端、渠道限制。
- 数据与一致性场景：独立的数据、产物和关联一致性。
- 边界场景：已明确的输入、数量或范围边界。
- 时序与并发场景：有依据的顺序、重复和交错规则。
- 性能场景、长稳场景、安全场景：有明确依据的质量要求或已要求的基线测量。

`name` 以与 `module` 完全一致的 `【功能项】` 开头，紧接“验证”，以自然、精炼的语序写出适用对象、决定结果的必要条件、触发和预期；适当使用标点，避免多个时点和条件连续堆叠导致句意不清。明确要求的基线测量以“测量”或“观察”代替“验证”，不能表述为验收达标。跨功能关系按需追加其他已确认功能项标注，但不因多个前缀重复生成目标。名称是面向审核的独立信息，不能只把关键条件留在来源引用中；不写步骤、示例数据或没有依据的具体界面表现。
