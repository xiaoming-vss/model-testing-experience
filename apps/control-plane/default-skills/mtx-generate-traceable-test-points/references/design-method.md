# 测试点设计方法

按需求实际情况选择，不把清单当作产品承诺：

- **输入与数据**：识别已明确的合法范围、必填、格式、关联约束；对有依据的边界和等价类设计正反向目标。非法预期只表达规则能支持的结果，不臆造提示或拦截位置。
- **状态与流程**：列出状态、触发、准入条件及明确结果；区分状态变化与变化后的能力，关注直接下游的准入。与本次需求相关且阻碍目标判断的未知迁移或时点记录为缺口。
- **规则组合**：对共同决定结果的条件、全局约束和例外建立决策关系，覆盖有独立价值的有效组合。避免机械枚举不可达或等价组合。
- **事件顺序与影响**：对有依据的生效时点、重复操作、上下游关系及关联数据，保留会改变结果的先后与范围。推测影响仅在通过[需求相关性筛选](../prompts/test-point-design.md#需求相关性筛选)且阻碍目标判断时记录缺口，不自动写成既定预期。
- **界面与入口**：业务操作的路径通常是执行条件；只有入口的显示、位置、状态或可达性有独立依据和验收价值时才单独生成测试点。
- **质量属性**：材料明确要求的性能、安全、兼容等目标可纳入；明确要求基线评估但没有阈值时可表达测量目标，不宣称达标。风险线索须通过[需求相关性筛选](../prompts/test-point-design.md#需求相关性筛选)且阻碍目标判断才记录缺口，不发明阈值或产品保证。

## 条件是否能检验目标

分别写出候选的目标规则、适用条件、触发及观察结果，构想一种与该规则相反的典型错误；比较正确行为与该错误在候选条件下的可观察结果。若结果相同，单靠该观察不能验证目标：优先选择有依据且能区分的条件，或使用有依据的其他观察；不能发明内部字段或断言。条件与目标规则无关但有独立验收价值时，检查已有覆盖后独立设计；无额外价值则不重复。若预期或必需判据未知，按缺口协议处理；不可观察与测试准备不足也不能编造成业务缺口。该检查不保证发现所有错误，也不删除有独立业务价值的否定目标或不可拆分的一致性关系。

例：某权限开关决定有资格用户能否进入功能；停用账户无论开关状态如何均不可进入。若要验证开关是否生效，使用有资格用户并观察访问结果；停用账户的拒绝可作为账户资格规则的独立目标，而不是拿其“仍被拒绝”证明开关生效。示例只展示推理方法，不引入实际产品规则。

若产物生成同时依赖设备和数据条件，验证运行开始时开关关闭、运行中开启后本次仍不生成，应写明设备与数据条件均满足；仅写设备支持时，数据不满足也会导致不生成，无法通过该观察判断开关生效时点。条件来自需求而非本示例；不能因此自动假设所有产物都有相同前提。

## 粒度示例

- 规则为“1 到 99 的整数可提交”：有效边界、超界和非整数可按不同判断设计；不添加未提供的提示文案。
- 两个角色分别获得不同权限：分别保留有独立授权意义的目标。等值筛选的多个状态若规则相同且没有独立风险，可参数化表达，名称仍需保留覆盖范围。
- 同一次触发带来两个可独立失败的业务结果：分别生成目标；不可拆分的跨对象一致性关系可以保留为一个目标。
- 已知提交被拒绝，但拒绝原因或提示未知：保留有依据的拒绝目标，提示的未知部分按实际影响记录缺口，不阻塞整条规则。

范围分析提出“可能影响历史记录”而材料没有说明历史行为：先核实历史记录与本次变更的关联；确有依据且预期缺失会阻碍相关覆盖时，记录缺口并关联风险或影响，不生成“历史记录保持不变”的确定预期。仅凭风险标签无法证明关联时不生成缺口。

字段组合、边界推导与局部缺口难以判断时，参考 [测试点与缺口示例](decision-examples.md)。
