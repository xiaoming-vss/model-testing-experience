# 可追溯测试点设计 Prompt

输入、修订范围和输出协议沿用 SKILL.md。以下只规定本阶段的方法。

## 设计与复核

收到程序分组时，先按 [并发生成与归属规则](../references/parallel-generation.md)确定负责范围，以下设计和自查只处理该范围。其余任务在环境提供 `subagent` 工具时，先读取 [自主委派规则](../references/subagent.md)，按当前生成或复核任务选择子 Agent 角色，自主决定任务边界并汇总；没有该工具时仍按本技能完成全部检查。

1. 遍历材料中功能、规则、流程、条件、结果和问题；结合范围分析中的对象、影响与风险，建立内部的独立要求和覆盖候选。按需回看所引用的材料块及来源，区分现状、目标、示例与确认范围。已知事实与未知部分分别处理；候选先通过下方“需求相关性筛选”，再设计和拆分。
2. 依据对象特征选择方法：输入约束用等价类和边界，状态与流程用状态、触发和迁移，组合规则用条件关系或决策表，事件顺序用时序分析。只分析本需求适用的对象，先展开有独立判断价值的分支，再比较是否等价。有关取舍和示例见 [设计方法](../references/design-method.md)。
3. 对每个可确定的独立验证目标生成测试点，名称写清对象、必要条件或触发和预期；业务条件允许时可以做明确且无歧义的边界或反向推导。先确定要发现的目标错误，再核对候选条件和观察是否能区分正确行为与该错误；如结果相同，考虑有依据的其他观察或改选条件。结果同时受多个已知条件控制、需要靠“不发生”判断目标时，写明其他必要条件均满足，例如不能只写设备能力而遗漏数据条件。把另一业务规则与当前目标分开，并检查是否已有覆盖；不可拆分的关系仍可作为一个目标。判断方法见 [设计方法](../references/design-method.md)。按业务功能项及主要测试场景归类，具体规则见 [功能项、场景与命名](../references/classification.md)；无需凑分类、比例或条数。不能确定预期时，将受影响的目标记为覆盖缺口，保留不受影响的测试点。纯背景或明确范围排除不自动生成测试点。
4. 完成初稿后按 [设计审查](../references/design-audit.md) 执行覆盖、依据条件和粒度审查。默认返回 `self_review_only` 初稿；独立审查的启动条件、执行责任和模式选择以主技能为准。需要执行完整流程时遵循 [独立审查协议](../references/independent-review.md)，状态只根据真实执行结果设置。

## 需求相关性筛选

- 每个测试点或覆盖缺口都须能结合材料说明它覆盖本次需求的哪个变更、业务规则或有依据的受影响行为；明确关联的上下游、既有行为和存量数据仍应覆盖，不限于新增功能。单有材料块、对象、风险或问题的引用，不证明与本次需求相关。
- 上游对象、风险、待确认问题和原始图片或历史材料只是候选线索：回查实际变更、关联与用户确认的适用范围，筛掉无关内容和用户明确排除的事项。不因两个对象相邻、名称相似或假设存在依赖而创建测试点或覆盖缺口；也不将用户不关注某项细节扩大为排除整个业务环节。
- 对已通过筛选的目标，预期有依据时生成测试点；确实缺少决定该目标预期或覆盖范围的关键事实时记录覆盖缺口。与本次需求无关的未知、仅为补全材料而产生的问题、缺少验证手段或实现细节本身，不形成测试点或覆盖缺口。未知不等于已确认，也不自动排除相关测试。
- 独立失败、边界或组合是通过筛选后决定粒度的方法，本身不能证明测试目标与本次需求相关；不得为凑覆盖而扩大需求。审查和修订时重新执行筛选，删除无关候选并清理引用，同时保留有材料依据的实际影响及必要覆盖。
