# 场景拆分与命名

先读完整测试点与已确认依据，列出其中确实要求验证的条件、角色、动作和结果，再决定一条还是多条。每条用例各自有可执行的前置条件、操作和可判定预期；多条用例共同承接测试点的目标。拆分只改变用例的组织方式，不新增上游测试点或编造未确认规则。

- 先识别当前验证目标并检查每个场景能否识别该目标的典型错误：比较规则正确与错误时的可观察结果；结果相同时应核对有依据的其他观察或条件。场景混入另一独立规则、且无法在原目标内处理时按主文件提示上游核对。目标清楚且条件、角色或操作有独立判定价值时，可拆成独立用例。例如一个权限测试点要求验证授权与未授权用户分别能否查看报告，可分别命名“【报告查看】验证有权限用户查看报告”和“【报告查看】验证无权限用户无法查看报告”。以实际依据为准，示例不构成产品规则。
- 相同流程、相同预期下的等价取值可以作为同一用例的数据组；写清每组数据、操作和判定，不为了数量逐值拆分。一个明确场景也可以只生成一条；测试点只要求验证通用行为时，不额外枚举未经要求的位置、数量或边界组合。
- 名称以自然语序说明本条场景和结果，例如“验证运行中关闭开关后，本次运行仍生成深度信息和深度预览视频”，具体执行准备写入前置条件。必须保留用来区分本用例和其他用例的条件与准确的对象、产物范围；不能用笼统词扩大断言。避免“验证功能正常”“验证各种场景”等空泛标题，不照搬包含多个分支的长测试点，不将其他用例的条件放进本条名称。同模块标题须互不相同；正文中的条件和预期与标题一致。示例只说明语句写法，不是产品规则。
- 某分支的业务行为或必需判据未知，或测试点混入独立目标、场景不能判定其原目标且不能在原目标内修正时，不靠删除该分支、编造答案或笼统标题声称覆盖；按主文件的澄清协议处理。其他有独立价值的否定规则不因无法验证当前目标而被认作无价值。环境或测试资源尚未落实、但业务判据明确时，写出必要的执行准备。

例：测试点要求验证运行中关闭开关是否影响本次生成，又同时指定“生成条件满足时生成、条件不满足时不生成”。若唯一观察是本次是否生成产物，则不满足生成条件时不论开关时机对错都会不生成，不能通过该分支判定开关时机；它关注的生成条件是另一规则。该测试点要求两个分支时，返回 `CLARIFICATION_REQUIRED:`，说明应在上游分别核对开关时机目标与生成条件目标；不能把无区分度的分支直接生成第二条用例，也不能只输出满足条件的一条后声称完整。若输入明确提供足以区分开关时机的其他观察，则按实际证据判断。此例仅展示验证目标的判断方法，不构成产品规则。
