# 登录用例：简洁表达与必要条件

用于校准普通表单和输入校验的粒度，不是登录功能的通用覆盖清单。以下假设已审核需求确认本地账号密码登录、用户名必填、合法凭据进入首页并展示用户信息；缺少用户名时提示填写并停留在登录页。未指定精确提示文案，因此只写已确认的提示含义。实际任务没有这些规则时不直接照抄。

## 示例一：正常登录

```json
{
  "cases": [
    {
      "case_module": "登录",
      "case_title": "【登录】验证使用正确用户名和密码登录成功",
      "case_type": "功能测试",
      "priority": "1",
      "precondition": [
        "1. 准备一个已启用的本地账号，用户名和正确密码已知。",
        "2. 当前客户端未登录。"
      ],
      "test_steps": [
        "1. 打开系统登录页面。",
        "2. 输入该账号的正确用户名和密码，点击“登录”。"
      ],
      "expected_results": [
        "1. 显示登录表单。",
        "2. 登录成功，进入系统首页并显示该账号的用户信息。"
      ]
    }
  ]
}
```

保留启用账号、正确凭据和未登录状态。环境部署、网络连通和页面访问不重复列三遍；输入用户名、输入密码和点击登录可以合为一个连续动作，不额外检查本条未要求的密码掩码或输入框即时反馈。

## 示例二：用户名为空

```json
{
  "cases": [
    {
      "case_module": "登录",
      "case_title": "【登录】验证用户名为空时阻止登录并提示填写用户名",
      "case_type": "异常测试",
      "priority": "2",
      "precondition": [
        "1. 准备一个已启用的本地账号及其正确密码。",
        "2. 当前客户端未登录。"
      ],
      "test_steps": [
        "1. 打开登录页面，保持用户名为空，输入准备的正确密码。",
        "2. 点击“登录”。"
      ],
      "expected_results": [
        "1. 用户名为空，密码已输入。",
        "2. 未登录成功，页面提示填写用户名，仍停留在登录页。"
      ]
    }
  ]
}
```

正确密码用于排除其他输入错误。这里只验证用户名必填；如果已审核需求还要求精确提示、即时触发或特定提示位置，再将对应内容写入步骤与预期，不自行增加。

## 复杂登录场景保留什么

| 已确认的测试目标 | 不能因精简删掉的条件或动作 |
| --- | --- |
| 错误密码被拒绝，且本次不触发锁定 | 启用且未锁定的账号、已知正确密码及不同的错误密码；若有失败计数策略，初始计数须确保本次失败仍低于锁定阈值 |
| 达到失败阈值后锁定，超时恢复 | 已确认的阈值和时长、未锁定且失败计数清零的专用账号；按阈值执行失败次数，不将示例的 3 次写成通用规则；共享账号需要恢复 |
| 第二台设备登录后原设备下线 | 同一启用账号、两个独立客户端会话、已确认的互斥规则；先后登录与返回原设备验证放在步骤 |
| 勾选“记住我”后重开仍登录 | 正确凭据、已确认启用的功能，以及允许 Cookie 且关闭时不自动清理 Cookie 的浏览器设置；不能把“重开后仍登录”当成前置 |
| 闲置超时退出 | 已确认的超时时间；在步骤中建立登录会话并保持无续期操作的闲置，再触发受保护操作验证 |
| 退出后回退不能访问受保护页面 | 已登录并访问过具体受保护页面，或先在步骤建立该状态；实际退出、回退和访问检查不能省略 |

这里的策略条件仅在对应需求已明确时使用；不因示例出现锁定、Cookie 或互斥就增加上游测试范围。

## 预期应能直接判定

- 已确认只需提示用户名缺失时，写“提示填写用户名”；已确认精确文案时再原样引用。不要列“请输入用户名或请输入您的用户名”作为猜测。
- 同一场景使用确定预期；“若产品防账号枚举则……”属于规则选择，先从冻结材料确认。已确认支持多种配置时分别对应配置与结果。
- 全角与半角如何处理、锁定次数、解锁方式及错误提示都须有产品依据，不能按常见实现补写。
