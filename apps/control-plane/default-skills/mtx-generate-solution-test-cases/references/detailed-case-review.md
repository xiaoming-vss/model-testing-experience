# 完整用例独立审查

仅在调用方明确指定独立审查时使用。审查者接收与生成同一次运行冻结的材料整理、测试范围风险分析、本批已审核测试点及其缺口和审查问题，以及待审候选、平台分配的 `case_id`、测试点到用例的映射；如有前轮审查意见，同时接收意见及本轮候选。仅审查已给出的点与用例，不执行测试，不修改候选或上游，不把模型建议当成人工审核。输入不足以审查时指出具体缺口，不编造材料、映射或业务事实。

## 审查范围

1. **目标和依据**：逐点检查用例的实际步骤和预期是否验证原目标；结合已确认材料、适用的共同规则、关联问题和风险检查条件及结果。材料块引用用于定位，`basis=derived`、风险分析、示例、未确认内容及审查意见不自动变成产品规则。区分业务预期确实未知与只缺执行资源；不能让“准备正确结果后比对”掩盖未知判据。
2. **可执行与可观察**：检查对象、角色、状态、测试数据及观察范围；步骤是否可达、条件是否在操作前核实、测试人员能否按步骤检查预期、断言是否能发现目标失效。区分受理、执行完成和最终结果；只在必要时要求恢复共享环境。准备粒度按 [编写方法第 3 节](../prompts/case-writing.md#3-准备数据和起点) 评估：只补本条不可缺少的条件或特殊能力，不因省略通用环境、普通页面入口绑定、重复基线记录或逐字段操作而要求加回；同时核对影响预期的业务条件没有被删掉。未提供具体地址或工具不自动等于业务预期未知。
3. **对应与重复**：一个测试点可以对应多条用例；检查给出的映射是否遗漏测试点、指向错误用例，以及多条用例是否共同覆盖原目标、各自场景是否清楚且不存在无意义重复。比较目标规则正确与典型错误时的观察结果：若两者相同且无其他有依据的观察，指出该场景无法判定目标；测试点混入独立规则而不能在原目标内解决时以 `unmet_target` 建议上游核对，不误报为业务事实未知。标题不必等于测试点名称；不因已有映射就认定语义已覆盖。重复或新增覆盖的建议只作为问题提交，不自行合并、删除或增加测试点；只用输入中存在的 ID，不按数组位置猜测映射。对人工编辑或继续优化后的候选，尊重已有的新增、删除和改名，不要求模型恢复已删除用例。
4. **问题处理**：将前轮意见当成待核验线索，逐项对照当前候选和冻结依据；已解决的不再作为未解决问题报告，仍存在的写明事实。只报告会影响目标、依据、执行、判定或维护的具体问题，不为了凑数或满足正向/边界/异常比例提出新范围。

核对当前测试点是否依赖 `coverageGaps` 或 `reviewIssues` 中尚未解决的业务范围、完整性或判定标准，结合来源和对象判断，不以缺少直接 ID 引用为由跳过。未知“全部/完整”的范围不能靠准备清单或文件存在来证明；与目标无关的问题不阻塞。逐条通读名称、前置、步骤和预期：标题是否把已在前置条件中写清的执行准备和初始状态堆在场景动作之前？步骤是否对象指向不明或跨多个执行阶段，预期是否重复解释整条规则而不便判定？对影响执行、判定或维护的可读性问题，使用调用方 Schema 支持的 `readability` 分类，给出具体位置与不改变业务范围的改写建议；保留区分场景所需的条件，不把文字风格问题误报为业务事实缺失。调用方未提供该分类时，遵守其输出 Schema，不擅自添加分类。指出重复的准备、记录、回读或无关的跨阶段断言；保留动态时机、必要对照和恢复环境所需的动作。需要验证运行开始时取值时，启动前确认或可靠的启动记录应保留；不能用运行中的当前值替代，也不要求已在步骤确认的普通单次运行另建一套重复基线。恢复共享环境的步骤和对应预期允许留在现有 `test_steps`、`expected_results` 中，不因其不是目标业务断言而要求移除或新增恢复字段。

## 问题分类与输出

调用方提供输出 Schema 时，以其结构和标识字段为准；没有额外 Schema 时输出一个 `{"issues": [...]}` JSON 对象，不输出 Markdown 或其他文字。每项问题包含：

- `kind`：`unsupported_expectation`、`unmet_target`、`unreachable_step`、`missing_preparation`、`duplicate_candidate`、`readability` 或 `clarification`。
- `testPointIds`、`caseIds`：受影响的输入 ID 数组；确实无法定位时使用空数组，不捏造 ID。
- `materialBlockIds`、`materialQuestionIds`、`testObjectIds`、`impactAreaIds`、`riskIds`、`scopeQuestionIds`：支持判断的材料块、材料问题及范围分析对象的 ID 数组；未使用的数组为空，缺失依据的问题可全部为空并在 `issue` 说明缺少什么。ID 必须分别属于对应输入集合，不跨类型混用。
- `issue`、`impact`、`suggestion`：分别说明具体问题、对验证的影响及不扩展范围的处理建议。

`clarification` 只用于当前测试目标必须依赖、且从已确认材料无法决定的业务行为或判定；写明阻塞的测试点、具体缺口及现有依据为何不能决定。不把普通可修复的步骤问题或账号、测试数据、执行工具未配置当成业务澄清。没有问题时返回 `{"issues":[]}`。审查意见是模型建议，不能声明人工批准、测试执行或通过；平台负责决定是否修订、保存候选、展示状态和进入人工审核。
