# Design UI test cases

The functional cases define what must be tested. Design corresponding UI cases before element binding. Read [execution profile](../references/execution-profile.md) and [references/contract.md](../references/contract.md) for the versioned output and capability decisions, then [references/platform-equivalents.md](../references/platform-equivalents.md) before excluding a composite check.

1. Treat the supplied `functionalCases` (or `cases`) as the complete scope of this invocation. When `batch` is supplied, its `caseIds` identify the current module; return exactly one design per supplied case. The Worker groups modules and merges results. Keep the entire supplied module together.
2. Read each selected case's title, prerequisites, actions and expected outcomes. Preserve the original acceptance question, object relationships, quantities and timing.
3. For lifecycle scenarios, identify initial environment inputs and values produced by earlier actions. Use supported scalar observations from platform-equivalents.md to retain runtime ID and baseline dependencies; record the producer/consumer relationship in existing action/target/value text without adding locator or dataPlan fields. Preserve original case identities and source-step order. If cross-case order conflicts with dependencies, explain the scheduling prerequisite in limitations rather than silently reordering. Produce ordered business steps and corresponding assertions. Split mixed expected outcomes into verbatim excerpts so supported UI checks remain usable even when another clause is excluded. Retain every prerequisite as a requirement; missing accounts or fixtures do not remove the case.
4. Classify actions/assertions against the caller's declared executor capabilities. First consider equivalent combinations of supported checks: an authoritative total of one plus the exact sole record ID can prove no extra records without a set-comparison keyword. Do not exclude based merely on words such as all/set/count. Exclude only operations outside the UI channel or explicitly unsupported capabilities. Record the precise operation/operator and reason. Missing locators, missing data, uncertain implementation or a source/requirement conflict are not capability exclusions.
   Check the semantic operator, not just whether a sentence can be labeled text_eq. Split composite expectations into their individual clauses. Input current value, checked state, row counts, OR alternatives and runtime-value comparisons require an actual supported implementation or equivalent combination; without one, exclude that clause with its precise reason here. Never mark an unsupported relation as an ordinary text assertion and defer it to a future YAML conflict field. Missing fixture values or locators remain included.
Before finalizing classifications, perform the dependency and whole-scope check in [references/capability-proof.md](../references/capability-proof.md). A manual/external calculation in limitations does not make its downstream automatic assertion supported. Preserve the full original goal and all source clauses, including explicit limitations when no complete supported strategy exists.
5. Include UI steps regardless of whether stage one found their elements. Express the operation, semantic target and intended value/relationship; do not supply locator strings or require control IDs, uniqueness proof, fixture evidence or ready status.
6. Mark coverage as full, partial or excluded design scope. If an excluded assertion defines the case's core goal, preserve that limitation explicitly. Never present a remaining setup check as verification of the original goal.

Use stage-one facts only as optional terminology/context. An absent or empty surface must not change design inclusion. Stage three resolves source details, locators and missing values into editable YAML.

Return the complete `ui_test_scenarios/2.0` JSON object directly in the final response, following the caller's JSON Schema. Include `schemaVersion`, `capabilities` and this module's `cases`; use no Markdown or explanatory text. `outputPath` and file receipts are not part of this stage's delivery contract. The Worker validates the response itself, so a saved file or a claim of successful validation cannot replace the JSON response.

When `currentArtifact` and `revisionInstruction` are supplied, use the existing module as the candidate data structure and patch the affected case/step IDs. Preserve unaffected objects rather than re-authoring every case from the source. Before serializing, compare changed objects against currentArtifact: each change must follow the revision request or a specific newly established semantic defect; retain existing IDs and wording elsewhere. Recheck modified dependencies and original source coverage, then return the complete module, including unchanged cases. When the Worker supplies validation errors and the previous response, correct those errors and return the complete module JSON again. Preserve original titles, prerequisites and source excerpts; keep supported assertions included. The Worker controls the repair limit and final merge check, then waits for human review before stage three.
