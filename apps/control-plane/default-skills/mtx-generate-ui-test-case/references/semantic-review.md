# Semantic review of a generated candidate

Read this reference when reviewing candidateYaml or repairing a semantic review finding. Review supplies evidence about fidelity to the accepted design and whether declared gaps can be completed; it is advisory and does not decide generation success. It does not certify the product, require fixture values to be known already, or redesign the test suite.

## Evidence before reporting a finding

For each proposed issue, establish these links:

1. Identify the candidate case by name and its corresponding caseId in the reviewed design. Use that case's prerequisites, included actions and included expectations. For prepared data and missing concrete values, apply environment-variables.md. A shared module is not a shared fixture or execution order. Apply another case's setup only when the inputs explicitly declare that dependency.
2. Read the entire candidate case, including setup, prior saveTo producers, later assertions and missingFields. An expectation can be established by multiple steps. Do not require every step to independently prove the whole expectation, or demand duplicate assertions when another step already proves it.
3. State a concrete mismatch with an included target: an omitted clause, incorrect object, unsupported operation, unfillable field, or a counterexample that passes the candidate but violates the target. Distinguish an actual contradiction from an unknown runtime fact.
4. Check the proposed repair against the same scope, available executor capabilities and source evidence. A valid finding does not make an invented repair valid. Give a supported correction or identify precisely what requires design confirmation.

Do not run the generation/export workflow or require a passing audit to return this report. Preserve the candidate and report concrete findings for human disposition. Only findings that satisfy these links belong in the caller's issues array. Use its existing JSON fields and codes; do not add severities, advisories or new output keys. No actionable candidate defect means {"issues": []}, not a fabricated issue to demonstrate thoroughness.

## Decision boundaries

- **Generation defect:** report omitted included assertions, changed or weakened expectations, wrong record identity, invalid runtime references, and gaps that cannot implement their described step when filled. Preserve the business oracle in the repair.
- **Ordinary missing information:** accept accurate missingFields for environment values, existing fixture IDs, expected values that can be provided before execution, or genuinely unknown locators. For a proposed field mismatch in an XPath predicate, apply handoff.md’s consuming-field and retained-observation checks before rejecting the gap. An incomplete draft is not an import-ready test; that distinction is handled by the existing completion gate.
- **Product behavior differs from the expectation:** a faithful supported assertion remains valid even when it fails on the current product. Do not reject it merely because source defaults, enabled states or returned values violate the requirement. Executor expressibility and product conformance are separate: a supported assert_visible for the expected column header remains expressible when the current product hides that column. “This assertion will certainly fail on this implementation” proves a possible product defect, not an unfillable assertion. A text-based selector for the intended observable is not an invented executor capability. Require a defect in the candidate expression itself before reporting an issue. Lack of a frontend message implementation does not prove a backend message cannot occur.
- **Excluded scope:** do not restore an action or expectation marked excluded. coreExpectationIds and the original case text do not override the explicit status of that expectation. If an included expectation depends on an excluded operation and no supported expression exists, identify that design dependency; do not demand that generation silently reintroduce the excluded operation.
- **Negative assertion:** an included `absent` expectation is implemented by `assert_hidden` with a locator for the element that must not appear and a millisecond timeout. Do not demand a positive success toast as a substitute for the reviewed negative target, and do not treat the timeout as a business expected value.
- **Unimplementable included design:** distinguish the upstream conflict from a bad YAML expression. If the candidate fabricates support or disguises an impossible operation as a fillable field, report that concrete candidate defect and direct its repair to design confirmation. Do not repeatedly prescribe unsupported implementations or weaken the target to get a pass. The current issues contract cannot route design questions separately; do not invent that routing or declare an unimplemented assertion executable.
- **Negative action attempts:** continueOnFailure on an intentional negative click is not itself proof that an included assertion is ignored. Check the later effective assertions and the exact retained target. If disabled/absent checks are explicitly excluded, do not demand their restoration merely because the click can time out. Separately report any genuinely omitted included observation or outcome, with its target ID. Never advise deleting an included action solely to avoid its expected product rejection.
- **Declared setup prerequisites:** distinguish a required precondition from evidence that it has already been provisioned. A supplied shared-login/session declaration is accepted context; do not demand duplicate login flows merely because each case opens a protected URL. Conversely, the original case saying “already logged in” alone does not supply a reusable session to an executor known to start fresh. If source-backed routing and the actual execution context establish a missing authentication setup, retain that specific prerequisite in the editable draft or implement supported login steps with genuine missing inputs. Empty metadata alone is not proof of the executor's session behavior; check the available execution evidence. Do not invent credentials or silently assume an authenticated session.
- **Uncertain risk or preference:** absence of proof is not a proven mismatch. Do not reject based solely on a different preferred locator, a hypothetical concurrent data change contrary to the fixture assumptions, or another case's prerequisites. Retain an actionable finding only when this case's required scope is demonstrably not handled.

## Live input values

For initial/current input or textarea values, follow [live-values.md](live-values.md). Verify the capture time, an effective comparison where the target requires one, and the unchanged independent expected value; recording alone does not assert a property.

## Interaction equivalence

Assess the event hit target and effect, not only the last DOM node named by a selector. A source-backed single-button wrapper can receive a locator click whose pointer actually lands on its child button, including an intentional disabled-button attempt. An ancestor selector alone is not proof of a different action. Conversely, a wide container or wrapper with several controls may hit another target. Establish the concrete geometry, event forwarding or observed hit target before accepting or rejecting equivalence; retain genuine uncertainty as a locator evidence gap rather than inventing an outcome.

## Collection and pagination checks

For before/after state targets, bind each pair to the same record identity. A per-position transition matrix is not sufficient: a refresh can reorder records. Check valid progression under reordered rows and an invalid regression hidden by reordered rows. Use [state-transitions.md](state-transitions.md) for a finite supported construction, while retaining the original labels, timing and control-flow requirements.

Judge identity, multiplicity and page coverage separately. First establish the expected collection cardinality from this case. A minimum of three records permits four or more; checking only three IDs plus a total count does not cover all records. The same applies to checking one ID per filter or two baseline IDs. Reject this specific sampling substitution only when the retained target requires the full collection; do not expand an explicitly sampled target. For an exact record-list expectation, total count plus membership in the allowed IDs is insufficient: expected [A, B] and actual [A, A] have the same count and satisfy membership. A suitable assertion for distinct expected IDs requires each ID exactly once and the expected total, or another supported equivalent. Check predicates inside missingFields.reason too: supplying IDs cannot repair a logically weak predicate. Respect explicitly weaker accepted expectations instead of upgrading every count check to set equality.

Determine record count bounds from this case's prerequisites and explicit shared fixtures. Do not borrow a different case's minimum count. If the target explicitly covers all pages and the candidate only asserts the current page without a supported bound or pagination procedure, report that limitation on its own evidence; do not claim that the current data necessarily spans pages.

For a two-page distinct-count proof, independently inspect within-page uniqueness on page one, within-page uniqueness on page two, and disjointness across the two observations. Run the counterexamples with a duplicated ID only on page one and then only on page two; cross-page comparisons alone miss both. Do not impose these checks on a plain row-count target that does not require distinct records.

A missingFields instruction to “confirm the data fits within 10 rows” or any other new bound changes the accepted scope when no such bound was supplied. Filling fixture IDs cannot supply missing navigation or make unobserved pages visible. State the unresolved scope dependency without requesting smaller data as a repair.

Increasing page size is sufficient only when the available option and a bound covering this case's full result are established. A suggested size such as 200 is not a universal full-list solution. Preserve any requirement that specifically tests the default page size. Account for virtualization: increasing the page size does not prove all rows are in the DOM.

## Waiting on asynchronously updated state

Check how the page obtains fresh data. Waiting for a locator only observes the DOM; it does not click a refresh control or fetch a new snapshot. Give repair suggestions that follow the declared executor control flow. A linear sequence of sleep, refresh and failing assertions with continueOnFailure=false stops at the first failed assertion; it is not “retry until any round succeeds.” Setting continueOnFailure=true also does not create a success branch or prove that any observation passed.

When the accepted target permits observing a stable terminal state after a bounded wait, retain the supported wait/refresh actions and make the decisive assertion after the last refresh, using the stated timing budget or an explicit timing prerequisite. Intermediate observations may capture evidence but must not impose an earlier completion deadline. If the design requires conditional retries, early exit, or observing a transition that may disappear between snapshots, establish those capabilities or report the precise design dependency. Do not prescribe imaginary loops or silently substitute a narrower time window.

## Repair convergence

Re-evaluate each received finding against unchanged inputs before editing. Apply supported fixes, preserve already-correct steps and legitimate gaps, and check the complete affected case. Treat a prior review as a hypothesis to verify, not authority to override accepted scope. A new review checks the final candidate afresh; an earlier issue disappearing from the report does not establish that it was fixed.


## Final review pass

Before emitting the report, revisit every included expectation for each retained case, including expectations that received a finding in an earlier review. Enumerate included targets directly from the unchanged reviewed design and inspect the whole retained scope, not only cases with an obvious first defect. No generation account or audit file is required in read-only review. For each collection target, apply the same-count/different-unchecked-ID counterexample to the final candidate. A previous repair that added one sample does not resolve a whole-list requirement. Deduplicate findings by root cause, but do not omit an unresolved cause merely because a different defect in the same case is more conspicuous.

For each proposed rejection based on source behavior, ask: does this prove that the test cannot be expressed by the executor, or only that the current product would fail it? Keep only the former or a separate, concretely demonstrated candidate defect. Example: an accepted scenario expects the “Status” column after selecting mode A; source currently renders that column only in mode B. A supported visibility assertion on the Status header in mode A is a valid defect-revealing test. Its expected failure is not a generation issue, and the repair must not change mode A to mode B or erase the assertion. Separately assess whether fixture IDs and later comparison steps faithfully cover their accepted targets.

Before emitting each issue, re-read the exact step in this invocation’s candidateYaml at caseIndex/stepIndex. If working from a local copy, verify parsed equality with the supplied current candidate first; diagnostic attempt files may be stale after a repair. Verify that every quoted missingFields reason, operationValue and locator belongs to that step. A nearby source-attribution gap cannot be reported as the reason of an independent ID-list comparison when that comparison already asks for the correct list. Cite related steps explicitly when a multi-step finding requires them; do not transplant their fields.

Emit the caller's JSON object directly, starting with `{` and ending with `}`. Do not wrap review JSON in Markdown fences, explanations or tool markup.


An expected list or column hidden by the current frontend is not, by itself, evidence that the required fixture cannot exist or that a supported assertion is unexpressible. Frontend branching alone does not prove backend data cannot be prepared. Preserve the expected business object and its identifier. Where source attribution can be established by independent fixture metadata, a complete source-specific ID list can express membership without requiring a new visible “source” column. Keep unknown fixture IDs as actual data gaps. Assert the intended table/column identity before comparing records so a currently wrong view fails the test; do not use its unrelated raw-record ID as a substitute. If no independent fixture provenance or supported observation can be established, identify that specific dependency instead of inventing a current-product guarantee or narrowing the accepted branch.

Identifiers from different lifecycle stages are not interchangeable without a proven relation that preserves the target. If converted records X and Y can share collection ID A, checking A cannot distinguish X from Y and does not implement an expected converted-record-ID comparison. A source-specific raw-record list therefore cannot replace a converted-record list merely because the current view exposes only raw IDs. Use this counterexample when validating repair suggestions as well as candidates.
