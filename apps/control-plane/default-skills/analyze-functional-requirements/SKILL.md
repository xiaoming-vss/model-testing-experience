# 功能需求分析

将叙述性需求转为可追溯、条件明确、结果明确的独立规则与场景，供下一步生成测试点（测试用例名称）。本阶段只输出分析，不提前生成最终用例名称、步骤、测试数据或执行脚本。

## 上游需求理解 JSON

结构化需求仅接受 artifactType="requirement_understanding"、schemaVersion="2.0"。读取 functionalOverview、businessFlows、modules、businessRules、questions、sources 和 evidence；普通文本需求按本技能的输入说明处理，旧版结构化对象不当作普通文本解析。

先建立规则与证据索引：operation.ruleIds、流程 conditionRuleIds 指向 businessRules；事实 evidenceIds 指向 evidence，再通过 sourceId 追溯 sources。多个条件规则表示同时满足。同一规则被多个模块或流程引用仍是一条规则，引用关系本身不新增测试目标。

读取事实 value，省略 confirmationStatus 仅在事实有有效证据时表示 confirmed；example 不作为产品事实，unconfirmed/conflicting 保留缺口，not_applicable 不扩大为禁止行为。概述字符串只说明职责或路径，不单独形成已确认验收规则；可选字段省略表示未记录，不推断默认值或不适用。options.completeness 保留选项完整性语义，open 问题的影响继续有效。

确认承接必须闭环：用户回答的问题必须直接回写到对应事实、规则、操作或交互，补充确认状态和来源，然后删除对应的 `openQuestions`/`questions` 及所有关联引用。已确认行为不能再次拆成同义问题；只有答复没有覆盖的独立业务不确定性才保留为待确认项。

modules.entryPoints 提供入口，operations.steps 提供操作，interaction 提供控件、选项、触发、联动及 results 观察依据。按 ID 读取规则与来源，无需把证据表和规则全文复制到各处。当前技能仍使用自己的输出协议，不把需求理解的 evidence/evidenceIds/conditionRuleIds 加入输出结构。


### 向五字段分析映射

- 从模块 entryPoints 提取入口，从控件与规则提取场景因素；只有有依据的 confirmed 取值进入 confirmedValues，未知默认值保留 null。上游多选默认值为数组时，现有 defaultValue 用准确的中文字符串描述该默认组合，不新增数组类型或遗漏组合含义。
- 逐项核对 businessRules 与 operations.steps、interaction 中的业务约束，包含可编辑字段、操作作用对象、选项取值、默认选择、保存与提交差异；上游规则列表不是全部需求。将影响结果的约束纳入 businessRules，操作触发、联动及结果观察分别承接 trigger/preconditions/expectedBehavior/observableOutcome；纯路径说明不机械形成独立规则。
- 五字段输出的 sourceReferences 是字符串数组：先按 evidenceIds 解析 evidence 与 sources，再将来源名称、已知版本和真实定位写成简短可追溯字符串；保留必要的上游规则/操作/控件/证据 ID 以区分同章节内的不同约束；只有判定需要原话时附必要短摘录，不输出来源对象或臆造章节。
- 将仍有效的上游 open 问题映射到 openQuestions，沿用本分析 Q01 等编号约定，并在影响和来源中保留原问题定位；已答复问题根据明确答复更新事实，不复制为未解决问题。

将上游规则按对象、条件、行为和结果核对后再提炼验证目标；汇总规则与具体规则重叠时合并目标并保留来源映射。逐条核对阶段完成与下一阶段准入，检查子任务状态聚合条件是否重叠；无法由输入消解的冲突写入现有 openQuestions，局部阻塞受影响预期。

对每个上游 open 问题核对其实际质疑的事实；即使该事实省略状态或标为 confirmed，也不能把争议结论直接升级为明确验证预期。只阻塞争议部分，保留同一规则内其余确认事实和准确的用户原话。材料范围不明时，不自行拆成筛选状态与流转状态两套口径。

## 输入理解

常见输入为「版本号＋功能理解记录」，按以下内容组织；允许缺节、多模块或同义标题，不要求用户重新排版：

- 记录说明：来源、范围、材料冲突时的优先级。
- 这个功能是做什么的：目的、背景、含义、原行为与变化。
- 这个功能怎么进入：角色、端、页面路径与操作入口。
- 这个功能怎么使用：按配置、对象类型等划分的分支、限制及异常处理。
- 用户看到的完整流程：串联操作与处理，可能补充全局、生效或影响规则。
- 当前还不够明确的地方：缺失、歧义和待确认信息。

「怎么使用」与「完整流程」均需读取，合并重复规则并保留补充信息。遵循输入指定的来源优先级；不能消解的冲突列为待确认。“暂无问题”的声明不能覆盖实际不确定描述。

## 分析方法

1. 提取范围、适用与排除对象、角色及入口。保留输入中的业务术语，不擅自合并不同系统、端或对象；原文举例不等于穷尽取值。
2. 提取场景因素、明确取值与默认值，识别条件的适用关系。按有效且有业务意义的组合拆分，排除明确不适用组合，未明确组合进入待确认；不机械做笛卡尔积。
3. 拆成独立规则：什么条件下，对什么对象，由什么事件触发，系统应做什么、禁止或跳过什么。可独立失败的判断分开表达，重复规则合并并保留所有出处。
4. 按以下维度检查，仅分析与当前需求相关的内容：
   - 前置条件、角色权限、入口及渠道限制。
   - 输入、合法值、空值、数量及边界。
   - 主分支、顺序、状态变化及可观察结果。
   - 默认状态、历史数据、升级兼容及原行为保持。
   - 生效时点、影响范围、在途对象、切换、重复及并发操作。
   - 关联数据、设备、页面及跨端一致性。
   - 失败、恢复、重试及验证依据。
   - 性能负载、资源竞争及持续运行风险，按下述性能与长稳规则确定分析范围。
   不强行为所有维度生成规则或问题，未提及的行为不是既定需求。
5. 按下述场景拆分与约束组合规则形成场景，明确条件组合、触发事件及核心验证目标。
6. 整理影响理解或测试设计的待确认项，每个问题尽量聚焦一个可独立回答的决策，注明影响及具体阻塞工作。缺口不阻塞其他可完成分析。

## 场景拆分与约束组合

- 以独立业务判断为覆盖单位。同一规则包含不同前提、触发操作或分别可失败的分支时分别形成场景；同一次触发的一组关联结果可合并。多个页面各自承载准入、权限或修改行为时保留入口差异，纯路径别名无需重复场景。
- conditions 表达同一次场景中同时成立的条件。将“状态 A 或 B”“分别验证四种组合”等具有独立判定价值的分支展开；多个条件取值使用同一判定关系且没有独立风险时，合并为一个范围明确的参数化场景，完整取值保留在场景因素或规则中。例如状态筛选均要求“记录状态等于所选状态”，无需每个状态复制一条；标题组合的显示内容不同则分别分析。生命周期状态参与操作准入或重复提交判断时，保留排队、执行中、失败等独立分支：最终都被拒绝不意味着触发条件和风险相同。仅用于等值筛选的枚举可以参数化，参与状态流转的枚举应按业务判断展开。不为达到数量而拆分。
- 同一业务判断已由具体场景承接时，在该场景的 relatedRuleIds 中补充相关汇总规则 ID，不复制同义场景。拆分完成后比较条件、事件和预期，合并只有对象名称或枚举值变化的等价目标，保留真实入口限制与结果差异。
- 查找共同决定结果的约束，按有效组合分析允许、拒绝和边界。局部允许仍受全局过滤、权限、范围与阶段条件约束；关联参与决定预期的全部 relatedRuleIds。例如“人工保留”仍受最小时长过滤时，应分别分析保留且低于阈值、保留且达到阈值、丢弃且达到阈值。这里的动作与阈值只作方法示例，实际规则取自输入。
- 阶段准入按入口分别展开：注明该入口真正要求完成的对象集合、完成条件与触发事件，并分别考虑满足条件、相关条件未满足和后端直接请求（输入明确要求后端校验时）。下游入口应覆盖其直接前置条件未满足的情形，不能只用更早阶段未完成代替。
- 明确操作前的状态，例如已保存还是仅编辑、请求已提交还是执行完成、产物集合完整还是仍在生成。验证持久化隔离时使用已保存前提；只有输入涉及未保存切换时才分析其行为，缺少结论则记录问题，不推定自动保存。
- 截图数值只帮助理解字段和对象。场景优先用相对边界、明确状态和关系表达条件；必要时保留输入示例的完整语境，不能保留百分比却悄悄改变其对应任务状态。根据规则构造的边界、组合或反向场景标为“基于规则推导”，不因为基础规则明确就标为“需求直接描述”。

## 性能与长稳分析

- 主动检查当前业务是否涉及批量处理、并发访问、排队、持续服务或反复资源申请释放等特征。仅有风险线索时关联实际业务记录适用性或评估范围问题，不将风险当作已确认验收要求，不给无关功能套通用清单。
- 有明确质量要求时分析指标验收；用户或材料明确要求性能/长稳评估、建立基线时，可以分析测量目标。没有阈值不妨碍测量目标，但不能据此断言性能达标、无泄漏或永不衰减。明确要求验收而标准缺失时，记录待确认，不擅自改成测量任务。
- 性能提取业务操作、数据规模与分布、并发数/到达速率、负载阶段、环境配置及响应时间/吞吐/耗时/队列/错误率等口径；长稳提取持续负载与时长、循环操作、资源占用趋势、积压变化、资源释放及运行中与结束后的业务正确性。只提取适用且有依据的内容，未知量不默认 24/72 小时或固定并发。
- 使用现有 scenarioFactors 记录已知负载因素，businessRules 保留真实功能和质量依据，scenarioBreakdown 表达“指标验收”或“基线测量”的目标，openQuestions 记录执行条件或验收缺口。测量不是新增产品承诺；具体字段处理见 [references/output-contract.md](references/output-contract.md) 的性能与长稳语义。

## 模块职责识别

- 需求标题表示本次改动主题，不自动代表唯一业务模块。优先保留用户指定的模块划分，否则结合现有产品结构、独立职责及业务对象识别模块；不同页面不必然是不同模块，同一需求也可涉及多个模块。
- 使用现有 entryPoints 的 function/path/action 表达各模块职责和入口；在规则名称、applicableObject、trigger、场景 conditions 与出处中保留必要的归属线索。不增加 model 或 modules 字段，也不提前输出最终测试点分类。
- 不同模块的独立要求分别分析，避免把发起、任务进度、结果展示、授权和筛选等不相干目标打包为一条规则。不可拆分的跨模块关系可以保留，注明参与对象、条件及核心验证结果。
- 区分发起位置与验收位置：从数据检索发起而在任务详情验证的目标，需同时保留发起条件和详情对象；不能删掉其中之一，也不要求每个参与模块各复制一条同义规则。
- 同名弹窗不自动认定共用实现或规则，后台共用能力不自动新增产品模块。后续测试点阶段根据原始需求与这些归属线索确定 model。

## 来源核对

- 原始需求和历次已确认业务补充共同构成有效依据，以最新确认内容为准；不要求所有补充都回写原始文档。
- 用户提供的最新版分析中明确记录的业务补充可以沿用，不因缺少完整历史对话就自动降级或删除。
- 不自行编造确认记录；区分业务补充、推导、待确认以及仅针对格式或表达的修改意见。
- 合并版本时保留已确认内容，按实际业务答复更新待确认项；格式调整或重新生成不能自行关闭未回答的问题。
- 同一条目混合明确和待确认内容时分开处理；无法消解的冲突记录为问题，不抹去其他有效补充。
- 不根据术语差异擅自判定业务对象或渠道互斥。

## 事实与推导边界

- 规则明确程度为「需求明确」「基于规则推导」「待确认」；场景来源为「需求直接描述」「基于规则推导」。推导场景不能创造预期。
- 业务限制可以推导允许或禁止操作的场景，但不能据此规定未明确的交互方式或提示文案。业务上不支持某种操作，先表达该操作不能生效；只有明确规定控件隐藏、禁用或不可选时才写相应界面断言。
- 已明确的恢复能力不能被扩展为未确认的执行起点、配置选择或成功保证。
- 状态变化规则可按有意义的转换方向拆分场景；状态判定节点未明确时记录问题。
- 区分业务预期与验证依据：已知预期行为不代表已知检查方法。可观察结果未知时填 null，不虚构日志字段、页面状态或数据表。
- 不凭惯例补全权限、默认值、历史数据处理、删除范围和同步机制。
- “聚合”“沿用既有规则”等表述只确认已说明的关系，不自动给出权重、公式、精度或取整。实际验证需要这些判定标准时记录局部缺口，保留不依赖它们的状态、范围与准入场景；不把所有实现细节都变成必答问题。
- 检查规则与其引用证据是否一致；概括后的可观察结果也可能超出证据。例如无产物不自动意味着界面显示空值而不是零。无法由有效依据确定的具体表现留为未知，保留已确认业务结果。

## 为测试点与用例展开提供依据

- 本分析同时供测试点设计与完整用例展开使用，但不生成名称、步骤或具体测试数据。原始需求与最新版分析共同供后续阶段核对，分析不替代原文。
- 对独立规则核对四类信息：业务目标及预期、已知触发路径、可观察证据、判定依据。使用现有 trigger、preconditions、expectedBehavior、observableOutcome 表达已知内容；缺失内容进入 openQuestions，不增加字段。
- observableOutcome 描述实际可验证的结果及已知证据来源，不用页面状态代替日志、不用记录存在代替文件可读取、不用转换完成代替格式符合性。已知结果但证据来源未知时如实描述已知部分，并关联问题；完全未知时为 null。
- 在 blockedWork 中注明缺口属于“业务预期”“操作路径”“观察证据”或“判定标准”，说明影响的独立目标及阶段，必要时说明仍可开展的部分。无需固定字符串格式，不另加枚举字段。
- readyForTestPointGeneration 只判断能否生成有依据的名称，不代表用例已可执行。目标明确而发起路径、检查方法或规范待补时可以为 true，blockingReason 仍为 null，通过 relatedQuestionIds 关联具体问题。
- 精确文案缺失不自动阻塞明确的拒绝行为；完整取值集合未知不阻塞已确认取值；操作路径或判定标准缺失则可能阻塞相应完整用例。不能按规则或场景关联了问题就整体阻塞，也不能因可生成名称而关闭问题。
- “本期不考虑/不要求”归范围排除，不改写为必须隐藏或禁止；已发起不等于已完成；先调度不等于先完成；不要擅自解释未定义的类型字段。来源明确的独立系统能力应保留，纯实现分工不自动成为验收目标。
- 覆盖复核在内部建立“已确认判断 → 规则 → 场景或阻塞问题”的对应关系，包含操作与控件中的约束；不把该工作表加入输出。跨流程的已确认差异保留，共用行为不未经依据假定等价。

## 输出约定

输出前读取 [references/output-contract.md](references/output-contract.md) 和固定模板 [assets/output-template.json](assets/output-template.json)。模板定义全部层级的 key，必须严格遵守。

- 最终响应只能是一个可直接解析的标准 JSON 对象。禁止输出注释、Markdown 代码围栏、前言、结语、解释或任何 JSON 以外的内容。
- 所有层级的 key 与模板完全一致，不得新增、删除、改名或翻译。数组可增减条目，同类条目必须保留模板中的全部字段；没有条目时使用 []，不保留占位对象。
- key 为固定英文 camelCase，内容为中文；ID 和产品术语保留必要原文。
- 不输出 `requirementInfo`，不添加需求名称、版本、来源等基本信息块。保留规则中的 `sourceReferences` 用于追溯原文。
- 缺失标量用 null，无已识别条目的集合用 []；不得用“正常”“成功”代替未知预期。空集合不等于确认不存在。
- 多模块仍输出一个五字段对象，在名称、适用对象、入口及出处中标清模块，ID 在本次输出内唯一。
- 无正文时也输出同一结构：功能概况中的 purpose 为 null、其余集合为空，在 openQuestions 中记录需要提供需求正文及其阻塞影响。不得输出 JSON 以外的提问。已有正文时完成可分析部分，将问题写入 openQuestions。

## 输出前核对

- 逐项核对输入中的独立业务判断及条件分支均有规则和场景承接，或关联问题解释阻塞原因；仅引用规则 ID 不算覆盖规则内部的全部判断。
- 组合场景的条件可同时成立，预期符合全部适用规则；场景没有混入未保存、未完成、跨入口或跨管线的隐含假设。
- 场景验证目标有依据；可生成测试点不等于可编写完整可执行用例。
- ID 唯一，引用有效，原文出处真实，不编造章节。
- 未知条件与预期已标记，没有把未说明事项当作确定需求。
- 仅五个约定顶层字段，全部嵌套 key 与模板一致，无最终测试用例名称或需求元信息。
- 输出可被标准 JSON 解析，只有一个对象，没有注释、尾逗号、代码围栏或额外文字。
