# 问题类型与严重度

## 类型

| 类型 | 含义 | 典型例子 |
| --- | --- | --- |
| `conflict` | 原文内部或跨来源互相矛盾 | PRD 说“库存不足仍可提交”，接口说明说“库存不足返回 400” |
| `ambiguity` | 同一句话可被理解为多种行为 | “积分不足时按可用积分兑换”不知道是部分兑换还是拒绝 |
| `missing` | 缺少影响行为、条件或结果的关键规则 | 没写导出任务失败后是否自动重试 |
| `weak_ac` | 有验收标准，但无法判定通过/失败 | “页面展示要友好” |
| `untestable` | 没有可观察的失败条件或判定依据 | “系统应尽量快”且没有时限或观察点 |
| `inconsistency` | 术语、状态、字段、流程前后不一致 | 同一字段在列表叫“订单号”，详情叫“单号” |
| `input_gap` | 缺少材料类别、章节、表格或图片无法识读 | 只有截图没有接口说明，截图中的字段看不清 |

## 严重度

| 严重度 | 定义 | 处理建议 |
| --- | --- | --- |
| `blocker` | 继续做必然返工，或根本无法设计正确的测试；必须先解决 | 必须给 `failureMode`，至少一条非空证据 |
| `major` | 很可能导致实现或测试偏差，需要需求方确认 | 至少一条非空证据 |
| `minor` | 表述、清晰度或低频场景问题，不阻断主流程 | 证据可选，仍建议引用原句 |

严重度不是“问题数量”的评分，也不使用 0–100 分、RPN 或红绿灯。

## 失败模式

| failureMode | 含义 |
| --- | --- |
| `misinterpret` | 实现方或测试方会理解成另一种行为 |
| `missed_rule` | 某个业务规则会被漏实现或漏测 |
| `no_oracle` | 没有可观察的判定依据，无法判断通过/失败 |
| `conflict_escape` | 冲突不会被发现，会漏到实现或测试阶段 |

`blocker` 必须填写 `failureMode`；`major` / `minor` 可选。选择最接近的一种，不要为了填字段编造。
