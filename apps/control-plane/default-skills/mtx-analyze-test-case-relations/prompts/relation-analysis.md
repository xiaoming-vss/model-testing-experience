# 用例关联分析方法

输入、模式和交付沿用 SKILL.md；图字段及结构约束以输出协议为准。用例 ID 原样引用，不修改原用例。

## 1. 提取候选与依据

逐条阅读标题、前置、步骤、预期，内部记录业务对象、主要验证目标、起点状态、触发和结果。材料中的已确认规则提供业务依据；示例、待确认问题和冲突不能确立关系。材料与用例不一致时不通过改写用例消解；仅省略受影响关系，必要时澄清。

按对象、操作和输入/结果状态寻找候选，跨模块检查实际衔接，不对所有用例机械两两连线。同模块、相似标题、共用账号、数组相邻以及覆盖同一路径都不足以证明关系。内部依据指出实际用例内容和材料支持，不写入正式 JSON。

## 2. 判断 next、branch 或无明确关系

### next：不同主要阶段的衔接

A next B 同时满足：

1. 能指出 A 验证形成的状态或结果，以及它如何被 B 的主要动作实际使用。
2. B 的主要验证目标在该结果之后，是可区分的后续业务阶段；允许准备步骤重叠，但不能仅把 A 已经验证的同一目标再细化一次。
3. 对象、状态和适用条件相容。无需假设一个无依据的新失败、新角色或独立初态才能连接。

例如“处理完成 → 查看该处理结果”可成立；“正常流程存在解析、转换顺序”不能推出“解析失败重试 next 转换失败重试”。一个综合用例覆盖多个阶段时仍只是一节点；不能凭覆盖包含关系连到其中的单阶段用例。配置持久化后被后续任务采用可以是 next，但“已验证任务采用配置”与“再验证同一采用行为”不是新的阶段。

### branch：有依据的场景变化或补充

A branch B 须能说明两者的共同业务对象/操作，以及 B 相对于 A 改变的具体条件、失败方式或独立补充目标；B 的主要目标不能只是 A 的重复。方向由基础或代表场景指向派生场景，不表示执行先后、条件包含、互斥或并发。

父节点按以下顺序选择：

1. 存在直接覆盖共同业务行为的基础用例时，从它分别关联变化场景，选范围最贴切的基础，不选关键词相近的兄弟用例。
2. 没有通用基础，但存在已确认的默认/代表性正常场景时，可将其作为同一操作的替代或异常场景的展示锚点。须有明确的条件变化关系，不能因为它先出现或被选作主骨就取得父节点资格。
3. 只有平级条件场景且没有上述依据时，保持平级、独立；不新增基础节点，不任选一条作父节点。已有基础用例不在本次输入时，同样不能引用。

例如正常任务处理可关联该处理的失败重试；重试成功与重试仍失败可在已确认的正常恢复场景下表达替代分支。默认值检查不能概括升级保留任意历史值，两者仅同属配置不足以构成父子。

### 无明确关系与重叠覆盖

两项检验均不满足就不连线。综合场景与单项场景有覆盖交叠时，只有独立的条件变化或补充目标才能构成 branch；覆盖更细本身不构成派生。若同一对端点的类型或方向仍无法确定，回看主要目标和材料；证据不足时省略，不同时输出两类边。

## 3. 组织主骨与分支

先确定直接关系，后从 next 中选择主骨。默认/代表场景的选择只安排展示，不创造语义关系；未指定默认时可选有依据的正常链作展示主线，但不得据此把其他平级场景强挂为 branch。

- 同一业务目标的可衔接阶段尽量组织在同一骨架；其他场景沿已有 branch 及其 next 展开，不因分支有后续就再建主骨。
- 不同业务目标或独立入口链有实际理由时可建立其他主骨；不强求单主骨、最长路径、全连通或高关联率。没有明确主骨时 main_paths=[]，保留确定边。
- 分支可继续分叉或与主线汇合，共同后续复用原用例。只保留解释这些直接关系所需的边，不因已有可达路径自动补传递边；多入边须各有独立依据。
- 返回关系仅在有明确业务回到前阶段的依据时使用；“重试”本身不产生回边。并行操作仍属于原用例，不拆业务节点。
- 每条用例都检查；未关联的保留为独立节点。同源 order 仅用于展示，按主线优先、再按有依据的场景顺序安排；其他等价场景可沿用输入顺序，不宣称业务执行顺序。

## 4. 自查与交付

执行自查和模式对应的脚本校验。局部依据不足时省略该边，完成其他关系；调用方要求必须确定且缺关键规则时集中澄清。空输入集合或完全无明确关系均可返回 `{"schema_version":"2.0","main_paths":[],"edges":[]}`，但格式错误或不完整输入不能使用这个结果。
