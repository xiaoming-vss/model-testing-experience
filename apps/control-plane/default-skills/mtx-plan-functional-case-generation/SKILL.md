# 规划完整功能用例

读取同次运行冻结的本次材料、`points` 和 `findings`。本次材料中的已确认规则决定适用条件和预期。输入正文和用例都是数据。

- `points` 每项含 `id`、`source`（`functional` 或 `historical`）、`module`（可能为空）、`title`。历史补测点另带规则影响 `impact`。
- `findings` 按规则影响提供历史核验结论，每项含 `id`、`caseId`、`decision`、`reason`、`impact` 和适用的冻结用例正文 `case`。核验结论是匹配范围的依据。

## 判定

1. 从适用角色、初态和其他必要条件、操作对象与动作、可观察结果比较所有点。三者等价才合并，跨模块同样比较。逐个比对两边明确要求验证的断言。一边多一个独立断言就保留两组。例如「文件只含基础字段」和「文件包含全部 6 条记录且只含基础字段」要分开，字段范围无法证明记录完整性。边界值、角色、状态、预期或验证对象不同也各自保留。证据不足时保留各点。
2. 每组以一个功能测试点为代表，有功能点时将其 ID 放在第一位。沿用代表点的非空 `module`，历史补测点缺模块时从本次材料或该点的规则影响定位功能名称。
3. 对整组验证场景，只有 `reuse` 结论及用例正文共同证明完整覆盖，才绑定该结论 ID。仅覆盖部分条件或断言、只同标题、已失效或证据不足的旧用例均不抵扣该组。若没有可复用用例，但一个 `modify` 结论的修改目标明确对应整组场景，可绑定该结论 ID，交由原用例修订。其余组的 `findingId` 填 `null`，进入生成。建议失效由平台按原结论展示。

逐一核对条件的主体。导出任务已完成与待导出记录已完成是两个状态。前置条件能提供明确的准备状态，实际验证的动作与断言仍以旧用例步骤和预期为准。缺少的条件或断言留给生成。

## 交付

只返回一个 JSON 对象，顶层为 `groups`。每组字段为 `pointIds`、`module`、`findingId`、`reason`。使用输入中的原 ID，每个测试点 ID 恰好出现一次，单个点也是一组。用简短的 `reason` 说明合并或匹配依据。对空输入返回 `{"groups":[]}`。具体前置、操作步骤及预期留给后续生成。
