# 生成前预检

先读取输入 contentBlocks、extractedFacts 和明确答复，保存一个简短的 `understanding-preflight.json`。仅用于当前工作目录，不添加输出协议字段，不把全文复制进去。

记录三部分：

- `decisions`：每项用户答复的 sourceId、locator、原话短摘录、原话实际确认的结论、提取稿是否额外推断。
- `openIssues`：影响业务判断或测试覆盖的具体缺口/矛盾、对应定位、最终需标为 unconfirmed 或 conflicting 的具体判定。没有缺口才为空。
- `stages`：正常路径的业务任务/人工提交顺序，每阶段完成信号和下一阶段准入；另列可选查看动作及重试触发。

## 来源判定

extractedFacts 的 value 是提取阶段的总结，不等同于 sourceReferences.excerpt 的原话。核对两者的逻辑范围；contentBlocks 中的正文、用户原话和可识别图示共同提供依据。引用多个证据 ID 不会自动补足缺失前提。

例如用户只确认“每秒 30 帧”，提取稿扩成“帧号自 1 起”，只承接帧率；截图 1–360 是该示例范围，不自行推广编号起点。用户说“没有运行任务就失败”，而正常路径存在全部成功且无运行任务，须标出适用范围缺口；不能因为提取稿标为 confirmed 就直接使用。两个声称完整的状态清单不同，在范围未明确前保留差异，不能直接取并集或自行划成筛选与流转口径。这些例子是逻辑检查方法，不是要求所有输入都产生这些问题。

部分明确答复仍可用：仅把超出原话或发生冲突的判定列入 openIssues。未知选项全集若影响枚举覆盖，保留局部问题；已有选项可继续形成确定规则。

## 流程判定

按“系统做什么/人提交什么”列业务阶段，再定位模块操作。页面打开、预览或查看进度是观察能力，不能作为业务任务启动的先决条件。恢复与历史重新处理接入真实执行阶段；逐阶段检查没有因复用而漏掉处理或核验。一个完成信号不足以同时表示前一阶段准入、当前完成和下一阶段完成。

绘制出边前，将每条拟引用规则读成一句判断：如果它包含互斥动作或多个结果，改用带证据的 condition 指定该次转换；例如“保存或提交”不是推进条件，“点击提交且满足全部核验完成”才是。对重试机制，分清已确认的失败条件、业务重试动作与未知按钮/入口；不可把初次提交方式自动作为重试方式。异常后无可用产物但恢复/最终状态未知时，只保留处理事实和节点问题，不生成 null 终止边。

生成最终 JSON 后重新读取本记录：逐项找到对应确认、问题/事实状态和阶段节点。若记录与输出不一致，修正输出；若有明确证据解决预检问题，记录依据再移除，不凭模型“已理解”消除疑问。
