# 需求理解与确认

读取 [输出结构](references/output_structure.md)、[schema](references/output-schema.json) 和 [输入与来源](references/source_usage.md)。输出完整 requirement_understanding 2.0 JSON，覆盖本次材料中的业务要求，不生成测试点或完整用例。

输入为完整 document_extraction、显式提供的补充材料和用户答复；修订另读取当前完整需求理解。只使用本次输入，不依赖其他运行或历史会话补齐事实。

## 1. 核对来源后提取事实

先执行[来源与流程预检](references/preflight.md)，把预检结果保存到工作目录的 `understanding-preflight.json`，再生成最终产物。该文件是内部工作记录，不作为返回结果。材料提取是另一阶段的解释稿，其 confirmed 标签不是业务裁决；发生内部矛盾或解释超过原话时，必须重新判定具体事实。

按业务对象、条件、行为和结果拆分要求，登记 sources 与集中 evidence。逐项把用户确认落实到受影响内容，复用证据 ID。每个断言的含义限于其证据支持范围；示例和截图保留实际适用范围。

证据明确且无争议的事实为 confirmed（可省略状态）；依据不足为 unconfirmed，相互冲突为 conflicting。争议判定本身须显式标记并关联问题，用户原话可留在证据或问题 answer 中。不能将同一争议判定同时写成 confirmed 和“尚未明确”。只将影响理解或测试的剩余缺口写入 questions，局部缺口不否定其他明确事实。

完成条件：预检记录已保存，每项确认对应原话和实际支持的结论，争议判定已定位到具体事实；这些争议必须落实为最终 questions 及关联事实状态。

## 2. 定义规则与操作

businessRules 是独立规则的唯一完整定义。比较对象、条件、行为和结果，合并等价表达，保留不同条件和结果；不要另建复述规则集合的汇总规则。

模块按业务职责组织，操作按独立目标或状态转换组织，同一目标下按钮通常保留为控件或步骤。操作通过 ruleIds 引用规则；steps 说明实际动作，interaction 保留控件、选项完整性、默认值、联动、独有反馈和观察位置。已有规则中的完整判据不再复制到操作前提、控件含义和反馈中。

purpose、goal、步骤和 note 的职责或路径可用简短字符串；涉及争议、独立约束或问题时使用事实对象。省略无内容的可选字段，不省略明确的未知或不适用结论；必填结构按 Schema 保留。

完成条件：每项独立要求有一个完整定义，操作中保留了实际使用与观察所需的独有信息。核对来源中的主体、作用范围、例外、阈值与命名对象仍在对应规则中；“沿用现有规则”“保持一致”等概括不能替代已明确的角色权限、对象范围或例外。

## 3. 组织流程

主流程按实际阶段推进建立一次。节点引用模块和操作，出边表达当前动作完成及下一阶段准入；同一操作含保存与提交时，明确哪种动作才推进。conditionRuleIds 只引用本身就是单一放行判据的规则，多 ID 表示同时满足。规则若同时描述保存与提交、成功与失败或多个行为，整条规则 ID 不能作为某一分支的条件；改用 condition 写清该边的实际动作和适用条件，并引用同一证据。背景条件不能代替推进条件。若下一节点是“执行某任务”，入边只能要求该任务的启动前提；该任务成功/产物生成应放在它的出边，不能要求目标任务先成功才能进入执行节点。

失败与重试优先作为同一流程内的分支，成功后接回已有节点；材料只确认“失败可重试”时，保留业务动作“重试该任务”，不推断必须再次点击初次提交按钮或修改核验内容；历史重新流转复用既有节点，历史专属动作单独表达。只有路径确实不同才另建流程，不能为了分类复制主流程或省略必经阶段。可选查看留在操作中，需要表达独立浏览顺序时才建浏览流程。

stepId 只能引用同一流程内节点。stepId=null 表示真正结束，不能表达“转入另一流程”；nextSteps=[] 表示后继尚未记录，不能宣称恢复路径完整。恢复去向或异常后的状态缺乏依据时，在当前节点关联问题并保留已知处理结果；暂不绘制去向未知的边，不能用 null 把未知后继变成终态。已确认无产物、不进入下游，不自动等于整个业务不可再处理。

完成条件：用预检中的阶段序列核对主路径；每个节点必须执行推进动作或等待真实业务任务完成。查看/预览/跟踪进度的 UI 操作不能代替任务执行节点，也不能与系统处理合成一个需要先查看再处理的操作；系统任务和可选观察分别定义，主路径只引用前者。历史重新处理从清洗任务开始复用正常路径，不直接跳进核验。重试边必须同时满足对应失败状态和重试触发，不把等待状态或笼统三态规则作为重试条件。

## 4. 复核并返回

执行[质量复核](references/quality-review.md)，并逐项对照预检中发现的争议和阶段序列。预检争议只能凭输入中的明确依据解决，不能在最终 JSON 中无声消失。修正材料足以判定的问题，其余保留局部问题；工作目录中只维护一份候选 `requirement-understanding.json`。按[覆盖复核](references/quality-review.md#独立要求覆盖)保存内部覆盖记录，完成后对这份候选执行 `python scripts/validate_output.py <候选文件>`（脚本路径相对本 skill 目录）；一次处理报告的全部格式问题，脚本也检查无后继且无问题的流程空壳；不能通过添加无实际缺口的问题来绕过检查。通过后核对 ID 和关联，仅原样返回该文件的完整 JSON。定稿后不再另写 final/compact 等简版，也不在返回时重新概括字段；需修改时在原候选上修改并重做覆盖与校验。校验过程只打印错误路径和摘要，不反复打印整份文档。内部对照表和复核过程不增加输出字段。

修订保留稳定 ID 和未受影响内容。明确答复先落实到业务事实、规则、操作或交互，再删除已解决问题及引用；不能只新增一个来源或 relatedQuestionIds 来表示已回答。部分答复仅缩小问题的范围和影响。旧问题只能因答复落实、合并到仍保留的问题或明确范围排除而移除，精简和重新生成不是解决依据。历史 resolved 答复先落实正文再移除。全部缺口解决时 questions=[]。

业务模块尚无法识别时 modules=[]，用 kind=requirement、id=requirement 记录整体范围问题，不编造占位模块。
