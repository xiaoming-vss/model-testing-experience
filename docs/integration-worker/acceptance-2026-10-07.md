## 后续核对放行及上游问题复核

上述表格记录首次恢复隔离检查时的状态。随后在同一自建环境升级恢复目标至 `20261007_0032`，使用当前项目所有者自己的授权，对 Bug #1 的既有映射/文件，以及旧快照中的 queued 任务实际创建的 Bug #2 执行只读核对。原任务取消，原操作与回执保留；全局放行成功，配置开关仍关闭。随后只在独立恢复验收配置中开启执行，提交新手动任务验证恢复后的工作流。

这轮检查发现禅道上游问题：创建 Bug #2 后，API 和数据库中原属于 Bug #1 的两个图片文件都被重新关联到 #2。本次 22.6 源码的 API router 将每次请求的编辑器 uid 固定为 `1`，同一 Token 会话复用图片 album，后续创建会更新旧图片的 objectID。Worker 的归属校验因此正确拒绝继续操作。这意味着首次成功推送的证明不能支持“后续创建后原图片仍正确关联”的结论，原版 22.6 尚未通过该项部署验收。

仅对本次自建禅道应用 [uid 修复](../../deploy/zentao-mcp/zentao-22.6-api-form-uid.patch)，并将明确创建的两个夹具文件通过条件更新恢复到原 Bug。API 元信息一度仍返回旧归属；重启自建 Apache 后重新读取。创建 #3、#4 用于修复验证；最终创建 #4 后，API 和新的数据库查询均确认两个文件仍属于 #1。此次记录包含上游源码修复与夹具数据修复，不能作为未经修改的禅道 22.6 的通过证明；没有修改用户既有禅道或 MCP 容器。

同时确认，正文中的图片可不出现在 Bug 的 files 列表里。MCP schema 增补 `get_files_fileID`，Worker 和恢复核对根据已确认编号只读查询、严格验证归属和字节，并从已观察的正文提取原生路径。修复没有放宽跨 Bug 文件校验。

首轮放行后新任务暴露两项本地问题：恢复核对重写等价正文的字节，破坏原操作摘要；只读 no-op 步骤复用关联 operation ID，被后续任务误当作未知写入恢复。修复后保留原正文证明，为新的只读步骤分配独立身份，并排除已确认 no-op 的未知恢复。失败任务继续保留，重试使用新的手动请求编号，未重放恢复旧任务。

## 自建部署的项目范围与排空演练
