# 功能测试需求分析产物

功能测试生成链的需求分析供人工审核，并作为同一份内容传递给测试点和完整用例生成；不生成单独的下游摘要。

测试点生成先产出草稿，再使用同一份需求、分析和用户修订要求分别核对条件与依据、覆盖与拆分；条件核对每批最多十条，发现问题时先修订，再进行两项核对。最多修订三轮，只有通过两项核对的最终结果进入人工审核和后续阶段。复核输出不作为业务产物，复核失败、引用不存在的测试点或修订后仍有问题时，当前尝试失败，不静默回退草稿。该流程至少增加两次模型调用，测试点较多时按批增加；每轮修订还会增加修订和再次核对的调用。

新规则格式保留 `ruleId`、`category`、`name`、`confirmationStatus`、`applicableObject`、`preconditions`、`trigger`、`expectedBehavior`、`sourceReferences` 和 `relatedQuestionIds`。业务预期、禁止或跳过要求，以及有依据且有独立价值的观察和判定信息均由 `expectedBehavior` 承接。缺少业务预期、操作路径、观察证据或判定标准时，使用现有 `openQuestions` 表达，不因缺少检查方法推定业务预期未知。

旧规则中的 `prohibitedOrSkippedBehavior` 和 `observableOutcome` 继续兼容读取和展示；新格式不包含这两个字段。历史内容不迁移，已有字段及其语义不被重新解释。顶层五字段及其余引用、状态和类型约束不变，Worker 逐条校验规则并保留实际格式。结构化需求中的证据 ID 仅在当前输入内可唯一定位时可作为简短来源引用。

技能由控制面默认技能库维护，Worker 在每次执行时按阶段获取；修改本地源码或本文不会自动更新已发布技能。前后端契约与技能需要协调发布：先部署兼容新旧规则的 Worker 和 Studio，再切换默认技能。旧 Worker 无法校验新格式，切换技能前应确认执行该任务的 Worker 均已更新。
