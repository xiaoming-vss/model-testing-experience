# 按模块并发生成完整用例

完整用例由程序按测试点的 `module` 分组派发，单次运行固定最多同时生成 2 个模块。每个模块使用独立 Agent 实例、会话和 `module-runs/<dispatch>/<index>/` 工作目录，复制本次已下载的技能，在独立目录内处理材料和临时文件。会话中只有本模块的请求及格式修复历史，不携带其他模块或上游生成会话历史。Pi 模块任务调用普通 `run`，不加载自主 subagent 扩展，避免嵌套并发；测试点阶段保留自主委派能力。Nanobot 通过同一 Agent 门面执行。并发上限按运行计算，多个 Worker 任务可能同时各运行 2 个模块。

模块输入仍包含冻结需求材料、需求分析、本模块测试点及相关审查意见、覆盖缺口。继续优化按模块传入已有候选和修订说明，附件图片直接传给模块 Agent。正常生成、阶段恢复、完整链及继续优化共用同一调度入口。

每个模块执行既有格式、Schema 和业务校验。所有模块完成后按输入模块顺序合并，继续校验跨模块重复；有冲突时只在对应模块会话中进行最多两次修复，复用已生成结果，其他模块不重新生成。最后统一分配或认回用例编号。完成回调不携带部分用例，任一模块失败均不发布部分候选。

模块失败会取消其他在途协程，等待 Agent 退出后再回传失败；外层取消同样回收全部模块。Pi 仍通过既有 `finally` 关闭子进程组，Worker 的独立心跳线程及进程级退出规则保持不变。进度请求在线程中串行提交，不阻塞模型事件循环；进度发送失败沿用 Worker 现有处理，不重新调用模型。

## 进度协议

沿用 Worker `resultSummaryJson`，新增可选 `moduleGeneration` 对象：

- `sequence`：本次执行内递增的完整快照序号。
- `concurrency`：模块并发上限，当前为 2。
- `status`：`running`、`merging`、`completed`、`failed`、`canceled`。
- `modules[]`：每项为 `id`、`module`、`status`、`elapsedMs`、`caseCount`、`repairAttempt`。
- 模块状态：`queued`、`running`、`repairing`、`completed`、`failed`、`canceled`；`completed` 代表该模块已生成并校验，整个阶段仍须等待合并成功。

快照只包含模块名称、状态、耗时和计数，不包含提示词、凭据、原始错误响应或未完成用例。模块耗时在状态更新时计算，不代表实时计时器。控制面在原有任务身份、租约和阶段事务校验后，严格校验此结构，保存到本次 attempt 的 `output_context_json.moduleGeneration`；较旧序号不覆盖新快照，普通心跳和旧 Worker 进度不清空它。最终成功保留统计；失败或取消后查询会将仍在运行、排队的模块投影为已停止。新 attempt 不继承旧进度。

生成链阶段响应增加可选 `moduleGeneration`，额外补充控制面确定的 `attemptId`。未生成过模块进度的历史数据及旧 Worker 返回 `null`，Studio 保留原有加载提示。此信息不进入后续生成输入或已审核版本内容。复用现有 JSON 字段，无数据库迁移。

## 页面

完整用例节点运行时显示已完成模块数；进入阶段阅读区后显示子 Agent 列表，包括排队、生成、修复、完成、失败、停止状态，完成项显示用例数量和耗时。进度复用运行中每 5 秒的轮询，合并阶段单独显示“正在合并并校验完整用例”。失败不会将已有模块产物误报为完整成功。
