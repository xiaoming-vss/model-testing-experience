## 4. 来源、事实与问题

两份产物都包含独立的 sources 列表：来源名称、类型、稳定位置和版本；没有材料版本时填 null。短时效签名 URL、凭据和机器私有临时路径不进入正式来源位置。

材料提取事实使用 `value`、`confirmationStatus`、`sourceReferences`、`relatedQuestionIds`；需求理解事实使用 `evidenceIds` 引用集中证据表，可省略已确认状态与空的可选字段。引用包含来源 ID、真实定位和可选简短摘录。这样可以分别标记控件名称、选项、默认值、触发、反馈等事实，不用一个“模块已确认”覆盖所有细节。

| confirmationStatus | 语义 |
| --- | --- |
| confirmed | 有明确且可追溯依据的事实；可以来自明确需求或用户明确答复，不代表在真实产品中实测过 |
| unconfirmed | 信息未提供、尚未确认或只掌握一部分；允许保留已知部分并关联问题 |
| conflicting | 依据存在冲突；保留相关来源和问题，等待来源优先级或用户答复 |
| example | 示例、占位或演示信息；下游不能把它当成当前产品规则 |
| not_applicable | 有依据明确不适用；value 为 null，同时保留范围依据 |

原始依据与用户补充分别通过 source.type 的 document/text/prototype/screenshot/design、user_confirmation 表达。图片中的静态展示可以证明可见文字与布局，不能独自证明自动刷新、条件保留等动态行为。

confirmed/example/not_applicable 事实至少有一条来源；conflicting 事实须关联来源和未解决问题。完全未知的 value=null 使用 unconfirmed。只有与当前目标执行或判定相关的缺口才形成问题，不机械地把每个 null 变成必答项。

questions 仅保存 status=open 的剩余缺口。明确答复先合并到对应提取事实或需求理解正文，更新确认状态和来源，再删除已解决问题及整个产物内指向它的 relatedQuestionIds。部分解决时问题文案、affectedRefs 和 impacts 收窄到剩余缺口，已确认业务结论以事实、操作、规则或交互正文为准；answer 仅允许理解剩余缺口仍必需的部分信息。全部解决时 questions=[]，不保留 resolved 条目或单独的问答历史。解析通过、重写文案、整体审核通过都不能自行关闭未答复问题。

生成、保存、批准和导入边界使用只允许 open 的新契约；历史产物仅作为修订或已审核上游输入读取，可包含此前的 resolved 答复，但必须有明确来源。AI 修订应先将其合并到当前业务内容，再返回符合新契约的完整产物。输入读取兼容不改变已审核上游内容，不用于放宽当前阶段的新输出校验。

业务内容 ID 用于引用与修订，不是数据库 ID、执行环境真实记录 ID或用例编号。修订尽量保留已有来源、模块、操作、规则及问题 ID；删除或新增条目时同步检查引用。

## 5. 第一阶段结构

顶层固定为 schemaVersion、artifactType、documentTitle、sources、contentBlocks、extractedFacts、questions。

- contentBlocks 用 parentId 和顺序表达材料层级，类型为 section/paragraph/list/table/image。
- 每块分别保存正文、列表项、结构化表格或图片理解；不将整篇 Markdown 放入单一文本字段。
- 表格用行列位置、单元格内容及合并跨度表达，保留有业务意义的表头与选项；不可辨识的单元格为 null，并关联问题。整张表不可识别时保留表格块，行列数为 null、cells 为 []，不伪造占位内容。
- 图片保存可见文字、可靠的业务含义和原材料定位；parseStatus 区分完整、部分和不可读取。
- extractedFacts 从这些块中提取必要事实，关联原块；类型覆盖范围、角色、入口、操作、控件、选项、默认值、生效方式、联动、结果、分页、排序、校验及业务规则。
- 不可读取的业务图片保留对应块与问题；装饰图可以不展开，不伪造业务事实。

## 6. 第二阶段结构与 UI 归属

顶层固定为 schemaVersion、artifactType、title、sources、evidence、functionalOverview、businessFlows、modules、businessRules、questions。

| 内容 | 位置与关系 |
| --- | --- |
| 功能范围、角色、明确排除 | functionalOverview |
| 跨模块主流程和分支 | businessFlows；节点引用 moduleId/operationId，条件和后继明确记录 |
| 模块目的 | modules[].purpose |
| 模块入口、适用角色、进入条件 | modules[].entryPoints |
| 操作目的、前提与步骤 | modules[].operations |
| 操作控件、选项与含义、输入规则、默认值 | operations[].interaction.controls |
| 生效动作、初始展示、条件联动 | interaction.trigger / initialState / dependencies |
| 观察位置、字段、记录标识、结果范围和空结果展示 | interaction.results |
| 分页、排序、校验及反馈 | interaction.pagination / sorting / validationAndFeedback |
| 模块完整使用顺序 | modules[].userVisibleFlow；引用操作，简短衔接说明避免重写交互细节 |
| 可独立识别的业务规则 | businessRules；通过 moduleIds、operationIds 和操作 ruleIds 关联 |
| 缺口、冲突及答复 | questions；操作和事实引用问题 ID，界面按模块汇总 |

控件 options 区分 items 和 completeness（complete/partial/unknown/not_applicable），避免把已知两个选项误认为完整列表。completeness 自身也有来源和确认状态。控件默认值支持标量与标量数组，满足单选、多选、数字及布尔值表达。

模块范围尚无法识别时 modules=[]，保留 kind=requirement、id=requirement 的整体范围问题，不编造占位模块；未知不等于解析失败。

操作可为页面操作或系统业务动作，没有 UI 的操作仍可以记录前提、步骤与系统响应。interaction 中未适用或未知的属性按事实状态表达，不编造控件或按钮。精确文案未知但业务动作明确时，保留已知动作；不因文案缺失丢弃可执行路径。

businessFlows 的节点只串联操作；操作内步骤保存具体动作与响应。规则保存可独立验收的要求，执行路径细节不自动成为独立测试点。

## 7. 输入、修订与执行

原文件身份随运行快照保存；新任务的提取与提取重试若发现文件已经替换，明确提示发起新运行，避免悄悄读取另一个版本。第二阶段继续使用已确认提取 JSON，不因原文件替换而丢失已保存内容。

阶段 2 初次输入必须显式包含已校验的完整文档提取 JSON、已提供的原始补充材料与用户确认补充。仅提供临时文件路径、自然语言摘要或旧流程稿不足以替代该结构化输入。必要图片依据未完整提取时，提供原材料或保留可追溯问题。

校验顺序：标准 JSON 语法 → 版本/产物类型 → JSON Schema → 引用与业务状态一致性。异常输出进入失败或已有重试流程；不得以清洗后的展示文本代替失败产物。未确认问题可以存在于合法产物中，是否阻塞后续目标按问题影响判断。

Schema 之外还需要语义校验：ID 唯一；parentId 无环且指向已有块；来源、问题、模块、操作、规则、流程引用存在；流程节点的 operationId 属于 moduleId；后继属于当前流程；表格位置/跨度合法；表格覆盖不冲突；示例来源不能生成 confirmed 事实；conflicting 事实关联 open 问题；问题 answer 不能构成无依据的确认。

新任务使用独立的 workflowVersion=2 标识阶段布局；产物 schemaVersion 不替代工作流版本。唯一执行阶段为 extracting_text 和 feature_understanding；通用运行结束标记 completed 仍用于已完成运行的保存、最终审核和修订，不构成第三个阶段。执行保留材料人工审核，修订、重试和技能获取采用同一布局。
