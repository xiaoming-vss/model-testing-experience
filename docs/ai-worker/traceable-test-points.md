# 可追溯测试点生成

功能测试链的测试点阶段消费同一次运行冻结的已审核材料整理（`readable_requirement_material` 0.2）和已审核测试范围风险分析（`test_scope_impact_risk` 1.0）。Worker 获取 `mtx-generate-traceable-test-points`，生成 `traceable_test_points` 1.0；测试点按功能项、场景分类并引用材料块和相关范围分析对象，`coverageGaps` 保存无法形成确定预期的覆盖缺口。

Worker 将初稿交给独立会话，分别检查依据、整体覆盖与拆分、缺口；Pi 审查者可根据 Skill 自主拆分和委派。依据审查每批最多 10 点，全部批次完成后汇总；其他后端沿用相同分批规则。引用不合法时失败，最多三次修订。首次审查及后续增量复核均无未解决问题才写 `reviewStatus=independent_reviewed`；修订用尽仍有问题时写 `independent_review_failed` 和 `reviewIssues`，候选供人工核查。格式校验与模型审查不证明业务语义或覆盖完整。人工修改后页面将审查状态重置为 `self_review_only`，仍须人工审核。

## 初稿按测试对象并发生成

首次生成或重新生成测试点时，程序直接读取已审核范围分析的 `testObjects`，按原顺序均匀拆为最多 3 个对象组，追加 1 个“跨组与公共规则”组。单次运行最多同时执行 2 个分组；不足 2 个测试对象时保留原单 Agent 路径，不额外创建分组或规划模型调用。分组是任务边界，不是业务模块或范围排除，未确认对象也保留在计划中，由模型根据材料判断可形成测试点还是覆盖缺口。

每组读取完整冻结材料及范围分析，使用独立 Agent、会话和 `module-runs/points-<dispatch>/<index>/` 工作目录，直接生成分派范围，不加载递归委派扩展。条目的 `testObjectIds` 非空且都归属同一对象组时由该组负责；跨不同组或无对象引用的条目归公共组。程序校验真实引用与分组归属，越界输出进入本组有上限的修复。Skill 说明不得通过删除或伪造引用改变归属，明确交互写测试点，真实业务未知才写缺口。

所有组成功后按分组顺序合并，仅去掉除 ID 外内容完全相同的条目（引用数组顺序不影响相同判断），统一分配 `tp-*` 和 `gap-*` ID。不同依据、不同预期及语义相似的条目保留给全局审查，不按标题相似自动合并。上游来源 ID 原样保留；合并结果仍执行完整结构和引用校验，然后执行首次全量依据、覆盖与拆分、缺口审查。

后续审查修订复用合并候选及稳定 ID，保留未受影响内容，按下节增量复核，不重新生成所有组。用户对已有候选“继续优化”时保留原单 Agent 修订路径，避免重新分组和重编号改变已有身份。分组或必要审查失败时取消并等待其余在途协程退出，不发布部分结果；外层取消同样清理各组。

## 测试点生成进度

复用完整用例的 `moduleGeneration` 快照，新增可选 `stage`（旧数据缺省为 `detailed_cases`，测试点为 `case_names`）、`reviewRound`、`issueCount` 和条目 `pointCount`。测试点的阶段状态除 `running/merging/completed/failed/canceled` 外增加 `reviewing`、`revising`、`review_failed`；这三个状态只用于测试点，且各组初稿必须已完成。控制面按同一 attempt 保存，旧序号和其他阶段的快照不能覆盖当前进度。

页面区分“初稿分组已完成”和全局审查、后续增量复核；各组数量标为初稿测试点数，不代表修订后的最终数量。独立审查仍有问题时显示待人工核查，不把子任务完成误报为整阶段通过。进度复用运行中每 5 秒轮询，旧 Worker 和不足两对象的单 Agent 路径继续显示原加载提示。

## 修订后的增量复核

首次完整审查后，Worker 比较修订前后的测试点及覆盖缺口，按 ID 识别新增、修改和删除。依据复核只处理新增、修改及仍有未解决意见的测试点；覆盖和缺口复核只处理变更、未解决意见及直接相关条目。相关范围由变更前后的模块、六类来源引用以及未解决意见的目标和引用确定；保留旧引用以检查移动、删除造成的覆盖丢失。引用按字段区分，避免不同集合的同名 ID 被误认为关联。

增量审查继续接收完整冻结材料和范围分析，但不会重新审查未受影响的全部候选。Worker 在提示词中明确本轮范围，覆盖/缺口审查接收变更前后内容及相关候选；局部数组中未出现某个条目不代表遗漏。删除造成的新遗漏使用 `targetType=missing`，不允许引用已删除或本次范围外的目标。全量候选仍执行结构和来源引用校验。

后续修订和复核只携带上一轮尚未解决的意见，已解决意见不再不断累积。若修订后测试点及缺口没有实际变化（仅调整条目顺序也算无变化），Worker 提前停止并保留意见，标记 `independent_review_failed`，供人工处理。增量策略依赖模型对相关范围的判断，不构成业务覆盖完整性的证明。

控制面在候选回传、编辑和审批时按冻结的材料及范围分析校验新结构和引用。详细用例生成按功能项将新测试点原格式分批传给详细用例生成，保留来源引用、覆盖缺口及相关审查问题；正式资产仍通过既有审核和导入流程产生。本阶段不继续消费旧的 `categories` 测试点产物。


## 审查并发与耗时

`config/platform.toml` 的 `[ai_worker.worker]` 可设置 `traceable_review_concurrency`（单次运行）和 `traceable_review_global_concurrency`（单个 Worker 进程内所有测试点审查共享），默认均为 4，允许 1–32。两项约束审查主 Agent 的并发；每个 Pi 审查主 Agent 还可同时启动最多 2 个子 Agent，因此不是所有模型请求的全局并发上限。通过 `python3 scripts/manage.py configure` 生成配置，重启 Worker 后对新运行生效；多进程或多台 Worker 的上限分别计算。调大前应考虑模型服务的限流和费用。首次审查与增量复核均使用各自独立 Agent 实例与会话，沿用既有并发额度及最多三次修订的上限。

Worker 日志以 `traceable_review_call` 记录任务、运行、调用阶段、状态、耗时毫秒和输入字符数，`traceable_review_round` 记录每轮测试点数、审查调用数、去重后意见数、是否增量及三类审查的实际条目数；无变化停止时记录 `traceable_review_stopped`。不记录提示词或模型输出。调用耗时不包含等待共享并发额度的时间，也不包含模型调用以外的轮次开销。
