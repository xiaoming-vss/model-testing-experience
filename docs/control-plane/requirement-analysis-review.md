# 需求分析运行的审核与拒绝

2026-10-07，用户明确确认已拒绝的需求分析运行作为只读终态：只能查看产物或删除运行记录；重新生成发起新运行。该规则适用于材料提取与需求理解的审核，不调整其他任务类型。

仅待审核产物可以执行审核。最终需求理解被拒绝后，生成状态为 success、阶段执行状态为 completed，审核状态为 rejected：生成完成与审核通过是两种状态。拒绝结果不再占用 waiting_review。材料阶段拒绝仍按原有取消流程结束。

保存、审核及 AI 修订入口在状态变更前统一拒绝已拒绝运行，返回既有400错误信封，提示仅支持查看或删除并重新运行任务。重试仍只允许失败执行且审核状态为 pending；导入仍要求 approved。已有已批准产物的编辑及重新审核规则保留。

Studio 的行内审核、产物弹框、原始 JSON、优化及重试入口使用对应状态条件；拒绝结果的弹框为只读，顶部也不提供导入。查看较早的运行时，弹框绑定运行 ID，避免切换选择时立即关闭。

验证覆盖服务层无状态改写/无入队、保存/审核/修订/重试/导入HTTP拒绝、待审核最终拒绝收尾、只读JSON、运行历史入口和首次打开旧产物。没有数据库结构或协议字段变更；响应组装中的临时审核重置标记不映射为数据库列。

## 需求理解精简契约（2026-10-16）

需求理解的 Worker 回传、人工保存、最终审核、导入及正式需求内容读取仅接受 2.0，拒绝旧版需求理解。材料提取维持 1.0，工作流版本维持 2。2.0 的集中证据与流程规则引用先通过 Schema，再直接执行来源、状态、模块/操作/规则和问题校验；持久化及下游快照仍保留精简对象。未知版本、失效证据、重复证据 ID、示例伪确认、失效条件规则和未关联问题的冲突均拒绝。

不改写或删除已有运行和正式需求，不改变审核与导入的独立性；旧版结构不再提供读取、审核、修订和导入兼容，需要重新生成符合当前契约的结果。新版 Worker 新生成和修订使用 2.0。协议见 [AI Worker 精简契约说明](../ai-worker/requirement-analysis-two-stage-design.md#2026-10-16-需求理解精简契约-20)。

## 需求理解版本取代写回需求（2026-11-03）

原 `POST /v1/requirement-analysis-runs/{runId}/import-to-requirement` 已退役，不再把审核通过的需求理解写回 `requirements.document_content`；该接口与 Studio 导入入口一并移除，需求理解只以生成链中已审核的 `feature_understanding` 版本为准。`document_content` 继续作为需求原文/增强文本载体，供需求分析阶段读取，不再承担需求理解的权威存储。

下游消费方在发起时解析版本：功能测试与代码风险分析默认取最新已审核版本，代码风险分析可用 `requirementUnderstandingVersionId` 指定历史版本；测试单图谱为每条本迭代需求取各自最新已审核版本。三者都没有可用版本时返回 400 并说明原因，不回退旧正文。UI 三阶段不读取需求理解内容。历史需求正文里的旧版需求理解 JSON 因此不再阻塞 UI 生成，也不需要迁移或清空。
