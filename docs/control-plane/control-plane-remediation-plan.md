# control-plane 模块整改方案

日期：2026-10-20。状态：排查后提出的方案，尚未执行。

## 结论与范围

control-plane 的主要问题是部分模块职责集中、提交过程隐含业务行为，以及业务模块之间相互访问内部实现。当前源码规模不构成拆成多个部署服务的充分理由。建议保留控制面的业务数据库和事务所有权，分批建立可验证的模块接口，再整理目录。

本方案覆盖 control-plane；Studio 和三个 Worker 仅作为接口消费方做兼容验证。本轮仅排查和编写方案，没有修改业务源码、安装新依赖、生成运行配置或操作业务数据库。量化结果与证据见[排查记录](control-plane-audit-2026-10-20.md)。

与既有[后端整改计划](../agents/backend-remediation-plan.md)的关系：本方案细化控制面模块组织、事务责任和验证入口，不替代该计划中的其他后端、数据库注释或日志安全要求。不因旧计划标记“尚未开始”而忽略当前已经存在的账号治理、LDAP 和认证模块整理。

## 最终应达到的状态

1. 业务调用方通过明确的公共入口完成一次业务操作，不依赖其他模块的私有方法、ORM 临时属性或提交前隐式扫描。
2. 谁提交事务、事务中更新哪些状态、哪些外部操作必须在事务外完成，均能在业务入口中直接确认。
3. 普通读取、纯规则、业务编排和外部访问各有归属；事务内一致性查询可以留在编排入口，不把所有 SQL 机械搬入 repository。
4. AI、API、UI 和集成执行有各自的业务规则，共用确实相同的基础机制，不将集成“一次远端写入”语义推广到全部 Worker。
5. 层间和模块间依赖有自动检查，测试准备不依赖导入另一个测试文件。
6. 当前浏览器、Worker、历史任务快照及数据库兼容语义不变。每个批次可独立验证和回退。

不以总文件数、单文件行数或新建目录数量作为完成标准；也不要求把所有存量无类型标注函数一次性改完。

## 建议模块职责

这里的模块首先表示职责和公共入口，不要求第一批就重建目录。

| 模块 | 负责 | 对外入口方向 | 应隐藏的实现 |
| --- | --- | --- | --- |
| 身份与账号 | 本地/LDAP 身份、会话、账号治理 | 登录、验证会话、账号治理操作 | 密码、目录适配、Token 和限流存储 |
| 项目授权 | 角色动作、可信成员事实 | 项目动作检查 | 策略引擎、成员查询；不接管资源归属 |
| AI 任务管理 | 创建、更新、查询任务与运行摘要 | 任务管理命令/查询 | 任务类型字段和查询组织 |
| AI 执行 | 阶段、attempt、运行推进、重试和当前产物 | 发起、推进、回传、审核 | 状态投影、兼容字段、提交细节 |
| 正式资产导入 | 已审核候选到正式资产 | 各测试域的导入命令 | 冲突处理、幂等、落库和来源关联 |
| Worker 协调 | 领取、心跳、租约与事件身份 | 内部协议入口 | 队列查询和通用租约机制 |
| 外部集成 | 本人凭据、外部资源读取、业务绑定 | 明确区分的凭据/查询/绑定入口 | 加密、供应方协议、实例核验 |
| 集成执行与恢复 | 写入意图、步骤证据、未知结果、恢复门控 | 提交、执行许可、证据应用、核对 | 账本、行锁、恢复指纹 |
| 各业务资源 | 需求、Bug、测试单及各类测试资产 | 本资源的读写与删除命令 | 本资源的归属与状态规则 |
| 文件基础设施 | 私有文件生命周期和授权交付 | 上传确认、关联、下载、清理 | S3、短期签名和存储键 |

身份与权限刚完成一轮整理，本方案不重新重写它们。文件模块已有同步 IO 线程委托等实现，应保留，不按体积重复拆分。

## 批次与依赖

顺序建议为 B0 → B1 → B2；B3 在 B0 后具备独立推进条件；B4 在 B1/B3 的事务接口稳定后进行；B5 最后收拢。批次描述为实施拆分依据，不表示已经创建或执行工单。

### B0 验证基线与最小质量修复

**优先级：第一批。**

- 固定包含未提交改动的工作区基线，避免将账号、LDAP 等并行修改误认为本次新增问题。
- 对齐正文漂移测试与 ADR 0007：当前两个参数化场景仍期望远端正文变化后返回 partial，
  与已确认的覆盖策略冲突。更新断言时保留图片上传复用、覆盖事实和一次写入验证；
  未知结果与字段修改的漂移保护不能一起放宽。
- 处理 OpenAPI 的第三项失败：`ZentaoBugImportPreview` 和 `ZentaoRemoteGroupPreview`
  的六个字典字段违反当前“无任意属性占位”测试。先核对真实响应：稳定结构使用命名模型，
  有意开放的结构逐字段记录兼容例外和对应测试，不全局关闭检查或直接禁止合法扩展。
- 修复本轮全量 mypy 的 7 处错误，按具体错误处理协议类型、ORM 查询返回类型和第三方配置类型，不全局关闭检查或用宽泛 `Any` 掩盖错误。
- 对 9 个格式未通过文件做独立格式提交，避免和后续业务迁移混在同一个补丁中。
- 建立可重复调用的检查入口，覆盖 Ruff、格式、类型、分层和相关行为测试；仓库当前未发现常见 CI 配置文件，选择实际 CI 平台后再接入，不虚构已有 CI。
- 将后续要修改的 AI/Worker/集成测试夹具逐步提到专用测试支持模块或作用域适当的 conftest，先迁移本次触及的测试，不一次改造全部测试文件。
- 给运行时生成 ZIP 等动态参数提供稳定的测试 ID。本轮 7 个 ZIP 参数的 ID 因归档时间戳变化而不同，
  虽然实际文件内容一致，仍会影响按 node ID 复验与失败跟踪。

**验收：** 全源码类型检查和全 `src/tests` Lint、格式检查通过；测试收集完整；修复前后测试基线可比；没有新增全局忽略项。

**回退：** 独立回退类型或格式改动，无数据库变化。若全量行为测试出现失败，先定位既有失败或环境问题，不把未知失败纳入“基线允许”。

### B1 明确 AI 执行事务与兼容投影

**优先级：核心整改，风险较高。**

重点文件：`repositories/ai_generate_task.py`、`repositories/worker_task.py`、
`services/ai_execution/__init__.py`、`services/ai_stage_workflow.py`、
`services/ai_generate_task.py`。

现状是两个 repository 的 `commit()` 会调用 `persist()`，后者扫描 session 中的 AI 运行与临时标记，并同步阶段、attempt 和队列记录。不能直接删除这段同步，它承载已有一致性。

实施步骤：

1. 列出发起、阶段保存、审核、修订、重试、Worker 回传、导入的提交点，以及每个提交点实际更新的表和临时标记。
2. 先把兼容输出投影和持久化同步区分成明确内部职责，保留现有字段名与序列化结果。
3. 为每类执行命令提供显式事务入口，协调 run、stage、attempt、queue 的原子写入。调用方不再自行设置 `_operation`、`_stage_review`、`_worker_event` 等标记来间接驱动提交。
4. 每迁移一个入口，就验证该入口的失败回滚、重试及旧 Worker 晚到事件；确保只有一条有效的状态应用路径。
5. 所有写入入口迁移并有测试证明后，移除 repository 中的业务提交覆盖和不再使用的隐式同步。禁止先删同步、再追补受影响流程。
6. 将任务管理、运行编排、候选审核/正式导入调用收敛到明确入口，解除 `ai_generate_task` 与 `code_risk_analysis` 的双向引用；共享格式转换移到双方可依赖的位置。

**验收：**

- 调用普通 repository `commit()` 不再隐式推进业务阶段。
- run、attempt 和 queue 在失败时整体回滚；旧 attempt 的回传不能覆盖新产物。
- 审核与正式资产导入仍为不同操作；修订失败不损坏当前有效产物。
- 浏览器字段、历史快照和各 Worker 载荷保持兼容。
- B1 目标范围不存在新的 repository → service 依赖。

**回退：** 每个入口一批迁移，采用替换原实现的方式；禁止新旧实现同时写同一状态。默认不做 schema 迁移，若后续设计证明必须迁移，单独交付迁移、回退和历史数据验证。

### B2 整理 Worker 协调与各域载荷

**优先级：B1 之后，避免同时改动执行存储和回传协议。**

重点文件：`services/worker.py`、`services/worker_task.py`、
`services/worker_context.py`、`repositories/worker_task.py`。

- 提供公开的执行上下文读取入口，消除 `self.repository._hydrate()` 这类跨模块私有调用。
- 将 AI、API、UI 的快照构造和结果应用分别交给各任务域；公共协调层保留领取、心跳、租约和事件身份检查。
- 逐步用明确的上下文/载荷类型表达域差异，避免依赖动态添加到 ORM 对象上的兼容字段。
- 明确保留 AI 旧 attempt 拒绝、API/UI 条目汇总、停止、超时和回传幂等的差异。
- 集成 Worker 继续采用现有独立账本与写许可协议，不并入普通队列重试模型。

**验收：** 原 `/internal/*` 协议不变；领取和回传回归通过；失租、旧回传、取消和进程退出可验证；真实 MySQL 的 `SKIP LOCKED` 检查通过后才能宣称并发验收完成。

**回退：** 按任务域迁移，一次只替换一种载荷/结果处理路径；不同时升级三个 Worker 的协议。

### B3 分清个人授权、外部资源读取和绑定

**优先级：B0 后可单独开展。**

重点文件：`services/integration_connection.py`、`services/shared_service.py`、
`services/resource_binding.py`、`services/zentao_bug_import.py`。

- 将个人连接管理、凭据解析/解密、外部资源读取和项目/需求绑定分开。
- 给通过本人归属校验后的凭据访问提供明确公共接口，移除其他模块对 `_decrypt_secret()` 的直接依赖；禁止因此增加他人凭据可见范围。
- 按 GitLab、禅道已有差异组织 Adapter，不为统一目录而抹平重新认证、实例检查和绑定规则。
- 禅道 Bug 导入按远端读取、内容转换/附件准备、本地事务应用划分。身份冲突、Bug 编号、来源关联、附件正式关联及失败清理必须保持原事务语义。
- 对共享服务列表逐项远端实例探测做测量：分别记录本地查询数和外部调用耗时。若需要分离状态探测，应单独定义字段缺省和前端兼容，不能直接删掉现有状态字段。

**验收：** 所有外部访问仍使用当前操作人本人授权；跨项目和错实例绑定被拒绝；重导入和失败重试不重复创建资源；候选列表/状态字段兼容。列表性能改善需用受控延迟测试或实际测量证明，不以减少行数代替。

**回退：** 按供应方和业务操作分别替换，保留原入口契约。不要将所有“集成”职责再合成另一个大型类。

### B4 从通用删除中移出业务生命周期编排

**优先级：事务接口稳定后，风险较高。**

重点文件：`repositories/base.py`、`repositories/deletion.py`、
`services/integration_lifecycle.py` 和各资源删除入口。

- 先列出各资源的阻止删除条件、运行取消、关联清理、历史保留和文件关联规则。
- 将删除前业务检查与生命周期撤销放到相应业务命令中；repository 负责明确的锁定与删除操作。
- 通用 BaseRepository 不再通过通用删除分派间接依赖集成执行和其他业务模块。
- 保留锁定顺序、运行中的删除限制，以及集成未知写入的证据保留；不将物理删除统一改为软删除。

**验收：** 本次识别出的通用基础仓储 → 业务生命周期依赖链被解除；各资源删除、回滚、候选产物删除和恢复隔离回归通过；不会因消除循环依赖而丢弃未知写入证据。

**回退：** 按资源类型逐个迁移；未迁移入口继续走原实现，禁止同一次删除重复执行两套清理流程。

### B5 组织模块目录并固化检查

**优先级：最后执行。**

- 先沿用当前 `router → handler → service → repository → model` 层次，在 service 等层内按 AI 执行、Worker 协调、外部集成等职责形成子包。
- 明确模块公开入口和可依赖的数据结构，跨模块只通过这些入口协作。已有 `services/ai_execution/` 是可利用的起点，不新增同时保留两套实现的目录树。
- 将与业务无关的格式转换、常量或纯规则放在双方可依赖的位置，不通过 `common.py` 建立新的通用杂物模块。
- 扩展现有架构测试：不仅检查文件存在和 router/handler 不导入 ORM，还检查禁止的层依赖、跨模块私有引用及新增循环关系。
- 更新 CONTEXT-MAP、项目说明与有效决策记录；只有确认了新的领域/架构决策时才新增 ADR，本方案本身不是已接受 ADR。
- 补齐统一异常诊断：入口产生/验证关联标识，未知错误记录脱敏堆栈，客户端错误信封保持不变。先核对框架已有日志，避免重复记录或泄露请求、凭据及第三方异常内容。

**验收：** 测试支持代码不再以 `test_*.py` 为被导入的公共模块；新增非法依赖能被自动检查拒绝；代表性新功能能够在所属业务模块内实现，不需要直接操作别的模块内部状态。

## 每批必守的业务约束

- 项目角色和资源归属分别校验，个人凭据只属于本人；超级管理员的普通访问与集成执行差异沿用[权限矩阵](auth-permission-modules.md)。
- 禁用账号、删除账号、成员移除和个人授权撤销保持各自对既有任务的语义。
- AI 产物仍先成为候选，审核不等于正式导入；用例编号和历史来源不被重构重写。
- 控制面拥有业务数据库和结果事务，Worker 不直接修改数据库。
- 外部写入未知结果不能自动重试；写入意图、操作身份、恢复门控和晚到证据按 ADR 0006 保留。
- `fileId`、私有存储和短期下载 URL 语义不变。
- 不修改已应用的历史迁移，不提交真实凭据、生成配置或运行状态。

## 验证入口与放行标准

所有命令在 `apps/control-plane/` 执行；依赖沿用锁文件。

```sh
uv run --locked --extra dev ruff check src tests
uv run --locked --extra dev ruff format --check src tests
uv run --locked --extra dev mypy --python-version 3.12 --check-untyped-defs src/testing_agent
uv run --locked --extra dev python -m pytest -q -rs
```

每批先跑关联行为，再运行全量回归；新失败必须解释并处理。数据库锁或并发改动必须提供指向空、可丢弃 MySQL 测试库的验证；SQLite 通过不是放行依据。外部目录、S3、浏览器及禅道真实验收单独记录，不使用模拟结果替代。

如果将来涉及编排，另按根规则运行 unittest 和 Compose 配置检查；当前方案不要求变更编排。

## 提交和执行建议

- 一批允许拆成多个小提交，每个提交应能解释具体行为和验证范围。类型/格式、纯搬迁、行为变更分别提交。
- 暂不承诺固定工期。B1/B4 要先确认全部提交/删除入口及真实 MySQL 验证条件，再据此估算。
- 首次实施只启动 B0 和 B1 的事务调用点梳理；不要同时重构 AI、集成、删除和目录。
- 只有当多个独立业务产品确实需要共同认证，或有明确的独立扩容/发布需求时，才重新评估服务拆分。当前没有负载或部署证据支持直接拆成微服务。
