# 预发布候选结构的数据复制

本操作用于从旧预发布 MySQL 结构复制到**独立新库**。它不修改旧库、不切换服务，也不是新的 Alembic revision。只有在明确要切换本机部署、完成备份恢复演练并安排停写后才可使用；空库安装直接使用现有唯一基线。

旧生成版本表和旧导入记录不复制。功能测试集、API 集合及 UI 测试套件中的 `effective_import_id` 清空，因为对应旧导入记录不再存在；正式用例的 ID、内容、归属和其余保留数据照常复制。与既有环境有关的数据数量及测试证据见[验收记录](../records/2026-11-21-generation-candidates-verification.md)。

## 复制前

1. 停止控制面、所有 Worker 和其他数据库写入者，确认没有进行中的任务，并保持停写直到新库切换及核验完成。工具只检测复制期间的变化，不能阻止复制后再次写入旧库。
2. 完整备份旧库，使用独立数据库恢复并对账；备份和临时配置必须使用受限权限并保留回退副本。脚本只检查备份文件存在且非空，**不会替操作者验证备份是否可恢复**。
3. 创建独立目标数据库，字符集和排序规则与源库一致，再使用当前唯一 Alembic baseline 初始化。目标必须没有业务记录，仅允许基线自带的 `auth_runtime` 单例。不要对已有业务库运行初始化、删除或 stamp。
4. 准备两个控制面配置文件，分别指向源库和目标库的 `data.db.user.dsn`，数据库账号需具备对应读取及写入权限；这些文件含凭据，使用临时受限权限文件，不纳入版本管理。正式运行配置仍由 `scripts/manage.py` 生成。

## 复制与验证

从 `apps/control-plane` 执行：

```bash
uv run --locked --extra dev python scripts/candidate_cutover_copy.py \
  --source-config /path/to/source-config.toml \
  --target-config /path/to/target-config.toml \
  --verified-backup /path/to/verified-backup.sql \
  --writers-stopped
```

脚本核验源、目标不是同一库，所有表均使用 InnoDB，目标表、主要结构、基线版本和空库状态符合预期；检查 Worker 队列、集成任务、性能运行及 AI 尝试的活动状态；逐列比较实际生效的排序规则，允许显式声明与继承默认规则的等价写法。此活动状态检查不能证明所有外部写入者都已停止。旧库通过只读一致性快照读取，按批次复制；逐表核对行数和正文摘要、检查目标外键，并以第二个源快照检测复制期间数据变化。复制事务内发生错误时目标事务回滚。提交后会将目标自增序号提高到不低于源库；MySQL 的该操作会隐式提交，如果此步骤失败，目标库可能已有数据，必须停止切换并检查或重新准备目标库。表注释和默认值不在自动结构比较范围内，必须由操作者另行核对。脚本不会验证对象存储中的文件是否可读，也不会覆盖备份或切换数据库配置。

复制成功后，人工核对功能、API、UI 正式用例数量和内容、项目归属、权限、连接配置、文件以及其他业务记录，再按部署流程生成配置并启动服务。启动后验证已有正式资产、新候选生成、来源一致性检查、采用和导入。旧库及备份继续保留；新库开始接受写入后，切回旧库会丢失切换后的新增修改，回退前必须评估并处理这些数据。

本机切换及后续自增序号核对的实际结果见[验收记录](../records/2026-11-21-generation-candidates-verification.md)；该记录不代表其他环境已经执行备份、恢复或切换。
