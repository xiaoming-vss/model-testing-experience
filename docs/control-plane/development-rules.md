# 控制面开发规则

适用范围为 `apps/control-plane/`，以及修改控制面与 AI、API/UI、集成 Worker 接口时涉及的协作边界。本文补充本项目的 Web、数据库、权限和业务事务要求；开发与审查同时遵循[通用后端规则](../agents/backend-development.md)。版本日期为 2026 年 10 月 7 日。

源码路径和应用内命令默认相对 `apps/control-plane/`；明确带有 `apps/`、`docs/`、`scripts/`、`.scratch/` 的路径相对仓库根目录。

规则等级、存量差异、接口演进及日志安全以通用后端规则为统一来源。以下条款限定控制面的具体职责和验证入口。

## 规格与变更范围

开发前先阅读根目录与目标项目的 `AGENTS.md`，通过 [CONTEXT-MAP](../../CONTEXT-MAP.md) 找到[控制面领域上下文](CONTEXT.md)及相关 ADR。跨项目变更同时阅读对应项目的上下文和接口契约。

- 功能规格与实现工单放在仓库根目录 `.scratch/<feature-slug>/`，规格使用 `spec.md`，工单分别放在 `issues/` 下。功能变更优先依据对应规格及已确认的补充要求。
- 业务术语使用 CONTEXT 中的名称，例如项目共享服务、服务个人授权、候选生成结果、测试单和执行条目。
- 与现有 ADR 冲突时明确说明原因及行为变化；确认新决策后记录 ADR，不静默替换原有语义。已经明确被后续 ADR 替代的部分按新决策执行。
- 五个应用保持独立依赖、锁文件、Dockerfile 和启动入口。控制面变更不顺带合并 Worker 运行环境，也不清理与本次任务无关的工作区修改。
- 持续维护的领域与技术说明放在 `docs/<project>/`；应用 README 负责导航和启动说明。

参见[领域文档规范](../agents/domain.md)、[本地问题跟踪约定](../agents/issue-tracker.md)。

## 技术栈与模块职责

沿用 Python 3.12、uv、FastAPI、Pydantic v2、SQLAlchemy 2 异步访问、Alembic 和 MySQL。依赖声明维护在 `pyproject.toml`，依赖变更同步更新该应用的 `uv.lock`。

通常调用顺序为 `router → handler → service → repository → model`。

| 模块 | 职责 |
| --- | --- |
| `routers/` | 注册路径、HTTP 方法和响应模型 |
| `handlers/` | 接收请求、通过依赖注入获取当前用户与服务、包装响应 |
| `services/` | 权限与归属校验、业务规则、状态迁移、事务协调和任务编排 |
| `repositories/` | 数据查询、持久化操作和明确命名的加锁查询 |
| `models/` | 表、字段、约束、索引及数据库注释 |
| `schemas/` | 请求、响应与 Worker 协议模型 |
| `domain/` | 领域值对象、状态规则及适合独立验证的计算逻辑 |
| `core/`、`db/` | 配置、错误、身份工具、数据库会话及基础设施 |
| `api/deps.py` | 鉴权依赖和服务装配；业务路由仍放在 `routers/` |

Router 和 handler 必须保持轻量，业务判断集中在 service 或 domain，两层不得直接访问 ORM 模型或数据库 session。通用查询、筛选、分页、聚合与持久化默认放在 repository，service 负责业务规则及事务协调。

Service 中保留 SQL 的例外限于同一业务事务内的跨资源一致性检查、锁定顺序和原子条件更新，必须说明该语句与事务边界的关系。可复用的查询应抽到 repository，并由调用者传入同一个 session；不能因保留一处事务查询，就把整个资源的查询复制到服务层。存量服务 SQL 按本次修改范围逐步整理，不要求一次性搬迁全部服务。

可复用的业务操作通过清晰的服务或领域接口暴露，不让其他模块依赖某个服务的私有函数。拆分模块时按业务职责划分，保留既有调用入口的兼容性，避免同一规则出现多份实现。

## 编码与异步执行

- 模块、函数和变量使用 `snake_case`，类使用 `PascalCase`，常量使用 `UPPER_SNAKE_CASE`，与现有源码保持一致。
- 新增或修改的公共函数注明参数和返回类型。稳定业务结构优先使用现有 Pydantic 模型或领域类型；`Any` 用于确实不固定的 JSON 内容与外部载荷，不代替已有业务模型。
- 状态比较与赋值复用 `core/enums.py` 或对应领域枚举。新增状态同时更新状态迁移、协议校验、展示映射和测试。
- 使用项目已有装配方式传入 repository、session、配置与外部调用依赖，避免业务方法临时创建另一套数据库连接或读取另一份配置。
- 异步请求路径使用异步数据库和 HTTP 客户端。密码哈希、同步对象存储访问等阻塞操作，按现有方式移入 `asyncio.to_thread` 或相应执行环境。
- 外部请求设置明确的超时。捕获异常后给出对应业务结果或继续抛出，不把失败转换成看似成功的空结果。

Ruff 配置以应用 `pyproject.toml` 为准，当前行宽为 100，检查规则为 `E/F/I/UP/B`，保留现有 `B008` 例外。不要为绕过一个局部问题关闭整个文件或项目的检查。

## HTTP 契约与错误处理

浏览器业务接口保持 `/v1/*` 契约，普通响应采用 `code`、`message`、`data` 信封。通过 `ApiResponse`、`success_payload` 和现有请求响应模型表达结构。Worker 接口保持各自 `/internal/*` 协议，不用浏览器信封统一覆盖既有特殊响应。

- Python 内部字段通常使用 `snake_case`，对外 JSON 使用已有的 camelCase alias。通过模型序列化处理别名，不在不同 handler 中维护不同转换规则。
- 新增接口明确 `response_model`。新增字段、修改可空性、错误码或分页行为时，同步检查 Studio 与相应 Worker 的消费方式。
- PATCH 按字段是否提交及其定义处理，区分缺省、空字符串和 `null`；仅允许修改明确列出的字段，不把请求字典整体写入 ORM 对象。
- 业务错误复用 `core/errors.py`。抛出命名错误使用 `raise ErrNotFound()` 这样的调用形式，创建请求自己的异常实例；需要动态消息时使用现有错误构造方式。
- HTTP 状态与业务错误码同时遵循既有契约。保留内部 Worker 未授权等已有响应例外；不能为了“统一”而破坏客户端已依赖的行为。
- 列表沿用 `items`、`total` 等现有字段，`total` 表示符合筛选的全部条数，不是本页条数。已有分页接口保留边界校验和稳定排序；相同时间使用 ID 作为排序补充。
- 列表与详情分开设计。历史列表返回摘要和产物存在标记，正文、执行大字段与完整报告通过详情接口读取。

契约验证入口包括 `test_app_contract.py`、`test_go_field_contracts.py`、`test_full_route_parity.py` 和 `test_worker_contract.py`。

接口演进、缺省与空值、新增请求的字段校验遵循[通用接口规则](../agents/backend-development.md#接口演进与兼容)。控制面的兼容例外包括既有 Go 字段别名、内部 Worker 特殊响应和历史导入格式；只在对应接口或解析入口保留适配。

## 身份权限与资源归属

用户身份来自后端验证的 JWT；角色和项目成员关系从数据库读取。普通业务请求不能使用请求体中的用户 ID 代替当前登录人。

| 项目角色 | 权限边界 |
| --- | --- |
| `owner` | 项目所有者，管理项目、成员及设置，并具备成员能力 |
| `member` | 维护共享业务资产、发起执行、审核与导入候选结果 |
| `viewer` | 查看项目业务资产，不修改资产或发起执行 |
| `developer` | 查看所属项目 Bug、动态及关联附件，评论、转派和处理状态 |

具体动作使用 `require_project_access` 等已有权限入口，区分 `read/write/execute/review/manage/project_read/bug_read/bug_handle`。开发成员获得项目选择所需的有限信息，不因此获得需求、用例、执行记录等完整读取权限。

需求、迭代、用例、测试单、环境和任务之间的关联必须验证完整归属。已存在的 ID、有效 UUID 或请求通过模型校验，都不能替代“该资源属于当前项目”的检查。

项目共享服务和资源绑定表达共享配置与关联；外部调用使用本次操作人或运行发起者的本人授权。后续成员主动触发 AI 修订、重试或下一阶段时，使用该次操作人的授权，不能继续借用任务创建者的凭据。

异步任务在获取访问材料、执行写前许可和结果应用等相关节点按协议重新检查当前权限及版本。成员移除、角色变化和授权撤销沿用各任务域的既有处理规则，不把全部任务统一视为可继续执行或必须直接删除。

登录注销、撤销记录和错误行为见[登录与服务端注销](authentication.md)。集成 Worker 使用独立专属令牌；Worker Token 验证不能替代业务资源授权。

## 数据模型与数据库迁移

数据库内部主键、平台业务标识和外部资源编号分别表达不同身份。普通新业务标识复用 `core/sid.py`；功能用例编号沿用已确定的创建和导入规则。不要把平台 Bug UUID、`bugs.id`、项目内 `bug_no` 和禅道 Bug 编号互相替代。

- 新增表和字段填写中文 `COMMENT`。表注释说明用途，字段注释说明业务含义，并在必要时标明单位、状态值、关联身份、空值含义和历史兼容用途。
- 注释在 ORM 模型中随结构维护，并通过 Alembic 迁移写入数据库。`description` 等业务字段不能替代结构注释。具体方式见[数据库结构描述](database-schema.md)。
- 表、字段、约束、索引、默认值和注释变更均增加迁移，不改写已经应用的历史迁移。迁移使用固定结构和数据规则，不导入会随应用版本变化的 ORM 模型来重建历史结构。
- 业务唯一性由数据库唯一约束兜底。并发写入发生唯一冲突时，服务层返回对应业务错误；写前查重本身不能保证并发唯一性。
- 外键与删除行为依据业务生命周期选择。Bug 的历史来源引用、集成执行账本等已有保留规则，不套用普通资产的级联删除规则。
- 持久化 JSON 明确结构、版本与兼容策略，优先复用已有领域结构；稳定的查询字段按实际筛选和索引需求设计。
- 时间沿用 UTC 存储约定。需要用户提供时区的计划时间按既有契约校验；指标业务日期与执行时间戳分开表达。
- 升级验证空库初始化及旧版本升级。回退说明数据和证据损失，存在活跃集成任务、未知写入等情况时保留既有拒绝回退条件。

### 中文注释的验收标准

表注释必须说明存放的业务对象及主要用途。字段注释必须解释该字段在本表中的业务含义，不能只重复字段名；业务含义已经明确的普通名称字段可以保持简短，不能用“名称”“状态”“数据”等词代替范围不明确的说明。

| 字段特征 | 必须说明的内容 | 示例 |
| --- | --- | --- |
| 顺序或范围 | 所属集合、排序用途及特殊值语义 | `order_no`：同一 API 集合内的用例执行顺序 |
| 数量、大小或时间间隔 | 统计范围与单位 | `timeout_ms`：单次 API 请求超时，单位毫秒 |
| 关联标识 | 目标实体及标识类型；外键不等于业务标识 | `duplicate_bug`：重复目标的平台 Bug 数据库主键 `bugs.id`；0 表示无重复关联 |
| 状态或枚举 | 业务含义和允许值；完整迁移规则由领域文档维护 | `bugs.status`：Bug 主状态 `active/resolved/closed`，确认情况独立保存 |
| 空值或哨兵值 | `null`、空字符串、0 等实际含义 | `assignee_user_id`：分配的执行人用户业务标识；空字符串表示未分配 |
| JSON、凭据或历史字段 | 内容结构、来源和用途；敏感材料的实际存储方式 | 输入快照说明冻结时点；历史路径说明是否仍用于交付 |

审查时必须核对注释与类型、默认值、枚举及实际读写逻辑一致。`test_schema_comments.py` 负责非空和数据库对应关系等机械检查；业务语义质量由开发与审查核对。注释变更同样通过新迁移落库，既有注释的完善按实际修改范围进行。

SQLite 可用于常规逻辑测试；MySQL 的字符集、排序规则、注释、默认值及并发锁行为必须由真实 MySQL 验证。

## 事务并发与查询

每个写业务入口必须明确负责提交的调用者及事务包含的更新。多表业务更新共享同一个 session；复用辅助函数可以 `add/flush` 或返回结果，禁止隐式提交或回滚调用者的外层事务。Repository 可保留现有 `commit/rollback` 代理，但不能在普通查询或单表更新内部自动调用。历史独立 service 方法已有提交行为时，调用者必须明确其边界，不能直接嵌入新的多表原子操作。

一次请求需要多段事务时，必须说明各段完成条件及失败后的状态。例如外部写入采用“本地准备并提交写入意图 → 远端执行 → 本地结果事务”的协议；远端结果未知时进入核对流程。本地数据库回滚不能撤销已经发生的远端写入。

- 普通读取使用普通查询；需要与删除、导入、覆盖或任务领取协调的修改路径使用明确的加锁查询。
- 外部等待尽量安排在长事务和项目写锁之外。远端验证完成后进入本地写事务，重新检查父资源、当前权限及输入和目标版本。
- 在 MySQL REPEATABLE READ 下，需要最新授权或状态的写入检查使用对应当前读取，不用旧事务快照重新授予写权限。
- 锁定父资源和业务行的顺序保持一致，避免不同操作逆序取锁。唯一约束、行锁和版本条件负责跨进程协调，不用进程内锁代替数据库约束。
- 集成任务领取沿用有界候选查询与精确行 `SKIP LOCKED` 方式，避免队列范围锁阻塞其他领取者。
- 死锁或锁等待超时，仅对明确已经中止、可重新执行的本地事务进行有界重试；重试范围不能包含已经发出的远端写操作。
- 查询按需要选择字段，列表不加载正文、快照和全部运行历史。跨条目关联数据通过批量查询或窗口查询取得，避免每个列表项再发一组查询。
- 索引结合实际权限、筛选、排序和最近运行查询设计；增加索引时保留原有唯一性和外键语义，并检查相应读取路径。

数据库读取与分页约定见[项目说明](README.md#数据库读取与历史列表)。

## 业务状态与 Worker 协议

控制面拥有业务状态、数据库、权限和任务账本；Worker 通过内部 HTTP 协议领取与执行任务，不绕过控制面直接修改业务数据库。

开发必须保留以下已确认语义：

- AI 任务产物首先是候选生成结果。人工审核和正式资产导入是不同操作；审核通过本身不自动创建正式用例。
- 运行仍在推进时，按现有规则拒绝删除。允许删除已导入候选运行时保留已形成的正式资产，来源记录的删除后果遵循 [ADR 0003](adr/0003-candidate-run-deletion.md)。
- 功能执行结果由平台拥有，保存在测试单执行条目中。测试单没有轮次，多轮执行通过新建测试单表达，遵循 [ADR 0001](adr/0001-platform-owns-functional-test-execution-results.md) 和 [ADR 0002](adr/0002-test-order-has-no-rounds.md)。
- Bug 主状态为 `active/resolved/closed`，确认标志与解决方案独立。重新激活保留完整处理历史；不能把所有“已解决”都解释为“已修复”，遵循 [ADR 0005](adr/0005-bug-zentao-lifecycle.md)。
- 缺陷指标按平台 Bug 的项目和发现迭代筛选统计（见 ADR 0004 的 2026-10-08 补充）。未采集或采集失败与“成功采集且结果为零”分别表达，不能用零掩盖不可用。

Worker 领取、心跳、执行结果和取消操作遵循各自状态机、领取身份和幂等约定。租约只证明当前执行权，不证明远端写入是否已经发生；未知结果不能直接重新发送写请求。

启用独立集成执行的项目，远端写入前先持久化步骤 operation ID 和写入意图。领域结果与步骤证据在同一事务更新，响应丢失重试返回原回执，不重复应用结果。授权撤销或失租后的晚到证据按受限证据路径处理，不能据此授予新的写许可。

示例集成执行开关默认关闭；当前环境已全量切换。未启用项目暂停异步提交，旧写路由已删除，不恢复原同步工作流。新增功能不得跳过灰度、恢复门控或未决写入保护。数据库恢复不能回滚禅道，恢复后继续执行须遵循只读核对与隔离放行规则。

详细约定见 [ADR 0006](adr/0006-independent-integration-execution.md) 和[集成 Worker 实施记录](integration-worker-implementation.md)。

## 文件凭据与配置

文件采用私有 S3 兼容对象存储和统一 `fileId` 管理。上传核验大小、摘要、用途、项目与上传者，正式关联在业务事务中完成。下载按当前权限和有效业务关联授权，再签发短期 URL；业务正文、任务快照和历史账本不保存长期下载地址。

共享业务响应、运行历史、快照与日志不包含原始密码、访问令牌、API Key 或签名 URL。授权接口按既有协议提供执行所需材料，登录接口按既有契约返回 Token；这类材料不复制到普通项目列表或共享历史中。凭据存储和脱敏必须与实际认证及存储方式一致，不把“所有秘密字段已经加密”作为未验证的前提。

配置来源为仓库 `config/platform.example.toml` 与本地忽略的 `config/platform.toml`，运行配置通过 `scripts/manage.py` 生成。不要在业务代码、测试、Dockerfile 中加入真实部署密码或将本地生成配置提交到仓库。

数据库、依赖目录、Worker 运行状态、对象存储凭据和生成文件保持在约定的忽略或外部存储范围内。存储桶、前缀和集成运行代次变化遵循现有迁移或恢复流程，不能只改连接地址就假定历史资产仍然有效。

参见[统一文件存储](file-storage.md)和[备份恢复约定](storage-operations.md)。

控制面的 HTTP 错误记录、日志等级及关联字段遵循[通用日志规则](../agents/backend-development.md#异常日志与执行追踪)。浏览器仍收到既有稳定错误信封，内部 Worker 保留其协议规定的安全错误格式；存量异常处理和追踪差异按通用规则记录整改范围。

## 验证与交付

必须按下表选择最小验证入口，再增加受影响功能的专项回归，并报告实际执行的命令、结果、跳过原因和未验证范围。修复问题时优先加入能复现错误行为的回归检查；测试覆盖对外行为、业务规则与边界，而不是逐行复制实现。

| 变更类型 | 必跑入口及追加范围 |
| --- | --- |
| 分层和模块依赖 | `test_architecture_layers.py`，加受影响业务测试 |
| HTTP 与 Schema | `test_app_contract.py`、`test_go_field_contracts.py`；路由变化加 `test_full_route_parity.py`，Worker 协议变化加 `test_worker_contract.py`，并验证缺省、空值与兼容格式 |
| 权限与关联 | `test_auth_contract.py`、`test_project_membership_api.py`、`test_developer_access.py`；外部授权变化加 `test_integration_authorization.py`，覆盖跨项目和撤销 |
| 业务状态 | 对应业务域专项，例如 `test_bug_lifecycle.py`、`test_generic_import_state.py`；改动删除行为加 `test_hard_deletion.py`，覆盖合法、非法及重复操作 |
| 查询与分页 | `test_database_read_paths.py`；项目列表变化加 `test_project_list_queries.py`，检查筛选总数、稳定排序、大字段排除及批量查询 |
| 模型与迁移 | `test_initial_schema_migration.py`、`test_schema_comments.py`，加对应迁移专项；MySQL 属性或锁行为变化必须运行真实 MySQL 的 `test_mysql_initialization.py` 或对应专项 |
| 队列与集成写入 | AI/API/UI 队列使用 `test_worker_queue_storage.py`、`test_worker_contract.py`；集成队列使用 `test_integration_jobs.py`、`test_integration_bug_api.py`，并按影响追加恢复、失租、授权及 `test_integration_jobs_mysql.py` |
| 文件与凭据 | `test_stored_files.py`、`test_stored_file_access.py`，加受影响授权和交付路径测试；真实存储行为变化追加显式存储验收 |
| 错误与日志 | `test_error_definitions.py`、`test_app_contract.py`，加本次修改的异常记录、脱敏与追踪专项 |

表中的测试文件均位于 `tests/`。测试入口重命名或职责调整时同步更新此表；基础入口不能代替本次业务改动的专项验证。真实 MySQL、对象存储等外部验收被跳过时，必须报告对应范围未验证。

源码和测试变更必须通过修改范围内的 Ruff 检查、格式检查、类型检查及上表回归。新增类型与修改过的公共函数必须检查参数、返回值和函数体；第三方缺少类型声明时局部说明，不能用全局忽略掩盖业务类型错误。

在 `apps/control-plane/` 执行应用检查：

```sh
uv sync --locked --extra dev
uv run --locked --extra dev python -m pytest tests/<相关测试文件>.py
uv run --locked --extra dev ruff check <修改的源码及测试路径>
uv run --locked --extra dev ruff format --check <修改的源码及测试路径>
uv run --locked --extra dev mypy --python-version 3.12 --check-untyped-defs <修改的业务模块路径>
```

Ruff 参数和规则以应用 `pyproject.toml` 为准；类型检查使用上面的固定参数，并将涉及的业务模块路径明确记录在交付说明中。后续迁入工具配置文件时，必须保持这些检查范围，不依赖各开发者的本地默认设置。新模块错误必须修复；触及历史模块时区分本次新增问题与存量问题，不能将仍有错误的检查报告为通过。

占位路径按本次修改替换。首次开发需要同步依赖，已有环境且依赖未变更时直接使用现有环境。下面是权限与数据库结构变更的固定测试入口示例：

```sh
uv run --locked --extra dev python -m pytest tests/test_auth_contract.py tests/test_project_membership_api.py tests/test_developer_access.py
uv run --locked --extra dev python -m pytest tests/test_initial_schema_migration.py tests/test_schema_comments.py
```

涉及多个类别时组合必跑入口；共享基础层或跨模块改动扩大回归范围。纯文档修改核对内容、路径和链接即可。CI 后续应复用相同检查入口；本规范不将尚未配置的自动检查声明为已经生效。

数据库或锁相关真实验收使用明确指定的空、可丢弃 MySQL 测试库，遵守测试夹具的库名和初始化限制。测试不得默认接入开发业务库或正式数据。

修改仓库编排时，在仓库根目录初始化本地配置后执行：

```sh
python3 -m unittest discover -s tests -v
python3 scripts/manage.py compose config --quiet
```

交付说明包含改动后的行为、迁移及配置要求、相关验证和实际限制。接口变更更新消费方及契约，数据库变更同时交付模型与迁移，领域语义变化同步文档；没有完成的验证不写成通过。

交付前必须核对本次涉及的规则等级、事务提交者、接口兼容、注释语义、日志安全和验证入口。存量例外与未完成验证分别说明，不用固定覆盖率或文件行数代替行为验证。
