# 仅支持新建数据库初始化

删除行为现已由 [ADR-0009](0009-child-first-hard-deletion.md) 更新为逐级硬删除；下文软删除描述保留作为当时决策背景。

项目发布时只会初始化新的空数据库，不存在需要升级的旧数据库。以 `20260915_0001` 作为唯一初始迁移，冻结当前完整表结构；后续改动通过新的迁移表达。初始迁移不导入运行时 ORM 模型，避免未来模型修改悄悄改变已发布的数据库版本。

移除开发期间的增量迁移、数据回填脚本、API 运行归属归档和 Worker 队列归档。运行归属和凭据来源通过当前业务关联推导；关联缺失时拒绝访问。现有前端和 Worker 使用的接口字段兼容层继续保留。

业务名称直接使用业务字段组合建立唯一约束，不增加生成的状态辅助列。当前删除接口仍保留软删除，已删除记录继续占用名称，物理删除后才释放唯一键；后续另行统一改为硬删除。资源绑定以 provider、本地资源类型和 ID、远端资源类型和 ID 组成唯一键，数据库约束拦截重复写入；停用或软删除不会释放绑定关系，该约束同时适用于 GitLab 和 ZenTao。群组和仓库统一保存 GitLab 返回的规范数字 ID，路径别名不会形成重复绑定。新增需求代码绑定和删除群组锁定同一群组行；删除的引用检查使用锁定读取，避免 MySQL REPEATABLE READ 下的旧快照漏掉刚提交的引用。

**取代的决策**：ADR-0003 中“唯一键加入可空 deleted_at 即可保持有效记录唯一”的结论不成立；其历史数据清理和升级步骤也不再适用。ADR-0004 所述重命名和收敛后的结构直接包含在新基线中。

**验证**：空库初始化、重复执行 `upgrade head`、回退到 base 后重新初始化，并比较实际数据库与 ORM 元数据；在隔离 MySQL 数据库验证全部业务唯一键的重复拒绝、软删除占用及硬删除释放、外键和并发绑定冲突。`downgrade base` 删除所有业务表，仅用于可丢弃的初始化验证数据库。
