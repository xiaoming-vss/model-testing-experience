# API 生成先设计后生成

2026-11-15。API 生成链从「接口配置提取 → API 用例生成」扩展为「接口配置提取 → 接口用例设计 → API 用例生成」。本决策取代 [ADR 0013](0013-software-repository-and-interface-library-api-generation.md) 中关于两阶段工作流和 `api_two_stage/2.0` 标记的部分；软件仓库、接口库输入和安全信息处理保持不变。

## 背景

原生成 skill 只要求每个接口生成正向全参数用例，并明确除非用户要求不生成反向用例。提取产物只描述接口事实，没有「哪些场景值得测、依据哪个字段或约束、如何变异参数、预期什么」的中间产物。直接在生成 skill 中放开反向用例会让模型编造未声明的约束、错误码和业务规则，人工审核也无法判断某条反向用例为何成立。

## 决策

- **三阶段**：`interface_extract` → `api_design` → `generate`，人工审核门禁不变。每次派发只加载当前阶段的一个 skill；新增 `api-case-designer`，生成阶段继续使用 `mtx-generate-api-test-case`。
- **设计产物**：`api_test_design/1.0` JSON，按接口分组、用例级设计。每条用例包含唯一 `id/title`、`category/priority`、`intent`、结构化 `basis`、按 `headers/path_params/query/json/data` 分区的 JSON Patch `patch`、区间 `statusClass` 和最多 2 条业务断言。未覆盖约束写入 `uncovered`。
- **设计依据**：只来自已审核提取产物和需求上下文；不读取接口 description/tags、源码或仓库。`required`/`constraint`/`type` 引用必须能在提取产物中逐字找到。
- **覆盖规则**：正向全参数和可选字段最小参数；必填缺失每字段最多一条且每接口最多 3 条；类型非法每接口最多 1 条；枚举/格式非法合计最多 2 条；边界只针对 `minimum/maximum/minLength/maxLength` 并成对设计边界内和越界。目标每接口 8 条，不设硬上限；超出目标写入 `uncovered`。
- **预期状态**：正向和边界内 `2xx`，反向和越界 `4xx`；不假设精确错误码，`4xx` 不写业务断言。
- **生成对齐**：一条设计对应一条 YAML 用例，名称、顺序、`description`、`method`、`urlTemplate`、状态区间断言和设计断言全部落实；`patch` 的 remove/add/replace 效果逐项校验；不生成设计之外的用例、断言或提取规则。反向和越界值不得被「修复」回合法值。
- **分批**：设计每 5 个接口一批，生成每 10 条设计用例一批；每批独立校验和自动修复（最多 2 次），合并后按完整提取产物和完整设计再校验一次。任一批失败则整个阶段失败，不发布部分结果。
- **审核与版本**：`api_design` 返回 `waiting_review`，`configJson` 同时保留 `apiExtraction` 和 `apiDesign`。审核通过后创建设计阶段版本，上游为提取阶段版本；生成阶段版本的上游为提取和设计两个版本，导入溯源同时记录两者。
- **独立检查点链**：需求无关的独立 API 检查点流程同样支持三阶段保存草稿、审核并继续、继续优化、重试和请求重放；`generate` 仍是叶子阶段。
- **工作流标记**：统一使用 `api_three_stage/1.0`，不再产生 `api_two_stage/2.0`，不保留双协议分支。切换前排空在途 API 任务；历史 API 任务和已通过版本不重写。
- **兼容边界**：旧的非 checkpoint 独立 API 运行链路保持现状；不新增数据库迁移，阶段名和产物字段沿用现有字符串/JSON 存储。

## 后果

- 设计成为可审核门禁：先审场景、依据和参数变异，再生成 YAML；失败时可区分设计问题与实现问题。
- 提取、设计和生成各自持有候选、审核和版本状态；删除上游版本沿用依赖草稿作废规则。
- Worker 承担完整设计校验和生成对齐校验；控制面只做 JSON/YAML 浅层校验，避免两份规则漂移。
- Studio 画布增加第三个真实阶段和设计结果查看器，展示接口分组、类别、优先级、意图、预期状态、patch 摘要和 `uncovered`；可视化只读，原始 JSON 可编辑。
- 生成阶段不再自动生成提取规则；设计协议没有提取规则层，后续串联需求另行设计。

## 拒绝的替代方案

- **直接放开生成 skill 的反向用例**：生成端没有设计依据，会编造约束、错误码和业务字段。
- **只增加一个「生成更多场景」的提示词**：无法审核场景为什么成立，也无法保证 YAML 与设计逐条对齐。
- **用固定模板批量生成通用反向用例**：不能引用具体字段和约束，容易产生与接口无关的用例。
- **把完整请求体作为设计产物**：嵌套对象和数组变异会与提取基线漂移，且审核时难以看出改了哪个字段。
- **保留 `api_two_stage/2.0` 兼容分支**：两套阶段协议会让候选、版本和回传校验长期分叉，切换成本更高。
