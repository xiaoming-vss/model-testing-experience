# ADR 0036：禅道反向拉取应用同时校验两端摘要

- 状态：已接受
- 日期：2026-11-27
- 取代：—
- 被取代：—
- 关联：[禅道反向同步需求](../bug-zentao-reverse-sync-requirements.md)、[ADR 0005](0005-bug-zentao-lifecycle.md)

## 背景

已关联 Bug 的“从禅道同步”分为预览和应用两步。预览返回远端摘要 `remoteDigest`，应用请求回传该摘要后再读取禅道并写入本地。此前应用只校验远端摘要，不校验本地侧：预览之后如果有人修改了本地标题、等级或状态，确认时仍会按旧预览无条件覆盖本地值，并把覆盖后的值记成“已同步”。应用还存在另一个顺序问题：先对本地 Bug 加行锁，再调用 MCP 读取禅道，导致一次慢的外部调用长时间阻塞同一 Bug 的并发编辑。

R31 要求预览包含两端版本或内容摘要，确认时任一端发生相关变化都应重新预览；`docs/control-plane/development-rules.md` 也要求外部等待安排在长事务和项目写锁之外。

## 决策

1. 预览响应新增 `localDigest`，覆盖四个字段组的本地当前值：基本信息、描述正文摘要、状态、责任人；它与现有 `remoteDigest` 一起构成一次确认所固定的两端版本。
2. 应用请求必须回传 `localDigest`；缺失或格式不合法的请求在进入业务逻辑前被拒绝。
3. 应用顺序改为：授权与关联校验 → 调用 MCP 读取远端 → 校验 `remoteDigest` → 重新校验项目写权限 → 对本地 Bug 加行锁并重读 → 校验 `localDigest` → 写入与保存基线。
4. 两端任一摘要不一致都返回 409，并提示重新预览；只有两端摘要都与预览一致时才会覆盖本地值或建立新基线。
5. Studio 的同步弹窗把预览得到的 `localDigest` 原样带回应用请求，不自行计算或推断。

## 后果

- 预览后本地发生相关修改时，确认会被拒绝，用户需要重新预览；不会再用过期确认覆盖本地编辑。
- MCP 调用不再占用 Bug 行锁；只有本地校验和写入处于锁内。
- 预览与应用请求各多一个 `localDigest` 字段，属于控制面与 Studio 的同步契约变更。
- 摘要只覆盖当前预览的四个字段组；后续新增字段组时必须同步扩展 `_local_groups`，否则新组的变化不会被过期确认检查发现。
