# UI YAML 待补内容

新生成的第三阶段产物使用原始平台格式：顶层 YAML 列表，每条用例只有 `name`、`enabled`、`orderNo`、`stepsJson`。步骤使用原有执行字段及可选的 `missingFields`，不新增数据管理或设计冲突协议，已有环境变量引用与 `saveTo` 按执行协议使用，也不提供独立的数据补全表单。

## 缺口标记

`missingFields` 每项包含 `fields`、`operation`、`target`、`value`、`reason`。`fields` 列出真正缺失的执行字段，字段本身显式为 null；已知内容直接填写。空 fields 只用于无法对应执行字段的真实前置准备条件，不能用作人工断言或能力冲突的替代品。

同一步中同一根因的缺口合并为一项。缺发布数据 ID 不等于缺少勾选框：已知定位类型和行定位规则时保留它们，说明需要哪个数据，不能再追加一份“请准备同一数据”的提示。不同步骤真正缺失的字段仍需在各自步骤标记。

```yaml
- name: 勾选目标发布数据
  enabled: true
  orderNo: 1
  stepsJson:
  - orderNo: 1
    stepName: 勾选目标发布数据行
    keyword: click
    locatorType: xpath
    locatorValue: null
    missingFields:
    - fields: [locatorValue]
      operation: 勾选发布数据行
      target: 已完成打包的目标发布数据
      value: null
      reason: 缺少目标发布数据ID；已知页面按发布数据ID所在行定位勾选框，补入ID后填写完整行定位表达式。
    continueOnFailure: false
    enabled: true
```

示例只展示数据缺口的表达方式，实际定位规则须根据第一阶段控件清单和源码确定。原格式不承诺自动跨步骤替换数据；环境变量与后置提取遵循 [UI 环境变量与后置提取](ui-environment-variables.md)，不能通过虚构变量名隐藏真实缺口。

## 阶段与校验

第二阶段按真实的操作、断言能力筛选目标，并保留排除理由；缺定位或缺测试数据不能成为排除依据。必须按业务语义判断能力，不能将输入框值、OR、行数、集合或运行时比较简单标为文本相等后交给第三阶段兜底。可用等价受支持操作完整表达的目标仍保留。否定型预期（如“未出现校验提示”）使用 `absent` 能力，第三阶段以 `assert_hidden`（唯一定位 + 毫秒超时）表达，不能用成功提示替代。

第三阶段根据已审核设计完成字段，不重新引入已排除内容，不把能力不足伪装成待补数据或人工确认。若发现设计无法忠实实现，需要修正第二阶段设计，不能以缩窄预期或伪造断言交付。

按模块生成、每批独立硬校验和最多两次自愈、最终合并检查继续保留。AI 复核仅提供附属问题清单，意见或复核调用失败不触发自愈、不阻断草稿交付；正式导入仍要求补齐真实缺口。原始已审核设计通过 reviewedDesignPath 供本地自检读取，产物仍直接返回 YAML。程序检查结构、执行字段和模块名称/顺序/数量；业务语义须对照原始用例及设计审核，不能将名称齐全视为断言全部覆盖。

用户可在现有 YAML 编辑器修改内容。补齐字段后移除对应 missingFields；正式导入及执行仍拒绝未处理的缺口，禁用步骤也不能绕过检查。

## 历史扩展格式

已有 `ui_yaml_draft/2.0` 产物不自动迁移或覆盖。控制面保留兼容读取、保存及导入校验；重新生成时 Worker 将历史内容规范化为原格式修订上下文，保留已知值，新的模型输出必须符合原格式。历史扩展格式中的待补数据和设计冲突仍保留原有导入保护，不会因本次调整自动变为可执行资产。
