# 移除暗色主题

前端此前有两套配色：`themes` 由 `<html>` 上的 `data-theme` 属性驱动，antd 走 `darkAlgorithm`，
CSS 侧靠 22 个文件里约 4,000 行 `:root[data-theme='dark']` 覆盖规则把浅色样式逐条改写，另有一个
891 行的补丁层 `app/styles/dark-polish.css`。我们决定整体移除暗色主题：应用只保留浅色一套，
`data-theme` 属性、`shared/store/theme.store.ts`、页头的切换按钮、全部暗色覆盖规则与
`dark-polish.css` 一并删除，按主题分叉的组件（代码编辑器配色、关系图、甘特图与任务树的导出样式）
收敛为固定的浅色取值。

理由是这套暗色不是靠 token 切换实现的，而是**覆盖式**：浅色规则里写裸色值，暗色只能整条规则重抄一遍，
还要额外抬一级选择器权重才能压过浅色侧的 `!important`。代价已经反映在文档里——`dark-polish.css`
一个文件引用 229 个 feature 内部类名（违反自家 S7「全局层不得出现 feature 内部类名」），
`workbench.css` 的深色玻璃规则与 `.tp-board` 覆盖同权重、只靠 import 顺序决胜，
三处「深色下凭空多出一层容器」的坑都是这么来的。既然暂时不需要双主题，先去掉这层复杂度，
比继续维护它更划算。

**已考虑的其他选项**：先做 token 化再删覆盖层（把浅色取值提成 `--x`、暗色只换值不换规则，
再让 `dark-polish.css` 退役）——这是文档原先写的理想路径，但它要求同时改掉浅色侧的裸色值、
并逐模块做视觉核对，工作量远大于"先不要暗色"；等将来真要支持双主题时再做，
届时可以进一步用 CSS `light-dark()` 把「两个块」合成「一条声明」。保留暗色但不提供切换入口
（把主题钉在浅色、暗色 CSS 留着）——那会留下约 4,000 行死规则，与 S13「死代码零容忍」直接冲突，
而且删不掉正是最初抱怨的「CSS 很冗余」。

**后果**：浅色渲染不受影响——被删的规则此前都挂在 `data-theme='dark'` 下，在浅色下本就不参与级联；
`surface-tokens.css` 的暗色 token 分支同样如此（随之删掉的是终端面那组在深浅两套里取值相同的重复声明，
它在浅色分支的定义不变）。有三处选择器写成 `:root:not([data-theme='dark'])` 的规则**刻意保留**：
这个 `:not()` 现在恒真，但它同时是权重的一部分，去掉会让四个列表页的名称 / 表头 / 行样式指纹失效
（详见 `docs/studio/STRUCTURE.md` 的同名小节）。移除过程中暴露出两处**浅色下早已存在**、
此前被深色规则掩盖的名称样式分歧（AI 任务列表名称行高 22px 而其余三页 20px；名称颜色在 jsdom 下
因同一元素存在两条 `!important` 规则而按出现顺序裁决），已在 `listNameConsistency.test.ts` 的注释中记录、
未纳入断言，需要按设计稿决定取值后再统一。文档侧同步删掉了 S10「深色对等」这条规则与新增模块清单里
「深色对照写了吗」一项——新写的 CSS 不应再出现 `:root[data-theme='dark']` 分支，它不会匹配到任何东西。
将来若要恢复暗色，正确路径是先做 token 化（S8 要求的 token 单一来源）而不是重建覆盖层。
