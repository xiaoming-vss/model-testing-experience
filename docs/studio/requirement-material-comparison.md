# 需求材料对照视图

界面中的需求分析第二阶段统一称为「材料整理」，对应产物称为「材料整理结果」。首阶段「需求评审」使用独立报告视图，阶段标识及产物格式不因显示名称调整而变化。

## 需求评审报告视图

`requirement_review` 使用 `RequirementReviewView`：顶部显示评审状态和 blocker/major/minor 数量，摘要区展示评审范围、已读材料、已确认事实、工作假设、待验证假设和输入缺口；问题登记表按严重度分组，每条展示类型、证据原文、影响、待确认问题、建议下一步、验证方式和失败模式；覆盖度区以折叠面板展示结构盘点、质量特性、需求气味、行为完整性、追溯和输入审计。

评审报告只供人工判断，不阻断材料整理：`reviewStatus` 不改变“审核通过 / 审核通过并继续”的可用性，也不提供接受风险入口。评审只基于需求文档本身，空状态只说明将要生成的内容。评审阶段的继续优化使用通用自由文本侧栏，不预填逐条 clarification。

## 当前阅读方式

材料提取采用三栏审查工作台：左侧是事实分类导航（总数、业务规则数、来源文件数、分类计数与占比条、来源文件清单），中间是紧凑事实列表（章节分组、搜索、确认状态筛选、事实／待确认问题切换），右侧是当前事实详情（完整正文、所属章节、依据与摘录、关联待确认问题）。选中事实后详情直接更新，不再在列表内展开，也不再渲染左侧原始材料、来源选择、内容块或已审核提取事实对照，不提供材料显隐和联动定位。事实／待确认问题切换时隐藏左右两栏，让问题列表独占正文。待审核时右侧详情继续提供事实正文、分类和确认状态编辑，改动回写原始 JSON。

需求理解保留模块导航、UI 交互、功能概况、业务流程、业务规则与待确认问题，来源引用以文本和摘录提示呈现。原始产物 JSON 与审核／优化流程保持不变，不再为需求理解阅读额外请求上游提取版本正文。嵌入生成全景时，可视化／JSON 切换与复制入口位于页面标题栏，阅读正文不再保留工具行。

## 实现

源码路径相对 apps/studio/src：

- features/ai-testing/components/RequirementMaterialComparison.tsx：三栏审查工作台、事实选择与编辑回写。

正文使用 `208px + 1fr + 336px` 三栏，中栏事实列表和右栏详情独立滚动；容器宽度低于1120px时收窄左右栏，低于920px时详情移到列表下方，低于700px时三栏纵向排列。待确认问题页签只保留单栏。审核操作由外层弹窗固定。列表行使用两行文本摘要，完整正文和依据摘录始终在详情面板阅读，避免长事实撑开列表。

组件测试覆盖事实计数与章节分组、选中联动详情、依据摘录、问题影响与答复、空搜索、非法 JSON、待审核编辑回写、问题编辑回写。相关页面、领域阅读器及布局测试通过；类型检查与生产构建通过。

## 问题闭环与继续优化

问题闭环规则：两阶段业务阅读只展示尚未解决的问题和剩余缺口，计数只包含未解决条目；没有待确认问题时隐藏分类，当前分类自动回到事实或模块。已解决条目及其关联问题提示不进入业务阅读，原始 JSON 编辑仍保持输入原貌，需通过继续优化补齐正文并返回新契约。新生成、保存和审核后的产物不保留已解决问题及关联引用；答复依据保存在对应业务事实的来源引用中。未答复的问题与相关未知状态仍保留。

继续优化预填：首次打开当前运行阶段的优化侧栏时，从当前产物草稿提取尚未解决的问题，按原编号逐题生成“答复”占位。材料提取与需求理解均适用；已解决问题不带入，无待确认问题时留空。取消后重新打开及提交失败保留已填写草稿。仅依据明确补充的信息修订，未填项继续待确认；原样模板不能提交，支持直接改写为其他优化要求。沿用阶段修订接口，同时携带左侧未保存的产物修改。

生成全景的需求分析第一阶段弹框复用本视图：可视化模式使用同一对照组件与弹窗外壳，版本条、上游版本、追溯和审核操作保留在弹框内；JSON 模式仍显示原始产物。材料提取结果与阶段弹框共用尺寸与分栏规则，两处阅读体验保持一致。

材料整理 0.2 采用章节聚焦阅读：按功能切换，只展示当前功能中有内容的统一分类；问题按 functionIds 归属，无法归属的列为整体待确认。依据按需展开，原材料仍可查看。旧格式提示重新生成，保留 JSON 阅读。
