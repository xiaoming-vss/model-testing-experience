# 性能运行指标与夜莺筛选规格

- 日期：2026-11-20
- 状态：实施中
- 负责人：perf-worker maintainer
- 来源：用户确认的性能运行与夜莺筛选需求
- 关联：[ADR 0003](../adr/0003-performance-run-metrics-context.md)


## 范围与归属

- 性能测试集归属于项目，不绑定迭代。发起测试集运行必选本项目迭代，允许选择任何状态；页面确实已选定同项目迭代时默认带入，否则留空。独立用例运行可不选迭代。
- 创建时校验权限及迭代项目归属，冻结项目、迭代、测试集、用例及运行身份与必要名称，后续修改不改变运行归属。对历史记录缺失的字段按未关联处理；旧指标不回填。
- 测试集运行所有子用例顺序执行，共用一次父运行 ID；现有代码创建子运行后才生成父 ID，应提前生成，再冻结到全部子运行。独立运行的用例若属于测试集可带 suite_id，不带 suite_run_id。
- `project_id`、`sprint_id`、`suite_id`、`suite_run_id`、`case_id`、`run_id` 为各自业务 ID；有值时附到运行指标。`step` 用于步骤指标。缺失的可选身份不伪造值或填写名称。
- 后续 Grafana 相关计划一律改为夜莺；不新增平台内 Prometheus 查询页面。跨项目接口变更在实现前完成 ADR 和兼容检查。

## 步骤执行语义

每个步骤检查按以下优先级，前一阶段失败则跳过后续阶段。一次已完成判断的步骤最多只计一次失败，且只计最先发生的一类失败原因：

1. 请求异常、无响应或最终 HTTP 状态不符合预期：`request`。
2. 任一响应检查失败：`check`。
3. 任一要求的变量提取失败：`extract`。

三阶段通过才算成功。未配置检查或提取时跳过对应阶段；后续步骤是否运行由既有 `onFailure` 控制，运行被中断而未完成判断的步骤不伪造结果。未配置预期状态时接受 2xx；配置一个或多个具体状态码后以配置为准。对已有用例不做旧状态断言推断。编辑器目前新步骤默认显式断言 200，需调整避免误伤其他 2xx。状态码列表需要严格校验、表单/YAML 往返及真实执行验证。

## 指标和时长口径

- 用已有 k6 指标查看请求量、HTTP 失败、响应时间、VU、未启动迭代和网络传输。原生 HTTP 失败与业务步骤成功不是同一口径；预期 404 可是业务成功但 k6 默认 HTTP 失败。
- 新增步骤结果计数和失败原因计数，按 step 与结果/原因筛选。既有 `biz_failures` 是失败事件数，不等于失败步骤数，应独立保留语义。
- 用例级 P95 直接收集该用例全部步骤请求耗时样本，步骤级按步骤收集；测试集只展示各用例对比，不计算综合 P95。成功或失败请求只要有可靠耗时均纳入；没有可靠样本时不伪造零值。
- 耗时采用 `http_req_duration`（发送、等待、接收；不含连接等前置阶段），重定向以最终响应耗时为准。应验证超时、无响应、重定向多跳时的样本及单位，确认是否存在缺失样本。
- 不对各序列或时间点 P95 求均值得到整体 P95；整次运行和实时曲线的语义、单位与查询应分别验证。隔离实验中，自定义 Trend 可产出运行级与步骤级指标，Prometheus 数值单位为秒，而 k6 JSON summary 为毫秒，名称不自动包含 seconds 后缀。
- 写入异常与执行结果分离；用户要求压测不中断并提示异常。k6 连接拒绝、401 和 503 的隔离实测均以退出码 0 结束、错误写在 stderr。需要在日志读取阶段识别而不是依赖尾部或退出码；未能确认是否写入时应标明未知，不误报成功。识别协议的稳定性和完整性需进一步验证。

## 夜莺与名称映射

仪表盘变量依次按项目 → 迭代 → 测试集 → 测试集运行 → 用例 → 步骤筛选；显示中文，实际使用 ID。优先当前名称，已删除时优先可用的运行时名称，否则显示 ID。夜莺变量支持 Prometheus 标签查询及级联。9.3.0 实机未保存变量预览中，使用 `query_result` 与命名捕获组 `text/value` 验证“测试项目”显示、实际值 `project-123`；变量设置中的“显示名称”本身只是变量标题。正式映射仍需数据源及权限设计。

2026-11-20 用户确认：夜莺看板的访问权限先由夜莺管理员统一管理，不要求本期自动同步平台账号和项目权限；筛选本身不构成权限隔离。

用户现有环境 v9.3.0，数据源 `prometheus` 指向夜莺容器内的 `http://prometheus:9090`，容器别名解析到 `prometheus-local`；本机映射 127.0.0.1:19091，Prometheus v3.13.5 已启用 remote-write receiver、保留期 7 天。必须验证实际 Worker 容器的网络路径和运行时配置，不能把夜莺页面端口当写入地址。当前已有 `k6` 仪表盘，其 `child_run_id` 变量定义为 `label_values(k6_vus, run_id)`；仅观察，未更改配置。

名称映射需继续在隔离环境验证可行的映射指标、受限只读数据源或适配方案，覆盖重名、改名、删除、旧序列残留和项目权限；禁止把筛选视为权限隔离。现有测试集/用例删除会清理运行记录，无法读取名称时必须回退 ID。

## 实施顺序

1. 等控制面整改形成稳定提交，并检查其对性能相关目录和数据库基线的影响。
2. 记录 ADR、契约字段及兼容矩阵；设计受控升级。Worker 严格拒绝未知 RunSpec，先部署兼容新旧快照的 Worker，确认旧 Worker 退出，再部署控制面和 Studio；迭代必填切换需有维护窗口或显式分阶段门控。
3. 控制面接收与校验迭代、父子运行身份及快照，按预发布政策修改唯一 baseline，同时为已有开发库提供清晰升级步骤。
4. Studio 测试集运行弹窗、步骤状态码配置、记录展示和 YAML 往返。
5. Worker 执行阶段优先级、自定义标签、步骤结果、P95、监控写入异常及安全处理。
6. 以真实 k6 与隔离 Prometheus 测试写入、查询、失败情形和单位，完成夜莺映射及仪表盘方案；再对用户实际数据源进行获授权的端到端验收。

## 验收

- 控制面：迭代所属项目、允许所有迭代状态、必填/可选、父子 ID、冻结字段、历史数据；串行、停止、租约、完成回传不回归。
- Studio：显式迭代选择与留空，多个候选时不自动误选；状态码默认、多个值、空值和错误输入；保存/重开一致。
- Worker：正常和异常状态、请求/断言/提取三种互斥失败、continue/abort、超时、重定向；步骤级和用例级样本及标签。
- 输出：真实 Prometheus 查询指标数值和单位，检查高基数/敏感信息；401、5xx、连接中断、未知状态不影响 k6 执行结果；不得只以假接收端或 SQLite 宣称真实服务通过。
- 夜莺：筛选变量实际查询值为 ID、展示中文、级联与多选；名称改名/重名/删除及权限隔离。输出以本机具体版本为准。
- 按 docs/commands.md 运行涉及项目的相关回归、lint、类型检查和规定的构建；真实 MySQL 和 Prometheus/夜莺能力单独列明通过或未验证。
