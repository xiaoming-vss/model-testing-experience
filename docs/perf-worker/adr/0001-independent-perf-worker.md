# ADR 0001：性能 Worker 独立成项目

- 状态：已接受
- 日期：2026-11-16
- 取代：—
- 被取代：—
- 关联：[ADR 0002](0002-control-plane-poll-mode.md)（控制面 poll 模式）

- 后续：控制面接入、`poll` 模式和 Compose 由 [ADR 0002](0002-control-plane-poll-mode.md) 补充；本文第 6 条和“后果”中的阶段说明以 ADR 0002 为准。

## 背景

性能测试模块需要把结构化性能用例转换为 k6 脚本并执行，同时把压测指标写入所选 Prometheus。压测会占用大量 CPU 和网络，执行时长从分钟到小时；现有 `api-ui-worker` 的职责是单任务 API/UI 功能执行，镜像基于 Playwright，队列和资源模型不适合承载持续发压。

平台后期还需要支持把 Runner 单独部署到压测主机、按压力独立扩容，并与 API/UI 执行队列隔离。

## 决策

1. 新建 `apps/perf-worker`，作为独立可运行项目，拥有自己的依赖、锁文件、Dockerfile、启动入口和配置。
2. Worker 使用 Python，负责运行规格校验、执行计划生成、k6 子进程管理、心跳/停止（下一阶段）和结果回传；k6 负责发压、业务校验和指标输出。
3. 性能用例使用 YAML，与 API/UI 用例保持一致；编译器生成 `plan.json`，固定模板 `main.js` 读取计划执行，不为每个用例生成 JS。
4. k6 通过 Remote Write 写入执行时选择的 Prometheus；平台只保存监控接入和查询凭据，不部署、不管理采集组件。
5. 一个 Worker 同时只执行一个 k6 任务；扩容通过增加 Worker 实例完成，不与 API/UI Worker 共用进程。
6. 当前阶段只实现本地 `once` 模式；控制面 perf 任务表、`/internal/perf-worker` 协议、`poll` 模式和 Compose/Helm 接入作为下一阶段。
7. Worker 不直接访问控制面数据库；业务状态、权限和最终达标判定归控制面。

## 后果

- 压测资源与功能执行隔离，Runner 可单独部署到主机或节点池。
- 镜像需要同时包含 Python 运行时和固定版本的 k6 二进制，镜像体积和版本管理需要单独维护。
- 固定模板需要版本化；模板升级时旧运行仍按冻结的模板版本复现。
- 用户不能直接编写 JS，复杂条件分支和循环暂不支持，需要后续以受控模板能力扩展。
- Compose 和 Helm 暂不包含 perf-worker，部署文档需明确当前只有本地运行入口。
