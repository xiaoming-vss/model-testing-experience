## 优先级与批次原则

| 优先级 | 判定条件 | 处理方式 |
| --- | --- | --- |
| P0 | 已证实的数据错误、越权、敏感材料外泄或重复外部写入 | 先补复现与回归，暂停依赖该行为的后续修改，优先修复 |
| P1 | 已证实的诊断缺口、协议兼容风险、事务或生命周期缺口 | 在相应阶段修复，附直接验收证据 |
| P2 | 类型、局部分层、字段说明或工具入口差异 | 按项目及模块推进，避免扩大行为变化 |
| P3 | 只有风格偏好、尚无收益证据的抽象或统一目录诉求 | 记录评估；没有具体维护收益时不执行 |

不存在已证实 P0 时，默认先完成静态质量与安全诊断，再做业务审计和结构调整。每批只解决一个明确主题，记录具体文件，不用全仓自动格式化、批量类型忽略或目录搬迁替代整改。

每个工作包的预计工作量在 W00 后依据问题数量、回归耗时和依赖重新估算。当前不承诺固定工期；遇到新增业务范围、未确认契约或外部验收缺失时更新计划及完成条件。

## W02 控制面安全异常诊断

**范围：** `apps/control-plane/src/testing_agent/app.py`、本项目日志或错误辅助模块，以及 HTTP 错误处理测试。

执行步骤：

1. 用真实应用请求触发未知异常，证明当前诊断缺口；保留既有 HTTP 状态和错误信封断言。
2. 定义安全诊断数据：异常类型、可定位的调用栈及已有请求关联信息。第三方错误、异常链和源码上下文可能携带秘密，不能直接输出未经处理的异常字符串或函数局部变量。
3. 在明确的异常处理入口记录一次未知错误；避免中间件与处理器重复输出同一堆栈。
4. 处理序列化失败、异常链和日志自身失败的降级，日志不能再次使原业务请求失败。
5. 已知业务错误按既有错误契约处理，权限或参数拒绝不逐次输出未知错误堆栈。

**必须新增或补齐的场景：** 普通未知异常；异常消息和 cause 中包含测试秘密；异常文本包含带签名参数的 URL；错误对象不能安全字符串化；没有请求上下文；错误路径仍返回原有安全 500；内部 Worker 401 特殊响应不改变。

**验证入口：** `test_app_contract.py`、`test_error_definitions.py`、`test_auth_contract.py`，以及本包新增的日志专项。

**完成条件：** 未知错误有可定位诊断，预置秘密标记不出现在日志及普通错误响应中，不改变现有状态码、业务错误码和 Worker 特殊响应，错误诊断不重复。

## W04 请求与任务关联追踪

**范围：** 控制面 HTTP 请求关联及四个项目中已有任务身份的日志传播。

执行步骤：

1. 列出现有 `task_id/run_id/worker_id` 与 `job_id/step_key/operation_id/claim_generation` 的来源和可用节点。
2. 控制面统一生成请求标识；允许客户端传入时限定格式、长度及字符，验证失败生成新的安全标识，避免控制字符及未经处理的请求头进入日志。
3. 明确上下文传递和清理方式，验证并发请求不会串用标识。需要通过线程、后台任务传播时显式处理，不能凭线程局部行为假定正确。
4. 路由记录模板与安全状态，不记录完整 URL 查询、请求体或认证头；正常健康和空轮询按明确策略控制噪声。
5. Worker 沿用任务载荷中真实存在的标识，不能为不存在的 run 或 operation 伪造 ID。新增协议字段时使用可选兼容方式并验证双方。

**场景：** 有效与无效请求标识、并发请求隔离、正常与异常结束后的上下文清理、线程委托、同一任务多个阶段、旧载荷缺少可选字段、内部接口拒绝、标识中出现换行或超长输入。

**验证入口：** 控制面 `test_app_contract.py`、`test_worker_contract.py`，各 Worker 的协议、运行及控制面客户端专项。

**完成条件：** 一次请求或操作可通过同一安全标识串联；并发无串号；现有响应结构及任务协议兼容；没有为追踪记录增加敏感载荷或不必要的空轮询日志。

## W05 审计关键业务边界

本包以审计和新增行为证据为主。只有查出具体缺口才在 W06 修改实现；已经符合规则的模块记录证据后保留。

| 审计主题 | 要检查的具体问题 | 核心验证场景 |
| --- | --- | --- |
| 权限与归属 | 当前用户、项目角色、父子资源及个人授权是否完整校验 | 四角色、跨项目 ID、成员移除、角色变化、授权撤销 |
| 事务与提交 | 谁提交，多表是否共用 session，辅助方法是否提前 commit | 任一步失败整体回滚、调用方组合、多段事务完成条件 |
| 查询与加锁 | 普通读是否加不必要锁，修改是否读到当前状态 | 读写并发、删除与导入竞争、RR 下旧授权快照 |
| 领取与回传 | 领取身份、租约、重复请求及回传丢失如何处理 | 重复领取、旧代次、失租、回传重试、重复结果 |
| 外部副作用 | 本地失败是否触发已经发出的外部写重试 | 超时、准备响应丢失、未知结果、晚到证据 |
| 停止与取消 | 是否停止新任务和新写入，在途任务如何收尾 | SIGTERM、取消、心跳继续、最终结果、资源清理 |
| 接口演进 | 信封、别名、空值、扩展字段和历史格式是否保留 | 旧请求、旧快照、未来能力声明、缺省与显式清除 |
| 删除与历史 | 正式资产、来源、Bug 历史和集成证据是否正确保留 | 删除候选、删除资源、当前关联、unknown 保护 |

每个主题输出检查路径、现有保护、证据缺口与问题判断。不得因为存在 service SQL、未完整标注类型或捕获 `Exception` 就直接认定行为错误。

**完成条件：** 四项目及其交互路径均有规则覆盖结果；所有拟修问题有可执行复现或明确静态违规证据；需要真实 MySQL或外部验证的结论单独列出。

## W06 修复已证实的权限 事务与生命周期缺口

**前置条件：** W05 已确认问题并建立对应工单。未发现问题的主题标记为“已验证无需改动”，不制造结构修改。

执行步骤：

1. 每个问题建立独立工单，记录原行为、预期、规则依据和最小复现。
2. 先运行能捕获该问题的回归，确认失败发生在真实调用边界。
3. 修复该边界，并保持既有状态机、权限动作、标识和消费方契约。
4. 若修复需要改变接口或数据规则，先明确新旧版本兼容、迁移及消费方变更，将扩大的范围记录在工单中。
5. 根据主题运行权限、事务、领取、恢复或停止专项；真正涉及 MySQL 并发的修复必须有真实 MySQL 证据。

**完成条件：** 原始复现通过，必要并发及跨进程回归通过，无新增越权、部分提交、重复操作、状态错写或停止后新写入；变更与证据能归属到独立问题。

## W07 字段语义及数据库注释质量

**范围：** 四项目的协议与产物字段、控制面数据库模型和注释。已完成的注释覆盖不重复重写历史迁移。

执行步骤：

1. 依据代码读写、领域结构与已有规则核对标识、单位、状态、排序范围、哨兵值和 JSON 快照用途。
2. 区分 `id`、平台业务 ID、项目内序号和外部资源编号；检查如 `duplicate_bug` 这类非普通关联字段。
3. 只修改语义不清或不准确的注释与说明，保持实际字段类型、默认值和合法值不变。改变实际数据语义时转入独立业务修复包。
4. 模型注释变化增加固定的新迁移，编号依据执行时当前 Alembic head 决定。不得编辑已应用的 `20261007_0034` 迁移以覆盖既有数据库。
5. 在隔离 MySQL 中验证注释以及字段类型、字符集、排序规则、默认值、可空性、自增、约束和业务行保留；普通 Worker 不引入数据库。

**验证入口：** `test_schema_comments.py`、`test_initial_schema_migration.py`、`test_mysql_initialization.py` 及对应协议测试。

**完成条件：** 本包字段说明与实际逻辑一致，模型和新迁移一致，数据库属性及业务数据保留有独立验证。当前业务库应用迁移作为独立运维动作，不由本包测试隐式执行。

## W08 分模块完善类型

本包优先覆盖行为已经稳定的公共接口与高频修改边界。控制面数量较大，按明确模块推进，不批量填充 `Any` 或用类型忽略替代建模。

| 顺序 | 范围 | 主要目标 |
| --- | --- | --- |
| 第一批 | API/UI Worker 的少量缺失标注及日志、协议接口 | 明确同步与异步回传、结果和可空值 |
| 第二批 | 集成 Worker 的协议、执行窗口、repository 与 gateway | 明确写许可、证据、异常和返回值 |
| 第三批 | AI Worker 的平台接口、运行器及任务公共接口 | 保留 Python 3.13、unittest 和当前执行模型 |
| 后续批次 | 控制面的错误、协议、领域规则，再到逐业务域服务 | 区分 ORM 对象、请求模型、响应结构和动态 JSON |

执行步骤：

1. 从 W00 清单选择一组有关联的公共函数，定义这一批的文件、调用方和完成标准。
2. 先明确实际输入输出及错误模式，再增加类型。稳定数据使用现有模型或确有收益的新结构；动态外部载荷保留明确的宽类型及运行时校验。
3. 修改模块接口或引入类型后验证所有直接调用方，避免仅让静态检查通过却改变运行时序列化。
4. 控制面及 API/UI 使用规则中的固定 mypy 参数，集成 Worker 使用现有配置；AI 当前没有 mypy 依赖，通过类型审查和现有行为测试完成本批，不临时借用其他应用的环境。
5. 如确需新增类型工具，作为独立工具配置变更评估依赖与锁文件，不夹带在业务类型修正中。

**完成条件：** 选定范围的公共接口标注完整，静态检查或对应审查证据明确，直接行为回归通过，没有扩大无依据的 `Any`、`cast` 或忽略项。尚未处理的模块继续列入台账。

## W09 有证据收益的模块边界调整

**候选范围：** 重复业务规则、难以单独测试的外部访问、跨资源查询耦合或事务责任不清。单纯文件较长、目录名字不一致或存在一层代理不自动进入整改。

2. 设计小范围接口，明确输入、输出、错误、事务与依赖；先利用现有装配，不建立全仓新抽象框架。
3. 普通查询默认迁到本项目 repository；服务层事务 SQL 符合有效例外时保留并解释。
4. 通过新接口验证原有行为，检查锁顺序、session、提交者及外部操作次数没有改变。
5. 新路径稳定后移除旧实现，不长期保留双套同义逻辑或仅增加转发层。

**完成条件：** 具体维护问题得到改善，规则来源集中、调用方复杂度降低，旧实现与多余适配清理，分层和行为回归通过。无法证明收益的候选记录“不采用”及原因。

## W10 固定持续检查入口

**目标：** 后续功能开发能重复执行同一组规则检查，防止已经修复的问题回退。

执行步骤：

## 测试环境与真实验收

| 环境 | 要求 |
| --- | --- |
| 单元与普通协议测试 | 使用各项目现有 fixture，不读取当前服务作为默认测试目标 |
| 控制面 SQLite | 用于一般行为和迁移结构测试，不作为 MySQL 并发锁证据 |
| MySQL | 明确指定空、可丢弃、名称以 `_test` 结尾的数据库；当前 fixture 使用 `CONTROL_PLANE_TEST_DATABASE_URL` |
| Playwright | 使用项目要求的镜像及浏览器版本；真实执行与模拟步骤分别报告 |
| S3、GitLab、LLM、禅道 | 首先隔离 fixture；真实访问以明确资源和验收指令执行，不借用其他用户授权 |
| 跨进程与长传输 | 使用现有独立 fixture 及显式开关；默认跳过的边界测试单独运行 |

MySQL 每次验收用任务独立的临时数据库，运行前检查目标及空库条件；同一库的建表、升级和清理不得并发。清理仅针对本次明确创建的资源。fixture 未完成清理时先保存必要的脱敏证据，再处理隔离资源，不扩大到业务数据库。

当前业务服务可能持续写入领取回执与心跳。读取业务库校验和时出现变化，不能直接认定是结构迁移修改数据；数据保留验收以隔离环境中的可比较样本为准。

真实验收缺少环境时继续能独立完成的工作，相关结论保持“未验证”。如该证据是工作包必要完成条件，则该包保持未完成，不跳过条件进入整体通过结论。

## 兼容 回退与暂停条件

每个修改包都保存自己的开始基线、文件清单、行为变化、测试结果和恢复方式。优先保留独立可审阅的差异；采用提交时只纳入本包文件。存在其他未提交修改时，恢复只能撤销本包的具体变化，禁止对整个工作区做清空或覆盖恢复。

| 情况 | 处理方式 |
| --- | --- |
| 目标文件被其他任务修改 | 停止对该文件的依赖编辑，读取最新内容并重新核对，保留双方改动后重新验证 |
| 发现破坏性协议变化或领域规格冲突 | 先给出具体新旧行为与兼容方案，澄清未确定语义；继续不依赖该结论的任务 |
| 新增回归失败 | 先定位到本包改动并修复，不能删除断言、放宽业务校验或标记跳过来通过 |
| 发现外部写入结果未知 | 保留意图及证据，按只读核对处理；不因重启、回退或测试重跑再次写入 |
| 迁移或类型修改扩大业务范围 | 分离成新工单，更新依赖与验收，不混入原机械整改包 |
| 环境缺少必要验收条件 | 明确缺少的条件，保持该结论未验证；完成其余独立工作 |
| 用户要求暂停 | 记录本包状态、已做改动、最后验证和下一步，再停止执行 |

代码回退、数据库回退、运行配置回退和远端业务恢复分别处理。加法迁移与执行账本按现有运维规则保留；不能为了回退应用删除未知写入证据。部署与真实外部操作的后续授权不从一次代码整改指令中自动推导。
