# 通用后端开发规则

本规则适用于 `apps/control-plane/`、`apps/ai-worker/`、`apps/ai-worker-pi/`、`apps/api-ui-worker/` 和 `apps/integration-worker/` 的新增功能、修改及代码审查。版本日期为 2026 年 10 月 7 日。前端 `studio` 按其自身项目规则开发。

源码路径、工具配置、测试命令和专用协议以目标项目为准。通用规则规定执行标准，项目补充规则规定具体模块与验证入口；项目差异只有明确限定范围时才构成例外。

| 项目 | 专用规则与边界 |
| --- | --- |
| 控制面 | [控制面开发规则](../control-plane/development-rules.md)：HTTP、数据库、权限、业务状态与本地事务 |
| AI Worker | [AI Worker 开发规则](../ai-worker/development-rules.md)：模型调用、技能输入、产物验证和回传 |
| AI Worker Pi | [Pi Worker 开发规则](../ai-worker-pi/development-rules.md)：Python 编排、Pi RPC 与进程生命周期 |
| API/UI Worker | [API/UI Worker 开发规则](../api-ui-worker/development-rules.md)：HTTP 与浏览器执行、步骤结果、文件上传和停止 |
| 集成 Worker | [集成 Worker 开发规则](../integration-worker/development-rules.md)：外部写许可、一次执行、未知结果和安全证据 |

## 规则等级与适用方式

| 等级 | 表达方式与执行要求 |
| --- | --- |
| 必须遵守 | 使用“必须”“禁止”“不得”等措辞；开发和审查必须检查，不满足时不能将该项报告为完成 |
| 推荐做法 | 使用“默认”“应”“优先”等措辞；按此执行，采用其他方案时说明理由及验证依据 |
| 兼容例外 | 明确限定接口、模块或历史数据范围；保留已有契约，范围外按通用规则执行 |

本规则用于新增代码和本次修改涉及的行为。修改触及历史代码时，必须检查相关规则；无法同时整改的存量差异，应记录范围、原因、风险和后续工单。采用推荐做法之外的方案或保留兼容例外时，在规格或交付说明中记录受影响路径、兼容理由、验证方式及收敛条件。

开发前必须阅读根目录与目标项目的 `AGENTS.md`、项目规则、领域上下文及相关 ADR。跨项目修改同时检查消费方和生产方契约。领域术语及决策遵循[领域文档规范](domain.md)，工单和规格按[问题跟踪约定](issue-tracker.md)放在仓库根目录 `.scratch/`。

## 模块职责与执行边界

项目必须保留独立依赖、锁文件、Dockerfile 和启动入口，沿用各自声明的 Python 版本与执行模型。命名和工具检查遵循项目配置，新增或修改的公共函数必须明确参数、返回值及稳定业务结构。

业务编排、纯规则、外部访问与运行生命周期应分开维护，依赖通过现有装配入口显式传入。控制面的 router、handler、service、repository 分层按其专用规则执行；Worker 不必为了统一目录而增加不需要的 Web 或数据库层。

Worker 必须通过控制面协议获取任务、权限材料和回传结果，不直接修改业务数据库。AI/API/UI Worker 的执行授权、重试及停止规则遵循对应任务域；集成 Worker 的远端写入遵循一次执行及证据核对规则，不能推广为所有调用的通用重试策略。

阻塞工作必须安排在不妨碍所在流程心跳和停止的执行环境中。异步路径使用异步客户端或线程委托；已有同步或线程运行模型按本项目约定保持。外部请求必须设置超时，并区分执行失败、回传失败、取消与未知结果。

## 事务与外部副作用

数据库事务只由持有数据库的控制面协调，提交者、原子更新范围和多段事务的完成条件必须明确。复用辅助函数禁止隐式提交调用者事务。查询默认在 repository，服务层事务 SQL 的限定例外见控制面规则。

跨进程操作必须明确请求、任务、运行及操作的身份，幂等重试复用原请求身份。回传重试不得隐式重新运行已经执行的任务或外部写操作。本地失败或数据库回滚不代表远端副作用已经撤销。

调整领取、心跳、并发、取消或停止行为时，必须说明已领取任务及在途请求如何处理，并补相关生命周期验证。不能用其他 Worker 的退出方式覆盖本项目已确认的策略。

## 接口演进与兼容

接口变化必须检查当前 Studio、对应 Worker、历史导入文件和已保存任务快照的消费方式；交付时记录新增或变化的字段、默认值、状态值以及兼容处理。HTTP 状态、响应信封、别名、产物结构和错误格式遵循各自协议，不统一覆盖已有差异。

| 变更 | 必须采用的处理方式 |
| --- | --- |
| 新增可选字段 | 定义缺省行为，保证旧请求不传该字段仍可处理；新增响应字段检查消费方是否允许扩展 |
| 新增必填字段 | 为旧请求提供兼容适配，或使用版本化接口和消费方切换方案 |
| 删除或重命名字段 | 通过兼容读取、过渡别名或版本化方式迁移，明确旧字段的保留范围及移除条件 |
| 修改类型、可空性或含义 | 检查请求、响应、历史数据和快照，按破坏性变更提供适配或迁移方案 |
| 新增或调整状态值 | 同步状态机、筛选、统计、展示和 Worker 校验；保留旧值解析或明确迁移范围 |

可更新字段必须明确未提交、`null` 和空字符串的区别：未提交表示保持原值；`null` 只在契约允许时表示清除或未设置；空字符串只在业务允许时作为有效值或明确的清除信号。创建请求及任务载荷也必须定义缺省行为，三者不得自动互换。

新增请求默认应拒绝未声明字段；修改旧模型、控制面能力声明及可扩展外部结构时，必须先检查兼容范围。明确允许扩展的协议保留扩展能力，并补验证，不能全局切换严格校验后再处理破坏。

## 数据说明与配置

持久化或回传字段必须说明业务含义，必要时包括单位、状态值、关联身份及特殊空值。关联字段区分数据库主键、平台业务标识和外部编号；快照与 JSON 说明结构、冻结时点和用途。

新增数据库表和字段必须在模型及迁移中维护准确的中文注释；数据库结构要求由控制面负责。Worker 的协议模型、产物契约和安全恢复文件按项目约定描述及验证，不为满足注释要求引入数据库依赖。

配置来源为 `config/platform.example.toml` 和本地忽略的 `config/platform.toml`，运行配置通过 `scripts/manage.py` 生成。各项目的配置加载方式和兼容环境变量保持明确，不把本地生成配置、凭据、依赖目录或运行状态提交到仓库。

## 异常日志与执行追踪

未知异常必须在服务端或 Worker 记录脱敏后的异常类型及堆栈；回传方继续输出既有安全错误格式。日志不得包含原始凭据、签名 URL、完整请求体、模型提示词、运行变量或未经清理的外部响应。第三方异常消息可能含敏感数据，记录前必须清理。

正常生命周期事件默认使用 INFO，影响执行但可恢复的失败使用 WARNING，未知异常或无法完成的操作使用 ERROR。预期参数或权限拒绝无需逐次记录完整堆栈；记录时使用安全错误码和关联标识，避免正常轮询形成重复噪声。

| 场景 | 应记录的最小追踪信息 |
| --- | --- |
| 控制面 HTTP 请求或错误 | 请求标识、方法、路由模板、状态码、业务错误码及耗时；不记录完整查询字符串 |
| AI/API/UI 执行 | 任务域及实际存在的 `task_id/run_id/worker_id`，事件、状态及耗时 |
| 集成写入与核对 | `job_id/step_key/operation_id`、相关 Worker 与领取代次、事件及安全结果码 |

新增日志必须沿用所在流程的关联标识，同一次操作不得在各层重新生成不同标识。标识应作为独立字段记录；不存在的字段保持缺省，不伪造 ID 或将秘密材料作为标识。引入 HTTP 请求标识时由入口统一生成或验证，再传入调用链，并补对应验证。

本节规定开发与审查要求，不表示现有全部日志已经满足。修改异常处理或执行流程时必须检查相关日志；存量差异按本规范记录范围和后续工单。

## 验证与交付

源码变更必须通过目标项目已有工具的 Lint、格式检查和相关回归；已有类型检查的项目同时检查本次涉及的模块。没有配置类型检查工具的项目仍须明确公共接口类型，由现有行为与契约测试验证，不为了文档一致性临时使用另一应用的检查环境。

项目规则必须提供具体测试入口。跨项目协议变更必须验证生产方和消费方；权限、数据库、领取、回传、停止及外部写入改动分别覆盖对应边界。SQLite、模拟 HTTP 和本地 fixture 的通过不能作为真实 MySQL、浏览器、S3 或禅道验收的替代。

验证范围按改动选择，共享基础层修改扩大回归。纯文档修改核对内容、路径和链接即可。必须报告实际命令、结果、跳过与未验证范围；存量错误和新增错误分别说明，不把失败或跳过写成通过。

仓库编排变更在初始化本地配置后运行根目录规定的 unittest 和 Compose 配置检查。各项目 CI 应复用已经明确的检查入口，不把尚未配置的自动检查声明为已生效。

交付前必须核对规则等级、模块边界、提交或回传责任、接口兼容、字段语义、日志安全和验证入口。没有明确完成的事项分别记录，不用固定覆盖率或文件行数代替行为验证。

已有代码的分阶段整改安排见[后端整改计划](backend-remediation-plan.md)。计划目前尚未执行，启动整改时按其工作包建立基线、台账与验收记录。
